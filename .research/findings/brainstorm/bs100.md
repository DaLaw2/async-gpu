### 1.2 GpuTensor Design

**Decision: N-dimensional with SmallVec-based shape (typical dim <= 4).**

A fixed 4D tensor would be awkward for GPT-2 (2D weight matrices, 3D [batch, seq, hidden],
4D [batch, heads, seq, d_head]). N-dimensional with runtime shape checking is the right
tradeoff — it matches PyTorch semantics and our kernels already accept flat pointers + shape args.

```rust
use smallvec::SmallVec;

/// N-dimensional GPU tensor with device memory and shape metadata.
pub struct GpuTensor {
    /// Device memory (f32). Owned — dropped when tensor is dropped.
    data: CudaSlice<f32>,
    /// Shape dimensions, e.g. [batch, channels, height, width].
    /// SmallVec avoids heap allocation for <= 4 dims.
    shape: SmallVec<[usize; 4]>,
    /// Strides in element count per dimension (row-major / C-contiguous by default).
    strides: SmallVec<[usize; 4]>,
    /// Device reference for memory operations.
    device: Arc<CudaDevice>,
}

impl GpuTensor {
    /// Create from raw device memory + shape (computes C-contiguous strides).
    pub fn from_data(data: CudaSlice<f32>, shape: &[usize], device: Arc<CudaDevice>) -> Self;

    /// Upload host data to GPU, returning a new tensor.
    pub fn from_host(data: &[f32], shape: &[usize], device: &Arc<CudaDevice>) -> Result<Self>;

    /// Download to host.
    pub fn to_host(&self) -> Result<Vec<f32>>;

    /// Allocate zeroed tensor with given shape.
    pub fn zeros(shape: &[usize], device: &Arc<CudaDevice>) -> Result<Self>;

    /// Number of elements.
    pub fn numel(&self) -> usize;

    /// Number of dimensions.
    pub fn ndim(&self) -> usize;

    /// Shape as slice.
    pub fn shape(&self) -> &[usize];

    /// Reshape (returns a view if contiguous, copies if not).
    pub fn reshape(&self, new_shape: &[usize]) -> Result<Self>;

    /// Transpose last two dimensions (needed for attention).
    pub fn transpose(&self, dim0: usize, dim1: usize) -> Result<Self>;

    /// Raw device pointer for kernel launch.
    pub fn as_ptr(&self) -> CUdeviceptr;

    /// Clone (deep copy on device).
    pub fn clone_tensor(&self) -> Result<Self>;
}
```

**Key design choices:**
- **Owns device memory** via `CudaSlice<f32>` — RAII cleanup.
- **Holds `Arc<CudaDevice>`** — can spawn new allocations without passing device everywhere.
- **f32 only** for now — f16 packing handled internally by kernels that need it (gemm_f32 already works with f32).
- **C-contiguous by default** — strides computed from shape. Non-contiguous views possible later.

### 1.3 KernelRegistry Design

The core problem: users should never write PTX function names, grid/block sizes, or launch configs.
The registry maps operation names to loaded CudaFunction handles and knows how to compute launch configs.

```rust
/// Registry of loaded GPU kernel functions with auto-config launch.
pub struct KernelRegistry {
    device: Arc<CudaDevice>,
    functions: HashMap<&'static str, CudaFunction>,
    status_host_ptr: *mut u32,
    status_dev_ptr: CUdeviceptr,
}

impl KernelRegistry {
    /// Load all ML kernels from PTX source.
    pub fn new(device: Arc<CudaDevice>, ptx_src: &str) -> Result<Self>;

    /// Get a kernel function by name (internal use).
    fn get(&self, name: &'static str) -> Result<CudaFunction>;

    /// Standard 1D launch config: grid = (n.div_ceil(256), 1, 1), block = (256, 1, 1).
    fn config_1d(n: u32) -> LaunchConfig;

    /// GEMM launch config: grid = (M.div_ceil(32), N.div_ceil(16), 1), block = (128, 1, 1).
    fn config_gemm(m: u32, n: u32) -> LaunchConfig;
}
```

### 1.4 nn Module (Layer) API

**Decision: Layers own their weights.**

This matches PyTorch's `nn.Module` pattern. Weights are uploaded once at construction time
and reused across forward passes. This avoids per-call weight upload overhead.

```rust
/// Trait for all nn layers — PyTorch-like forward().
pub trait Module {
    fn forward(&self, input: &GpuTensor) -> Result<GpuTensor>;
}

/// Linear layer: y = xW^T + b
pub struct Linear {
    weight: GpuTensor,     // [out_features, in_features]
    bias: Option<GpuTensor>, // [out_features]
    registry: Arc<KernelRegistry>,
}

impl Linear {
    pub fn new(
        weight: &[f32],
        bias: Option<&[f32]>,
        in_features: usize,
        out_features: usize,
        registry: &Arc<KernelRegistry>,
    ) -> Result<Self>;
}

impl Module for Linear {
    /// input: [..., in_features] → output: [..., out_features]
    fn forward(&self, input: &GpuTensor) -> Result<GpuTensor>;
}

/// Conv2d layer
pub struct Conv2d {
    weight: GpuTensor,       // [c_out, c_in, kh, kw]
    weight_cm: CudaSlice<f32>, // pre-transposed column-major for GEMM
    bias: Option<GpuTensor>,
    c_out: usize,
    kernel_size: (usize, usize),
    stride: usize,
    padding: usize,
    registry: Arc<KernelRegistry>,
}

/// LayerNorm
pub struct LayerNorm {
    gamma: GpuTensor,  // [normalized_shape]
    beta: GpuTensor,   // [normalized_shape]
    eps: f32,
    normalized_shape: usize,
    registry: Arc<KernelRegistry>,
}

/// BatchNorm2d (with fused SiLU option)
pub struct BatchNorm2d {
    gamma: GpuTensor,
    beta: GpuTensor,
    running_mean: GpuTensor,
    running_var: GpuTensor,
    eps: f32,
    fuse_silu: bool,  // if true, uses batchnorm_silu kernel
    registry: Arc<KernelRegistry>,
}

/// Embedding lookup table
pub struct Embedding {
    weight: GpuTensor,  // [vocab_size, embed_dim]
    vocab_size: usize,
    embed_dim: usize,
    registry: Arc<KernelRegistry>,
}
```

### 1.5 Example: GPT-2 Inference API

```rust
use gpu_host::nn::{GpuTensor, KernelRegistry};
use gpu_host::nn::models::gpt2::{Gpt2Model, Gpt2Config};

fn main() -> Result<()> {
    // 1. Init GPU
    let rt = GpuRuntime::new(0)?;
    let registry = Arc::new(KernelRegistry::new(rt.device_arc(), ptx::KERNEL)?);

    // 2. Load model
    let config = Gpt2Config::small();  // 12 layers, 768 hidden, 12 heads
    let weights = gpu_host::model::load_gpt2_weights("models/model.safetensors")?;
    let model = Gpt2Model::from_weights(&weights, &config, &registry)?;

    // 3. Tokenize
    let tokenizer = Gpt2Tokenizer::new()?;
    let tokens = tokenizer.encode("The capital of France is");

    // 4. Run inference
    let input = GpuTensor::from_host_u32(&tokens, &[1, tokens.len()], rt.device())?;
    let logits = model.forward(&input)?;  // [1, seq_len, vocab_size]

    // 5. Greedy decode
    let logits_host = logits.to_host()?;
    let next_token = logits_host[/* last position */..].iter()
        .enumerate().max_by(|a, b| a.1.partial_cmp(b.1).unwrap())
        .unwrap().0;
    println!("Next token: {}", tokenizer.decode(&[next_token as u32]));

    Ok(())
}
```

## 2. Theme Breakdown

### Theme 1: `nn-tensor` — GpuTensor Foundation
**Goal:** Unified N-dimensional tensor type with shape, strides, device memory, and basic ops.
**Success criteria:** GpuTensor can be created, uploaded, downloaded, reshaped, transposed;
replaces the old 3-field `{data, c, h, w}` struct in all code paths.

### Theme 2: `nn-registry` — Kernel Registry & Auto-Launch
**Goal:** Abstract kernel loading and launch config behind a registry.
**Success criteria:** No user code ever writes `LaunchConfig`, `get_func()`, or PTX function names.
All 87+ kernels accessible through the registry.

### Theme 3: `nn-ops` — Stateless Operations
**Goal:** Functional API for all GPU operations: `matmul()`, `conv2d()`, `layer_norm()`, etc.
Each takes `GpuTensor` inputs and returns `GpuTensor` output.
**Success criteria:** Every kernel in compute_cnn.rs, compute_transformer.rs, compute_gemm.rs
is wrapped as a stateless function.

### Theme 4: `nn-layers` — Composable Modules
**Goal:** Stateful `Module` trait implementations: `Linear`, `Conv2d`, `LayerNorm`,
`BatchNorm2d`, `Embedding`, `MultiHeadAttention`, `GELU`, `SiLU`, `MaxPool2d`.
**Success criteria:** Each layer owns weights, implements `forward()`, can be composed
into models without manual kernel management.

### Theme 5: `nn-gpt2` — GPT-2 Model
**Goal:** `Gpt2Model` struct that loads weights from safetensors and runs full inference
through the nn API. Standalone example binary.
**Success criteria:** `examples/gpt2_inference.rs` generates coherent text using only the
nn API. No raw kernel launches in user code.

### Theme 6: `nn-yolo` — YOLOv8-nano Model
**Goal:** `YoloV8Nano` struct that loads weights and runs detection pipeline through nn API.
Standalone example binary.
**Success criteria:** `examples/yolov8_detect.rs` produces bounding boxes on test images
using only the nn API. No raw kernel launches in user code.

### Theme 7: `nn-migrate` — Legacy Code Migration
**Goal:** Rewrite existing test code (tests_inference.rs, tests_cnn.rs, yolo_backbone.rs)
to use the nn API. Apply patched-std where applicable.
**Success criteria:** Old hardcoded runner code removed. Tests pass using nn API.

**Why before YOLO:** GPT-2 exercises the transformer path (LayerNorm, attention, GELU, Linear,
Embedding). The existing tests_inference.rs provides a reference implementation to validate against.

### Phase 4: YOLOv8 Model (theme 6)
Build order: `nn-yolo.1` → `.2` → `.3` → `.4` → `.5` → `.6` → `.7` → `.8` → `.9`

**Why after GPT-2:** YOLO exercises the CNN path (Conv2d, BatchNorm, MaxPool, Upsample, Concat).

full reference. More confident in the nn API after GPT-2 validates it.

### Phase 5: Migration (theme 7)
Build order: `nn-migrate.5` → `.2` → `.1` → `.3` → `.4`

**Why last:** Only migrate after both models work. Migration is refactoring, not new functionality.

## 5. Risk Assessment

### Risk 1: GEMM padding / transpose complexity (HIGH)
**What:** The existing `gemm_f32` kernel expects column-major weight matrices with N padded
to multiples of 16. The current `conv2d()` in yolo_backbone.rs does a CPU-side transpose
after GEMM to go from `[HW, C_out]` to `[C_out, HW]`. This is slow and must be replaced
with either a GPU transpose kernel or a smarter layout strategy.

**Mitigation:** Add a dedicated `transpose_2d` kernel to gpu-kernel, or change the GEMM kernel
to output in the desired layout. Alternatively, keep tensors in `[M, N]` row-major after GEMM
and let downstream ops work with that layout (requires strides-aware ops).

### Risk 2: Strides / non-contiguous tensors (MEDIUM)
**What:** Some ops (reshape, transpose, split) can produce non-contiguous tensors. If kernels
assume contiguous memory, results will be wrong silently.

**Mitigation:** For v1, always materialize contiguous tensors after transpose/split (copy to new
buffer with correct layout). Add an `is_contiguous()` check and auto-contiguify before kernel launch.
Non-contiguous views are a v2 optimization.

### Risk 3: conv2d CPU-side transpose bottleneck (MEDIUM)
**What:** The current Conv2d pipeline downloads GEMM output to CPU for transpose, then re-uploads.
This kills GPU occupancy and adds PCIe latency.

**Mitigation:** Write a simple GPU transpose kernel (one thread per element, no shared memory
needed for correctness). Or restructure the GEMM weight layout so output is already in the
desired format. The `gemm_f32` kernel computes `C = A * B` where A is `[M, K]` and B is
`[K, N]` column-major. If we store weights as `[C_out, K]` in the right layout, the output
`[M, C_out]` may already be what we want.

### Risk 4: flash_attention launch config complexity (MEDIUM)
**What:** `flash_attention` and `flash_attention_kv` kernels have complex launch requirements
(shared memory for Q/K/V tiles, specific block sizes). Abstracting this behind a clean API
while maintaining correctness is tricky.

**Mitigation:** Start with the simpler `attention_head` kernel for correctness testing, then
swap in flash_attention for performance. Document exact launch requirements in KernelRegistry.

### Risk 5: Weight format mismatch between safetensors and kernel expectations (LOW)
**What:** PyTorch saves weights in `[out_features, in_features]` row-major, but our GEMM
kernel may expect column-major. The existing code already handles this (weight reshaping in
yolo_backbone.rs), but it needs to be systematized.

**Mitigation:** `Linear::new()` and `Conv2d::new()` handle weight format conversion at
construction time (once, not per forward pass). Document expected formats clearly.

### Risk 6: Feature gate complexity (LOW)
**What:** The nn module adds a new dependency (smallvec) and significant code. It should be
feature-gated to avoid bloating builds that don't need ML.

**Mitigation:** Add `nn` feature flag in gpu-host's Cargo.toml. Use `#[cfg(feature = "nn")]`
on the module. SmallVec is tiny and no_std compatible, minimal impact.

### Risk 7: No batch dimension support in existing kernels (LOW)
**What:** Most existing kernels operate on single tensors without a batch dimension. GPT-2
works with batch=1, YOLO works with batch=1. But the GpuTensor type supports N dimensions,
which could mislead users into expecting batched execution.

**Mitigation:** Document batch=1 limitation clearly. The nn layers can validate that the
batch dimension is 1 and return a clear error otherwise. Batched execution is a v2 feature.

## 7. Key Design Decisions Summary

| Decision | Choice | Rationale |
|----------|--------|-----------|
| Tensor dimensionality | N-dim with SmallVec | GPT-2 needs 2D/3D/4D; fixed-4D is too rigid |
| Weight ownership | Layers own weights | Upload once, reuse — matches PyTorch nn.Module |
| Module location | `gpu-host/src/nn/` submodule | Avoids new crate, shares error types and runtime |
| Error type | `NnError` via thiserror | Project prohibits anyhow; need structured errors |
| Tensor dtype | f32 only (v1) | All existing kernels work with f32; f16 packing internal |
| Strides | Always materialize contiguous | Simpler v1; non-contiguous views are future work |
| Batch support | batch=1 only (v1) | Matches existing kernels; batching is v2 |
| Feature gate | `#[cfg(feature = "nn")]` | Optional; doesn't bloat non-ML builds |
