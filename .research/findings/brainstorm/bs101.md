## Status: Brainstorm
## Date: 2026-03-15
## Context: 22 completed epics, 462 tasks, 3 active epics (verify-examples, codebase-health, developer-experience)

## 1. Reopen Candidates

### 1.1 gpu-perf (PARKED criteria 2-4)

**Parked criteria:**
- Per-token generation latency < 20ms (down from ~143ms, currently ~26ms with MMA)
- BF16/TF32 MMA inference matches f32 FMA output (top-5 agreement)
- Mixed precision pipeline: GEMM via Tensor Core, everything else f32

**Assessment: WORTH REOPENING (medium priority)**

The 26ms/token achieved with Split-K MMA is good but not competitive with production
inference engines (vLLM targets <5ms/token for GPT-2-scale on A100). The gap is primarily:
1. No kernel fusion — each layer launches a separate kernel (launch overhead ~5-10us each,
   12 transformer blocks x ~6 kernels = 72 launches = ~0.5ms overhead alone)
2. No persistent kernel — the executor could keep a single kernel alive across layers
3. Memory bandwidth — no quantized weights, full f32 intermediates

**Skeptic challenge:** Is sub-20ms actually needed? This is a research framework, not a
production inference server. The 26ms number already proves Tensor Core utilization works.
Chasing vLLM-level latency would require architectural changes (paged attention, continuous
batching) that are out of scope for a "Rust async on GPU" demo project.

**Verdict:** Reopen ONLY if user wants to pursue kernel fusion as a research direction.
The latency target itself is less important than the architectural patterns to get there.

### 1.2 benchmarks (completed)

**What exists:** Hostcall latency/throughput benchmarks with thread scaling.

**What's missing:**
- No nn API benchmarks (layer-level and model-level latency breakdown)
- No comparison with cuDNN/cuBLAS for individual operations
- No memory usage benchmarks (peak VRAM, allocation patterns)
- No multi-GPU scaling benchmarks

**Assessment: LOW VALUE to reopen**

The existing benchmarks serve their purpose — they prove the hostcall protocol works at
scale. Adding nn-level benchmarks would be useful for optimization but is better done as
part of a gpu-perf reopen, not as a standalone epic.

**Skeptic challenge:** Who reads these benchmarks? They validate the system for the
developers, but external users care about end-to-end model throughput, not hostcall
microbenchmarks. Better to invest in making the system usable than making numbers smaller.

**Verdict:** Do NOT reopen. Fold any benchmark needs into gpu-perf or verify-examples.

### 1.3 public-api (completed)

**What exists:** GpuRuntime, HostcallBuffer, HostcallSession as public API. 3 examples.

**What's missing:**
- nn module API is not part of the public-api epic's scope
- No versioned API stability guarantees
- No migration guide from raw hostcall to nn API

**Assessment: LOW VALUE to reopen**

The nn API (ml-framework epic) already covers the higher-level public API. The raw
hostcall API is stable and documented. Reopening this would just generate busywork.

**Skeptic challenge:** Valid — the public-api epic met its criteria. New API surface
(nn module) was handled by ml-framework. Don't double-count.

**Verdict:** Do NOT reopen. Any API work belongs in new epics.

### 1.4 gpu-inference (archived, incomplete)

**What existed:** Early full-inference theme with pending tasks (full-inference.12, .13).

**Assessment: SUPERSEDED**

The ml-framework epic completely superseded gpu-inference. GPT-2 and YOLOv8 both work
end-to-end through the nn API. The archived tasks are no longer relevant.

**Verdict:** Do NOT reopen. Fully superseded.

### 1.5 async-std (warp-batch-io theme PARKED)

**Parked theme:** Warp-batched hostcall — 32 lanes share 1 packet (warp-batch-io.2-.4 pending).

**Assessment: INTERESTING RESEARCH but low practical impact**

The warp-batch-io optimization would reduce hostcall packet contention when all 32 lanes
in a warp need the same I/O. In practice, the current system already works because:
1. Warp-cooperative async already has lane-0 submit + shfl.sync broadcast
2. The main bottleneck is host-side I/O latency, not packet allocation
3. The 10x throughput improvement target assumes uniform I/O across all lanes, which
   is unrealistic for most workloads

**Skeptic challenge:** This optimization only matters if hostcall throughput is the
bottleneck, and benchmarks show it isn't. Host I/O latency dominates. Optimizing the
packet allocation path is premature.

**Verdict:** Leave PARKED. Could be unparked if someone builds a workload that's
packet-allocation-bound (e.g., massively parallel file reads).

## 2. New Epic Ideas

### 2.1 EPIC: `autograd` — Automatic Differentiation for Training on GPU

**What:** Backward pass computation graph for GpuTensor operations. tape-based autograd
that records forward ops and replays backward passes. Enables training, not just inference.

**Themes:**
- autograd-tape: Record computation graph during forward pass
- autograd-backward: Implement backward kernels for all nn ops (matmul, conv2d, layernorm, etc.)
- autograd-optim: SGD, Adam optimizers updating weights in-place on GPU
- autograd-demo: Train a small model (MNIST MLP or tiny transformer) on GPU

**Impact: VERY HIGH** — This is the single biggest capability gap. The project can run
inference but cannot train. Training is what makes a GPU compute framework actually useful
for ML researchers. Without autograd, this is a demo, not a tool.

**Feasibility: HIGH** — The nn ops are already structured as stateless functions taking
and returning GpuTensor. Adding a tape that records {op, inputs, output} and then replaying
backward ops is architecturally straightforward. The hardest part is writing backward
kernels (gemm_backward, conv2d_backward, layernorm_backward), but these are well-documented
mathematical operations.

**Skeptic challenge:**
- Is anyone going to train models with a custom Rust GPU framework instead of PyTorch?
  Probably not for production. But autograd is the canonical proof that a GPU compute
  framework is "real" — it transforms async_gpu from "cool demo" to "actual framework."
- Scope risk: backward kernels for conv2d and attention are complex. Could easily
  spiral into 50+ tasks. Mitigation: start with MLP-only (Linear + activations) and
  expand incrementally.
- Performance: training requires many more operations than inference (2-3x FLOPS for
  backward pass). The hostcall overhead might become visible. Mitigation: training
  doesn't need hostcall for compute — only for I/O (loading data).

**Estimated effort:** 40-60 tasks across 4 themes.

### 2.2 EPIC: `gpu-safety` — Memory Safety and Resource Lifetime Guarantees

**What:** Formalize GPU memory safety beyond what Rust's type system currently enforces.
The current system uses raw pointers, manual lifetime management for device memory, and
unsafe kernel launches extensively. This epic would:
- Add a borrow-checker-like lifetime system for GPU memory (GpuRef<'a, T>)
- Prevent use-after-free of device memory across kernel launches
- Prevent data races between concurrent kernels accessing the same buffer
- Integrate with the CUDA stream system to enforce execution ordering at the type level

**Themes:**
- gpu-lifetime: GpuRef<'a, T> that tracks device memory lifetimes
- gpu-borrow: &GpuTensor (shared) vs &mut GpuTensor (exclusive) for kernel args
- gpu-stream-safety: Stream-ordered memory access — type system prevents cross-stream races
- gpu-audit: Audit all existing unsafe blocks, document safety invariants

**Impact: HIGH** — This is what would make async_gpu genuinely novel. No existing GPU
framework (CUDA, ROCm, Vulkan compute, wgpu) has compile-time GPU memory safety. This
is the "Rust for GPUs" value proposition.

**Feasibility: MEDIUM** — The lifetime tracking for device memory is tractable (similar
to how cudarc handles it). The hard part is making it ergonomic without requiring lifetime
annotations everywhere. Stream-ordered safety is research-grade — no one has done this
well in a systems language.

**Skeptic challenge:**
- CUDA developers have survived without compile-time GPU memory safety for 15+ years.
  Is this actually needed? Counter: Rust developers survived without ownership before
  Rust, but ownership turned out to be transformative. GPU memory bugs are notoriously
  hard to debug (silent corruption, nondeterministic failures).
- Risk of making the API unusable — too many lifetime parameters, ergonomic death by
  a thousand annotations. Mitigation: use inference-heavy design, sensible defaults,
  and unsafe escape hatches for power users.

**Estimated effort:** 25-35 tasks across 4 themes.

### 2.3 EPIC: `dynamic-graphs` — Dynamic Computation Graphs with GPU-Side Control Flow

**What:** Enable data-dependent control flow in GPU compute graphs. Currently, all
compute graphs are static (the host decides the execution order). This epic would allow
the GPU executor to make branching decisions:
- Conditional execution: if tensor.sum() > threshold, run path A, else path B
- Early stopping: halt generation when EOS token is produced (without host roundtrip)
- Dynamic shapes: handle variable-length sequences without padding
- Loop fusion: GPU-side loop over transformer layers without per-layer host intervention

**Themes:**
- dynamic-cond: GPU-side conditional execution (branch on tensor values)
- dynamic-loop: GPU-side loops with convergence checking
- dynamic-shape: Variable-length tensor support (ragged tensors or mask-based)
- dynamic-demo: GPT-2 generation with GPU-side EOS detection

**Impact: MEDIUM-HIGH** — This is where async_gpu's architecture uniquely shines. The
hostcall + executor model means the GPU is already an autonomous agent that can make
decisions. Other frameworks (TensorRT, ONNX Runtime) struggle with dynamic control flow
because they compile static graphs. async_gpu's interpreter-style executor is inherently
dynamic.

**Feasibility: MEDIUM** — The executor already supports dynamic task spawning. Adding
conditional execution is architecturally natural. The hard part is tensor-value-dependent
branching (requires reading a scalar from a tensor without a full device-to-host copy,
which means either a small hostcall or a device-side comparison kernel).

**Skeptic challenge:**
- The gpu-autonomous epic already demonstrated data-dependent iteration and convergence
  checking at the kernel level. How is this different? Answer: that was raw inline PTX.
  This epic wraps it in the nn API so users don't write PTX.
- Performance concern: GPU-side branching on tensor values requires sync points.
  Mitigation: only sync on scalar reductions, not full tensors.

**Estimated effort:** 20-30 tasks across 4 themes.

### 2.4 EPIC: `gpu-interop` — Interoperability with Existing GPU Ecosystems

**What:** Enable async_gpu to work alongside existing GPU libraries and frameworks:
- Load cuDNN/cuBLAS as optional acceleration backends
- Export tensors to/from PyTorch via shared CUDA memory (zero-copy)
- Vulkan interop for graphics + compute hybrid workflows
- ONNX model import (parse ONNX protobuf, map ops to nn API)

**Themes:**
- interop-cublas: Optional cuBLAS GEMM backend (for users who have it installed)
- interop-pytorch: Share CUDA memory with PyTorch via DLPack or cuda_array_interface
- interop-onnx: ONNX model loader mapping to nn Module graph
- interop-vulkan: Vulkan-CUDA buffer sharing for graphics pipelines

**Impact: MEDIUM** — Interop makes the project useful in real workflows. Without it,
async_gpu is an island. With ONNX import, any model becomes runnable. With PyTorch
interop, async_gpu becomes a Rust acceleration backend for Python ML.

**Feasibility: LOW-MEDIUM** — Each interop target is a significant integration effort.
cuBLAS FFI is well-trodden (cudarc already supports it). ONNX parsing is tedious but
mechanical. PyTorch memory sharing requires careful lifetime management. Vulkan interop
is the hardest (requires Vulkan external memory extensions).

**Skeptic challenge:**
- If users want cuBLAS, why not just use cuBLAS directly? Counter: the value is
  seamless integration — use async_gpu's nn API for the graph, cuBLAS for the GEMM,
  without the user managing two separate memory spaces.
- ONNX import is a massive undertaking (hundreds of ops). Counter: only need to support
  the ops already in the nn API (~15 ops). Unsupported ops fail with a clear error.
- Dependency policy says "no external dependencies beyond what's already in the project."
  cuBLAS/cuDNN/PyTorch are external. This may be blocked by project constraints.

**Estimated effort:** 30-50 tasks across 4 themes.

### 2.5 EPIC: `kernel-fusion` — Automatic Kernel Fusion for Performance

**What:** Automatically merge sequential kernel launches into a single fused kernel to
eliminate launch overhead and intermediate memory allocations:
- LayerNorm + Linear fusion (elementwise → GEMM in one kernel)
- GELU + bias fusion
- Residual add + LayerNorm fusion
- General pattern: detect fusable op sequences in the nn graph and emit fused PTX

**Themes:**
- fusion-patterns: Identify common fusable patterns in GPT-2 and YOLO graphs
- fusion-codegen: PTX template system for generating fused kernels
- fusion-nn: Integration with nn Module forward() — auto-detect and apply fusions
- fusion-benchmark: Measure speedup from fusion (target: 2x end-to-end)

**Impact: HIGH** — Kernel fusion is the #1 optimization technique in production inference.
The current system launches 72+ kernels per GPT-2 forward pass. Fusing even the obvious
pairs (residual+layernorm, bias+gelu) could cut launch count in half and eliminate
intermediate buffer allocations.

**Feasibility: MEDIUM** — Pattern-based fusion (hardcoded pairs) is straightforward.
General fusion (arbitrary op sequences) is a compiler problem and very hard. Recommend
starting with 3-5 hardcoded fusion patterns and measuring impact before going general.

**Skeptic challenge:**
- The hostcall architecture means kernel launch is even more expensive than CUDA (host
  roundtrip per launch). So fusion has MORE benefit here than in vanilla CUDA.
  Counter-counter: the persistent kernel + executor model already amortizes launch
  cost. The real benefit is eliminating intermediate buffers and memory bandwidth.
- Is codegen realistic? Generating correct PTX from templates is error-prone. Mitigation:
  handwrite the 5 most important fused kernels, don't try to generalize.

**Estimated effort:** 20-30 tasks across 4 themes.

### 2.6 EPIC: `wasm-gpu` — WebAssembly Target for Browser-Based GPU Compute

**What:** Compile the host-side runtime to WASM and use WebGPU for compute, enabling
async_gpu programs to run in a browser. This would make demos instantly accessible.

**Impact: MEDIUM** — Great for demos and accessibility. Would make async_gpu the first
Rust GPU async framework runnable in a browser.

**Feasibility: VERY LOW** — The entire system is built on CUDA. WebGPU has a completely
different compute model (no inline PTX, no shared memory control, no warp-level ops).
This would essentially be a full rewrite of the kernel side.

**Skeptic challenge:** This is a different project, not an extension of async_gpu.
The value proposition of async_gpu is CUDA-specific (hostcall, warp cooperation,
Tensor Core MMA). None of that translates to WebGPU.

**Verdict:** REJECT. Out of scope.

### 2.7 EPIC: `testing-infra` — Comprehensive Test Infrastructure

**What:** Build proper test infrastructure beyond the current manual test files:
- Property-based testing for tensor operations (arbitrary shapes, values)
- Numerical accuracy test harness (compare GPU vs CPU with configurable tolerance)
- Regression test suite with golden outputs for GPT-2 and YOLO
- CI that actually runs GPU tests (requires GPU in CI, or mock-based testing)

**Themes:**
- test-proptest: Property-based tests for tensor ops (uses proptest crate)
- test-golden: Golden output files for model inference (checked into repo)
- test-numerical: Numerical accuracy framework with ULP and relative error metrics
- test-ci: GPU-capable CI or mock-based test execution

**Impact: MEDIUM-HIGH** — The project has 462 completed tasks but the test infrastructure
is ad-hoc. Model outputs are validated by eyeballing. A regression in conv2d could silently
break YOLO without anyone noticing until the example is run manually.

**Feasibility: HIGH** — Most of this is standard software engineering. Property-based
testing with proptest is well-established in Rust. Golden files are trivial. The only
hard part is GPU CI (requires cloud GPU instances or self-hosted runner with CUDA).

**Skeptic challenge:**
- The verify-examples epic already covers running examples end-to-end. How is this
  different? Answer: verify-examples is a one-time validation pass. testing-infra is
  ongoing infrastructure that catches regressions automatically.
- Without GPU CI, tests can only run locally. That limits the value. Mitigation: the
  numerical accuracy harness and golden files are useful even without CI — they
  make local testing systematic instead of ad-hoc.

**Estimated effort:** 15-25 tasks across 4 themes.

## 4. Recommended Next Actions

### If the goal is "make async_gpu a credible framework":
1. **testing-infra** (immediate) — foundation for everything else
2. **autograd** (next) — the capability that makes or breaks framework credibility
3. **gpu-safety** (parallel) — the unique differentiator

### If the goal is "optimize what exists":
1. **kernel-fusion** (immediate) — biggest bang for effort
2. **gpu-perf reopen** (after fusion) — now latency targets are achievable
3. **testing-infra** (parallel) — catch regressions from optimization work

### If the goal is "attract external users":
1. **testing-infra** (immediate) — users need confidence the system works
2. **dynamic-graphs** (next) — showcase async_gpu's unique architecture
3. **gpu-interop** (ONNX) — let users bring their own models

## 5. Key Insight

The project has reached a critical inflection point. With 22 epics completed, the
**breadth** of capabilities is impressive: hostcall protocol, async executor, patched std,
MIR compiler pass, nn framework, object detection, TCP networking, formal verification.

What's missing is **depth** in any single direction:
- ML: inference works but no training (autograd)
- Safety: works but no compile-time guarantees (gpu-safety)
- Performance: works but no fusion or optimization (kernel-fusion)
- Testing: works but no regression protection (testing-infra)

The most impactful move is to pick ONE depth direction and go deep, rather than adding
more breadth. The recommendation is **testing-infra + autograd** as the combination
that transforms async_gpu from "impressive demo" to "credible framework."
