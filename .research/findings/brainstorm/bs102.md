**Date**: 2026-03-15
**Level**: Deep (proposer + skeptic)
**Direction**: Foundation → Testing → Training → Safety

---

## Consensus Points (Proposer + Skeptic agree)

### 1. verify-examples is correctly scoped and must go first
Both agree this is essential and low-risk. No changes needed.

### 2. Autograd is the highest-impact but highest-risk epic
- Proposer estimates ~35 tasks; Skeptic warns this could spiral to 40+
- Both agree **flash attention backward is too hard for v1** — decompose into matmul+softmax+matmul
- Both agree **conv2d backward needs col2im**, which is new but feasible kernel work
- Both agree VRAM fits for GPT-2 Small training (~2GB at seq=32)

### 3. Element-wise backward kernels are trivial
GELU, SiLU, sigmoid, ReLU backward are ~20 lines of PTX each. No risk.

### 4. GEMM backward reuses existing kernels
`dA = dC · B^T` and `dB = A^T · dC` are just transposed matmuls. Zero new kernel code.

### 5. Golden-file tests are more valuable than property-based tests
Skeptic argues property-based testing is overkill for 13 GPU ops — boundary-condition golden files from PyTorch give better coverage with less infrastructure. Proposer's property tests should be downscoped to CPU-only tape logic.

---

## Key Disputes and Resolutions

### Dispute 1: Full tape-based autograd vs manual backward?

**Proposer**: Full tape with TapeEntry, TensorPool, OpKind enum. Records graph, traverses backward automatically. `loss.backward()` API.

**Skeptic**: Manual backward per module is simpler, sufficient for known architectures (GPT-2/YOLO fine-tuning), avoids tape complexity.

**Resolution**: **Start with tape-based approach, but minimal scope.** The tape API (`loss.backward()`) is the expected interface for any ML framework. Manual backward is a dead-end — users won't adopt it. However, scope v1 to **linear models only** (skip conv2d/attention backward). This gives tape + backward + optimizer in ~20 tasks.

### Dispute 2: Is gpu-safety (GpuRef) actually needed?

**Proposer**: GpuRef prevents use-after-free, adds zero-cost lifetime tracking, enables safe kernel launches.

**Skeptic**: `CudaSlice<f32>` is already RAII with `!Copy`. GpuRef only prevents bugs in `unsafe` code the user intentionally writes. The real value is **zero-copy tensor views**, not safety. Rename the epic.

**Resolution**: **Run a 2-task investigation spike before committing to a full epic.** The spike should:
1. Document 3 concrete bug scenarios GpuRef would prevent
2. Assess whether zero-copy views (reshape/slice without copy) are the actual need

If the spike shows GpuRef is just a view optimization → reframe as "tensor-views" epic.
If it shows genuine safety gaps → proceed as gpu-safety.

### Dispute 3: Autograd scope — how many tasks?

**Proposer**: 9 themes, 35 tasks covering all 13 ops + tape + optimizers + losses.

**Skeptic**: Split into v1 (linear models, ~15 tasks) and v2 (conv + attention, ~20 tasks).

**Resolution**: **Split autograd into two phases.**

**autograd-v1** (~20 tasks): Tape + Linear/LayerNorm/GELU/Embedding backward + SGD/Adam + cross-entropy loss + train MNIST MLP
**autograd-v2** (~20 tasks): Conv2d/BatchNorm/MaxPool backward + gradient checkpointing + mixed-precision awareness

v1 is sufficient to prove training works. v2 enables YOLO/CNN training.

### Dispute 4: Ordering — gpu-safety spike timing

**Proposer**: gpu-safety after autograd (need tape patterns to motivate lifetimes).

**Skeptic**: Resolve gpu-safety question BEFORE autograd (if GpuRef is needed, autograd should use it from the start).

**Resolution**: **Run gpu-safety spike in parallel with verify-examples.** This is purely a design investigation (no code changes). The result informs whether autograd uses GpuRef or not.

## Key Insight

The project needs **depth over breadth**. The safest path is:
1. **Validate what exists** (verify-examples)
2. **Build regression protection** (testing-infra)
3. **Add the transformative capability** (autograd-v1 for linear models)
4. **Decide** whether to go deeper on training (autograd-v2) or safety (gpu-safety)

The biggest risk is autograd scope explosion. The v1/v2 split contains this risk by delivering a working training demo in ~20 tasks before tackling the hard kernels (conv2d, attention backward).
