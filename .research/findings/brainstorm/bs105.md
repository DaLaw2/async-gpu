## Technical Analysis

### 1. Generic SafeTensors Loader — How Hard? What Schema?

**Current loading patterns examined:**

| Aspect | GPT-2 (`model.rs`) | YOLO (`model_yolo.rs`) |
|--------|-------|------|
| Loader | `load_gpt2_weights()` — hardcoded tensor names, shapes, struct fields | `load_yolo_weights()` → `load_all_tensors()` → `HashMap<String, (Vec<f32>, Vec<usize>)>` |
| Weight struct | Typed: `Gpt2Weights { wte, wpe, ln_f, layers: Vec<TransformerLayerWeights> }` | Generic: `YoloWeights { tensors: HashMap<String, TensorData> }` with accessor methods |
| Name convention | HuggingFace: `h.{i}.attn.c_attn.weight`, `wte.weight` | Ultralytics: `model.{idx}.conv.weight`, `model.22.cv2.0.0.conv.weight` |
| Shape handling | Strict validation per tensor | Flexible — reads shape from safetensors metadata |
| Weight transforms | Conv1D→Linear transpose (`[in, out]` → `[out, in]`) | None (already in PyTorch layout) |

**What a generic loader would need:**

```
ModelDef schema (conceptual):
  - architecture_type: "transformer" | "cnn" | "hybrid"
  - tensor_name_pattern: regex/template for mapping
  - per-layer config:
      - layer_type: Linear | Conv2d | LayerNorm | BatchNorm2d | Embedding
      - weight_key: "h.{i}.attn.c_attn.weight"
      - shape_transform: Optional<Transpose | Reshape | None>
      - dtype_convert: Optional<f16_to_f32 | None>
  - global tensors: [{key, target_field, shape_validation}]
```

**Estimated effort:** ~20-25 hours for a usable schema + loader.

**The fundamental problem:** YOLO already uses a generic approach (`load_all_tensors` + `HashMap`). GPT-2 has a typed struct because it needs Conv1D→Linear transposition. The "generic" part is really just:
1. A config file describing tensor name patterns → nn layer mapping
2. Optional weight transforms (transpose, reshape)

This is a TOML/JSON config parser, not deep infrastructure. And each new architecture would still need:
- Architecture-specific model struct (like `YoloV8Nano` or `Gpt2Model`)
- Architecture-specific forward pass
- Architecture-specific weight transform logic

The loader only saves ~50 lines of boilerplate per model. Not worth 25 hours.

### 2. Other Directions Worth Exploring

#### A. ResNet (inference + training) — HIGH VALUE
**What we have:** Conv2d, BatchNorm2d, ReLU, MaxPool2d, Linear, Sequential — everything needed for ResNet forward pass. Conv2d backward computes dInput. Autograd tape exists.

**What's missing for training:**
- `conv2d_backward_dweight` (critical — currently only dInput)
- `batch_norm_backward` (dInput, dGamma, dBeta — currently passthrough in backward.rs)
- Avg pooling (ResNet uses global average pool before FC)

**Why valuable:**
- ResNet-18 uses ONLY layers we already have (conv, bn, relu, maxpool, avgpool, linear)
- Safetensors files available on HuggingFace for all ResNet variants
- Loading is trivial — PyTorch state_dict naming is clean: `layer1.0.conv1.weight`
- Would be the 3rd architecture (after GPT-2 and YOLO), proving generality
- Training on CIFAR-10 is a natural next step (we already have CIFAR-10 data loading)

**Effort:** ~15h (inference) + ~20h (training with missing backward kernels)

#### B. f16/Mixed Precision Training — MEDIUM VALUE
**What we have:** Tensor Core MMA for f16 inference GEMM.

**What's missing:** f16 storage tensors, loss scaling, f16 backward kernels, master weight copies.

**Why defer:** Adds complexity to every kernel. The project is a research framework — f32 training is fine for demonstrating concepts. Mixed precision is an optimization, not a capability.

**Effort:** ~40h+ (touches every kernel)

#### C. BatchNorm2d Backward — HIGH VALUE (prerequisite)
Currently a passthrough in `backward.rs:180`. Needed for any CNN training (ResNet, YOLO fine-tuning).

**Effort:** ~8h (kernel + host wrapper + tape integration + tests)

#### D. Conv2d Backward dWeight — HIGH VALUE (prerequisite)
Currently only computes dInput. Without dWeight, we cannot train any CNN.

**Effort:** ~10h (im2col(input)^T x d_output approach)

#### E. Average Pooling — LOW EFFORT
Simple kernel, needed for ResNet global average pool.

**Effort:** ~3h

#### F. Better Conv2d Performance (batched backward) — LOW PRIORITY
The conv2d works. Performance optimization can wait until we have correct training first.

## Skeptic Challenges

### "Is generic-loader useful if we only support 2 architectures?"
**No.** With 2 architectures, we don't even know what the right abstraction is. YOLO and GPT-2 have radically different naming conventions, weight layouts, and transform requirements. Building a "generic" loader now means guessing at a schema that might not fit architecture #3. Better to add ResNet with a simple loader, then see if a pattern emerges across 3 concrete cases.

### "What's the real user value vs. complexity?"
The generic loader saves ~50 lines of boilerplate per model. At 25 hours of development, that's 500 lines of framework code to save 50 lines of model code. The ROI is negative until we have 10+ architectures — which is not the goal of a research framework.

**What DOES have user value:**
- A 3rd working architecture (ResNet) proves the nn module is general, not just GPT-2+YOLO-specific
- CNN training (CIFAR-10 ResNet) demonstrates the autograd system works for vision
- These are capabilities users care about, not loading convenience

## Recommendations

### Priority 1: Fix CNN Training Foundation (~18h)
These are prerequisites for ResNet training AND improvements to existing CIFAR-10/MNIST CNN training:

| Task | Effort | Why |
|------|--------|-----|
| `conv2d_backward_dweight` PTX kernel | 10h | Without this, no CNN can train |
| `batch_norm_backward` PTX kernel | 8h | Required for any BN-based model training |

### Priority 2: ResNet-18 Inference + Training (~18h)
| Task | Effort | Why |
|------|--------|-----|
| `avg_pool2d` forward kernel | 3h | ResNet needs global average pooling |
| ResNet-18 model struct + weight loader | 5h | 3rd architecture, proves generality |
| ResNet-18 CIFAR-10 training example | 10h | End-to-end CNN training demo |

### Priority 3: PARK generic-loader
- Only revisit when adding architecture #4
- By then, patterns from GPT-2/YOLO/ResNet will inform the right abstraction

### What NOT to do
- **ONNX**: Out of scope (BS-104 consensus)
- **f16 training**: Optimization, not capability. Defer indefinitely.
- **Conv2d performance**: Correctness first, performance second
- **Generic loader**: Premature abstraction

## Summary

The project's next natural step is proving CNN training works end-to-end. This requires two missing backward kernels (conv2d dWeight, batch_norm backward) plus a small avg_pool kernel. With those, ResNet-18 on CIFAR-10 becomes a compelling 7th example that demonstrates the framework handles both transformers AND CNNs. The generic loader should be parked — it's infrastructure that doesn't serve a real use case yet.
