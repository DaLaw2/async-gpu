## Analysis: Criterion 1 — extern "gpu-kernel" vs extern "ptx-kernel"

### The Contradiction
ADR-1 (accepted 2026-03-11) explicitly chose `extern "ptx-kernel"` over `extern "gpu-kernel"` with clear rationale: ptx-kernel is stable on nvptx64, gpu-kernel is functionally identical on NVPTX, VectorWare uses ptx-kernel. The criterion was likely written BEFORE ADR-1 was finalized, reflecting an aspirational direction.

### Technical Reality
- `extern "gpu-kernel"` IS available behind `#[cfg(feature = "gpu_kernel_abi")]` in the patched rustc. A working `gpu_kernel_demo` already exists in `thread_test.rs`.
- On nvptx64, `gpu-kernel` and `ptx-kernel` generate identical LLVM IR. The only difference is the name.
- `gpu-kernel` is the cross-vendor future (needed for AMD/Vulkan in the T2 `cross-vendor` epic).
- BUT: migrating all kernels to `gpu-kernel` today gains nothing for NVIDIA and adds a feature gate dependency on the patched rustc.

### Recommendation: UPDATE THE CRITERION
The criterion should be updated to reflect ADR-1's decision. The spirit of the criterion (clean kernel entry) is already satisfied — `extern "ptx-kernel" fn main()` with `#[no_mangle]` IS the clean entry point for the nvptx64 target. The `unsafe` and `#![feature(abi_ptx)]` are inherent to the target, not fixable at the library level.

**Proposed rewording**: "Kernel entry uses `extern \"ptx-kernel\"` (per ADR-1) with no custom attribute macros needed beyond standard Rust features."

**Defer `gpu-kernel` migration to the T2 `cross-vendor` epic** where it actually matters. Doing it now is make-work that serves no user.

## Analysis: Criterion 4 — Example Conversion

### Current State

**Hostcall examples (examples/hostcall/)**:
| Example | Host API | Kernel Side | Convertible? |
|---------|----------|-------------|-------------|
| hello-gpu | gpu::run_with_output ✓ | raw hostcall | Yes (already converted host) |
| async-io | gpu::run_with_output ✓ | raw hostcall | Yes (already converted host) |
| async-pipeline | gpu::run_with_output ✓ | WarpFuture + raw hostcall | Yes (already converted host) |
| thread-demo | gpu::launch ✓ | thread::spawn | Yes (already converted host) |
| vector-math | GpuRuntime + manual | raw compute kernels | HARD — 4-argument saxpy, multi-kernel softmax |
| parallel-search | GpuRuntime + HostcallSession + MappedBuffer | raw hostcall + shfl.sync | HARD — 6-argument kernel, sideband, mapped buffers |
| tcp-echo | GpuRuntime + HostcallSession + MappedBuffer | raw hostcall TCP | HARD — 4-argument kernel, external TCP server |
| warp-cooperative | CudaDevice + raw PTX load | low-level WarpFuture demo | INTENTIONAL — demonstrates MIR pass output |

**Std examples (examples/std/)**:
| Example | Host API | Notes |
|---------|----------|-------|
| thread-demo | gpu::launch ✓ | Clean, idiomatic |
| benchmark | direct cudarc | Performance measurement — needs raw control |
| gpt2-inference | KernelRegistry + nn ops | High-level but nn-specific |
| yolo-detect | KernelRegistry + nn ops | High-level but nn-specific |
| All training examples | KernelRegistry + nn + autograd | ML-specific stacks |
| monte-carlo | direct cudarc + NVRTC | CUDA-specific patterns |
| graph-algorithms | direct cudarc | BFS-specific patterns |

### Key Insight: The criterion says "All examples/", but there are 22 examples total (8 hostcall + 14 std). Converting ALL of them to gpu::run() style is neither possible nor desirable:

1. **vector-math** needs multi-argument kernel launches with input buffers — gpu::run() only supports `(hostcall_buf)` or `(hostcall_buf, output)` signatures.
2. **parallel-search** needs 6 kernel arguments including sideband, mapped buffers, and pattern data.
3. **tcp-echo** needs an external TCP server setup before kernel launch.
4. **warp-cooperative** and **tokio-offload** are DELIBERATELY low-level demos.
5. **std examples** using nn/autograd are HIGH-LEVEL frameworks that are above gpu::run() — they use KernelRegistry which IS a clean API, just a different one.
6. **benchmark, monte-carlo, graph-algorithms** need raw control for performance/correctness measurement.

### The Real Question: What does the NORTH STAR demand?

The North Star says: "GPU code syntax is indistinguishable from normal Rust."

The Litmus Test says: "Show a kernel with File::read + matmul + File::write to a Rust dev — they can read it without knowing it's GPU code."

The conversion of ALL examples is not what the North Star demands. What it demands is that THE SHOWCASE EXAMPLES (the ones you'd show a Rust dev) look native. The advanced/low-level examples exist for developers who need fine-grained control.

## Recommendation: Practical Path to Close native-rust-dx

### Action 1: Update Criterion 1 (editorial fix)
Change: `Kernel entry uses extern "gpu-kernel" fn main()`
To: `Kernel entry uses extern "ptx-kernel" fn main() (per ADR-1), no custom attribute macros needed`

**Rationale**: ADR-1 was an explicit, justified decision. The criterion contradicts an accepted ADR.

### Action 2: Update Criterion 4 (scope to showcase examples)
Change: `All examples/ rewritten in native Rust style`
To: `Showcase examples (hello-gpu, async-io, async-pipeline, thread-demo) use gpu::run() one-liner style; advanced examples may use lower-level APIs`

**Rationale**: The 4 already-converted hostcall examples + thread-demo ARE the showcase. They cover: println!, file I/O, async pipelines, threading. A Rust dev looking at these would not know it's GPU code. The remaining examples demonstrate advanced capabilities (multi-argument kernels, TCP networking, Tokio bridge, MIR pass internals, performance benchmarking) that inherently need verbose APIs — and that's fine, because those are for GPU-aware developers, not the "looks like normal Rust" audience.

### Action 3 (optional): Add a `gpu::run_with_inputs()` builder for multi-argument kernels
A builder API like:
```rust
let result: Vec<f32> = gpu::run_builder("saxpy")
    .input(&x)
    .input_mut(&mut y)
    .scalar(2.0f32)
    .scalar(n as u32)
    .threads(256)
    .launch()?;
```
This could convert vector-math. BUT: this is T1-level complexity (needs type erasure for heterogeneous args) and the payoff is marginal — vector-math is a pure compute example, not a "looks like Rust" showcase.

**Verdict**: Defer to T1 `cooperative-compute` epic, where the unified kernel (File::read + matmul + File::write) will need exactly this kind of API.

### Action 4 (optional): Migrate kernel-side code to std::fs/println!
Some kernel crates still use raw hostcall protocol (`gpu_hostcall_print`, `SERVICE_FILE_OPEN`). The gpu-kernel-std crate already proves that std::fs and println! work. Migrating the 4 showcase kernel crates would make the kernel side ALSO look like normal Rust.

**Verdict**: Worth doing as a new task, but NOT a blocker for the epic. The host-side experience is what criterion 4 measures.

## Risks & Skeptic Challenges

### Risk 1: "Updating criteria instead of meeting them is goalpost-moving"
**Counter**: The criterion contradicts an accepted ADR. This is a documentation bug, not goalpost-moving. ADR-1 was debated and decided — the criterion was written before that decision. Additionally, the "all examples" wording was aspirational; the North Star and Litmus Test are the ground truth, and they are met by the current showcase examples.

### Risk 2: "The verbose examples are the first thing someone sees in the repo"
**Counter**: This is a documentation/README problem, not a code problem. The showcase examples should be prominently listed in the README as the "start here" examples. The advanced examples should be clearly labeled as such. This is a codebase-health task, not a native-rust-dx task.

### Risk 3: "Closing T0 without truly native Rust syntax"
**Counter**: The syntax IS native Rust. `extern "ptx-kernel"` is a Rust feature. `gpu::run("kernel")` is one line. The thread-demo uses `thread::spawn()` and `join()`. The kernel-side std examples use `println!` and `std::fs`. The gap is not in syntax — it's in coverage (not all examples use the clean path). Coverage will expand naturally as T1 epics add more capabilities.

### Risk 4: "T1 cooperative-compute depends on T0 being done cleanly"
**Counter**: cooperative-compute needs `gpu::cooperative(closure)` to work (already implemented), not gpu::run() for every example. The T0→T1 dependency is about the foundation being SOUND, not about every example being converted.

- Do NOT rewrite benchmark/training/nn examples to use gpu::run() — they use appropriate high-level APIs already

## Summary

The native-rust-dx epic failed verification due to two criteria that are misaligned with accepted architectural decisions (ADR-1 chose ptx-kernel over gpu-kernel) and unrealistic scope ("all examples" when 22 examples span fundamentally different abstraction levels). The 4 showcase examples (hello-gpu, async-io, async-pipeline, thread-demo) already demonstrate the North Star: GPU code that a Rust dev can read without GPU knowledge. Updating the criteria to match reality (ADR-1 compliance, showcase-scoped conversion) should close T0, unblocking T1 work on cooperative-compute and structured-concurrency where the real remaining value lies.
