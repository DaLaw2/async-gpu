## Detailed Gap Analysis

### Gap 1: cooperative() API ergonomics

**What exists**: `thread::cooperative(&|| { ... })` in `thread.rs` (lines 380-426).
- Takes `&F` where `F: Fn()` (not `FnOnce`)
- Returns `()` — no way to return computed results
- Requires `unsafe` block
- Closure CANNOT capture local variables (per-warp memory isolation -> ILLEGAL_ADDRESS)
- Data must be passed via global `AtomicU64`/`AtomicU32` statics

**What's needed**:
- A higher-level wrapper that handles data passing automatically
- Return value support (at minimum, warp 0's result or a reduction)
- Ideally: pass input slice + output slice as arguments, not via global atomics

**Technical approach**: Create a `cooperative_with_data()` variant that takes input/output pointers as explicit arguments, stores them in the SCRATCH buffers alongside the closure, and provides them to each warp. This avoids closure captures entirely — data flows through the runtime, not through the closure.

```rust
// Target API (kernel-side):
thread::cooperative_map(input.as_ptr(), output.as_mut_ptr(), n, |src, dst, wid, n_warps| {
    // Each warp processes its partition
    let mut i = wid;
    while i < n { dst[i] = src[i] * 2.0; i += n_warps; }
});
```

**Feasibility**: HIGH. The existing cooperative() already handles warp wake-up and synchronization. Adding data pointer passing is a straightforward extension of the SCRATCH buffer mechanism. The closure capture limitation is sidestepped entirely because we pass data as function arguments, not captures.

### Gap 2: Seamless mode transition

**What exists**: `north_star_demo` shows the pattern working end-to-end:
1. Sequential: `File::open` + `read_to_end` (warp 0 only)
2. Global atomic setup: `NS_IN_PTR.store(...)`, `NS_OUT_PTR.store(...)`, `NS_LEN.store(...)`
3. Cooperative: `thread::cooperative(&|| { ... loads from atomics ... })`
4. Sequential: `File::create` + `write_all` (warp 0 only)

**The boilerplate problem**: Lines 697-699 in gpu-kernel-std/src/lib.rs — three global atomic stores just to pass data into cooperative(). Lines 704-706 inside the closure — three global atomic loads to receive data. This is 6 lines of ceremony for what should be zero.

**What's needed**: The `cooperative_map` API from Gap 1 eliminates this entirely. The mode transition becomes:

```rust
let data = File::open("input.bin")?.read_to_end()?;
let mut output = vec![0u8; data.len()];
thread::cooperative_map(data.as_ptr(), output.as_mut_ptr(), n, |src, dst, wid, n_warps| { ... });
File::create("output.bin")?.write_all(&output)?;
```

No global statics. No atomic stores/loads. Sequential -> cooperative -> sequential with zero ceremony.

**Feasibility**: HIGH. The key insight is that `cooperative_map` receives raw pointers as function arguments (not closure captures). These pointers are to HEAP memory allocated by warp 0. Heap memory lives in GLOBAL address space on CUDA, so ALL warps can read/write it. This is why the north_star_demo works — `Vec` allocates on the heap, and the pointers stored in atomics point to heap memory. We just need to remove the atomic indirection.

### Gap 3: Kernel-side compute operations (matmul, attention, conv2d)

**This is the critical gap.** Currently:
- Compute kernels (`gemm_f32`, `full_gemm`, etc.) are standalone GPU entry points
- They're launched from the HOST via cudarc (`func.launch(config, args)`)
- The nn layer (`gpu-host/src/nn/ops/gemm.rs`) orchestrates: pad -> transpose -> launch gemm -> extract result
- There is NO way to call matmul from WITHIN a running kernel

**What's needed**: A kernel-side compute library that can be called from cooperative() context.

**Approach options**:

**Option A: Port core GEMM loop into gpu-runtime as library function**
- Extract the inner loop from `gemm_f32_v2` (register-blocked, tiled GEMM)
- Make it a function in `gpu_runtime::compute` that takes (A_ptr, B_ptr, C_ptr, M, K, N)
- Each warp computes its portion via cooperative()
- **Pro**: Clean library API, reusable
- **Con**: Significant engineering — must handle tiling, shared memory, multi-warp coordination within cooperative

**Option B: Single-warp simple GEMM (MVP)**
- Implement a naive triple-loop matmul in gpu-runtime
- In cooperative mode, partition rows across warps
- Good for small matrices (< 256x256), proof of concept
- **Pro**: Fast to implement, proves the concept
- **Con**: Not competitive performance (no tiling, no shared memory)

**Option C: Cooperative kernel-side dispatch**
- From cooperative(), launch a sub-dispatch that assigns warps to tiles
- Essentially re-implement multi-warp GEMM coordination within the cooperative context
- **Pro**: Can achieve high performance
- **Con**: Complex — essentially building a kernel-within-a-kernel scheduler

**Recommendation**: Start with Option B (naive matmul, MVP), then evolve to Option A for real performance. Option B proves the architecture works and satisfies the demo criterion. Option A is needed to satisfy "nn ops callable from within a kernel."

**Why not just call the existing compute kernels?**
- CUDA does not support dynamic parallelism on all architectures (and our target GTX 1660 SM_75 does NOT support it)
- Even with CDP, launching a kernel from a kernel has massive overhead
- The right answer is a library function, not a kernel launch

### Gap 4: Full demo (File::read -> matmul -> File::write)

**Dependencies**: Gaps 1 + 2 + 3 above.

**Existing prototype**: `north_star_demo` does File::read -> elementwise(x2) -> File::write.

**What's needed**: Replace the elementwise(x2) with actual matmul.

**Demo spec**:
1. Read two matrix files (A.bin, B.bin) via std::fs
2. Cooperative matmul: C = A * B using all warps
3. Write result (C.bin) via std::fs
4. Verify on host: compare C with reference computed on CPU

**Host test**: Create input files, launch kernel, read output, verify.

## Risk Assessment

### Risk 1: Pointer passing in cooperative — address space correctness
**Severity**: Medium
**Detail**: Pointers from Vec (heap-allocated by warp 0) should be in global address space. But if the compiler places them in local memory (stack), other warps CANNOT access them. The north_star_demo already proves Vec pointers work, but cooperative_map needs to guarantee this.
**Mitigation**: Test immediately in coop-api.1. If stack pointers leak in, use `core::ptr::write_volatile` or explicit global-memory allocation via gpu-runtime scratch.

### Risk 2: Shared memory availability in cooperative()
**Severity**: Medium
**Detail**: High-performance matmul needs shared memory for tile staging. Currently, cooperative() uses the standard worker_loop which doesn't set up shared memory. Dynamic shared memory (`extern shared`) may or may not be available.
**Mitigation**: coop-compute.1 investigation will determine this. Worst case: register-only matmul (still functional, just slower). GTX 1660 has 48KB shared memory per SM — plenty if we can access it.

### Risk 3: Performance of kernel-side matmul vs host-launched
**Severity**: Low (for MVP)
**Detail**: Kernel-side matmul with 4 warps (128 threads) will be much slower than host-launched with 256 threads/block x N blocks. But the demo criterion is about CORRECTNESS and ERGONOMICS, not performance.
**Mitigation**: Accept slow MVP. Performance optimization is the kernel-perf epic's job. The cooperative-compute epic just needs to prove the architecture.

### Risk 4: Closure size limit (SCRATCH_SIZE = 256 bytes)
**Severity**: Low
**Detail**: cooperative() copies the closure to each warp's SCRATCH buffer (256 bytes). With cooperative_map passing additional pointers, the total size must fit in 256 bytes.
**Mitigation**: A closure carrying 2 pointers + 1 usize + function pointer = ~32 bytes. Well within limits. If needed, increase SCRATCH_SIZE.

## Summary

The cooperative-compute epic has a solid foundation: `thread::cooperative()` works, the `north_star_demo` proves File I/O + parallel compute + File I/O in one kernel. The three gaps are: (1) API ergonomics — eliminate global-atomic boilerplate with `cooperative_map()`, (2) kernel-side compute — port matmul as a library function callable from cooperative context, (3) full demo — replace the trivial `*2.0` with real matmul. The largest technical risk is kernel-side matmul performance, but the demo criterion requires correctness, not speed. Three themes (coop-api, coop-compute, coop-demo) with 9 tasks cover the full path from API design to the North Star demo.
