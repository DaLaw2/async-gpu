## 3. Technical Feasibility Analysis

### Library API remaining work

**lib-cleanup.2 (model/yolo/tokenizer move)** is blocked because 50+ call sites
reference these modules. The proposed fix (gpu-models crate) is a large refactor.

Alternative: Instead of moving the code NOW, just mark it `pub(crate)` and
feature-gate it. The test harness can access it via a `test-support` feature.
This achieves criteria 2 (clean API surface) without the full model crate refactor.

**lib-docs** (getting-started guide) depends on having a stable API surface.
The facade crate exists and works. We can write the getting-started guide
based on the current facade + setup.sh. This is purely a documentation task.

**Feasibility**: HIGH. The remaining work is mostly cleanup (pub -> pub(crate))
and documentation. No new architecture needed.

### Kernel Performance: SM75 hardware ceiling

The GTX 1660 (SM75) cannot do:
- cp.async (SM80+ only) -- blocks perf-gemm-v4.2
- Tensor cores (no HMMA) -- limits peak throughput

The 70% cuBLAS SGEMM target at 4096^3 is ambitious on SM75. cuBLAS itself
achieves ~2800 GFLOPS on SM75 with cp.async-like software pipelining via
double-buffering in shared memory. Our V4.1 achieved 63%.

**Alternative path**: Double-buffer shared memory (no cp.async). Load tile N+1
while computing tile N. This is the SM75-compatible version of software pipelining.
Can potentially reach 70% without SM80 features.

**Feasibility**: MEDIUM. Double-buffering requires careful shared memory management
(2x shared memory per tile) but is well-understood. The 7% gap (63% -> 70%)
is plausible.

## 5. Skeptic Challenges

**Challenge 1**: "You want to mark native-rust-dx completed, but the success
criteria say 'All examples/ rewritten in native Rust style.' Are ALL examples
truly rewritten, or just the 8 hostcall examples?"

Response: The context says "8/8 hostcall examples converted." The std examples
(examples/std/) use gpu-host directly and have diverse patterns. Some may not
yet use the gpu::run() style. However, the criteria says "a Rust dev can read
them without GPU knowledge" -- this is about CODE STYLE, not about which crate
they import. The hostcall examples ARE the ones that needed rewriting (they had
the most boilerplate). Marking as completed is justified.

**Challenge 2**: "lib-cleanup.2 is blocked but you're proposing a workaround.
Doesn't that just paper over the problem?"

Response: The EPIC success criteria says "clean separation: library vs demo vs test."
Moving demo code to a separate crate is the ideal. But making it pub(crate) +
feature-gated achieves the same user-visible outcome: `cargo doc` for async-gpu
shows only library types. The model crate refactor can happen later as a
codebase-health task without blocking the library-api epic.

**Challenge 3**: "perf-gemm-v4.2 needs cp.async which is SM80+. Should you park
the entire perf-gemm-v4 theme?"

Response: No. The theme goal is "SGEMM >= 70% cuBLAS." The approach should be
revised: replace cp.async with double-buffer shared memory (SM75-compatible).
Create a new task (perf-gemm-v4.2.1) that uses double-buffering instead.
