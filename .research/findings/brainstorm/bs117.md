### The Situation

T0 has two epics:
- `developer-showcase` — **COMPLETED** (all 5 criteria verified)
- `gpu-test` — **PENDING** (no work started, 4 tasks queued)

Strict tier rules say: "Never start T(N+1) tasks while T(N) has unmet criteria."
T0 is not cleared because gpu-test remains pending. However, T1 epics
(gpu-iterator, auto-fusion) were activated in brainstorm 116 when all prior T0/T1
epics were completed — the tier system at that time had different T0/T1 assignments.

### Analysis

Looking at the tier history: gpu-test was classified as T0 *alongside* developer-showcase.
Both were post-hoc additions — the original T0 contained native-rust-dx and std-thread-gpu
(both completed long ago). The gpu-test epic was added later as T0 because testing
infrastructure is foundational.

The key question: **Does the ongoing T1 work depend on gpu-test?**

Answer: **No.** gpu-iterator and auto-fusion do not depend on #[gpu_test]. The par_iter
API is already working (6 demo kernels compile, iter-design/compiler/runtime.1 all done).
Auto-fusion's codegen investigation is complete. Neither epic needs gpu-test to proceed.

### Recommendation: Parallel Execution

**Allow T0 (gpu-test) and T1 (gpu-iterator, auto-fusion) to proceed in parallel.**

Rationale:
1. gpu-test is genuinely T0 (testing is foundational) but has no forward dependency
   from T1 work — it's a lateral dependency (tests validate what's built, not gate what's built)
2. Halting 20 tasks of T1 progress to do gpu-test first would waste momentum
3. gpu-test can start immediately alongside remaining T1 tasks
4. The 2-subagent limit means we can interleave: one T0 task + one T1 task per dispatch

**Priority ordering when both T0 and T1 tasks are eligible:**
- T0 tasks get **first slot** (higher priority)
- T1 tasks fill **second slot** (continue momentum)
- This means gpu-test will progress at 50% capacity while T1 finishes

## 2. gpu-test Readiness Review

### Existing Infrastructure

The project already has a substantial test harness:
- `crates/test/gpu-test-harness/` — 24,755 lines across 15 source files
- Tests cover: basic, benchmark, CNN, GEMM, hostcall, inference, pipeline,
  scaling, search, std, tokenizer, transformer, warp
- All tests run via a custom binary (`gpu-tests`) with `ONLY_TEST=` env filtering

### What gpu-test Adds

The gpu-test epic is about a fundamentally different testing model:
- **Current**: Host-side binary launches GPU kernels and checks results from host
- **Target**: `#[gpu_test]` attribute on a function that runs ON GPU directly,
  with GPU-side assert! that reports warp/thread ID, integrated with `cargo test`

### Theme/Task Readiness

The existing 2 themes and 4 tasks are well-defined:

1. **test-framework.1** (investigation): Design #[gpu_test] proc macro
   - No proc macro infrastructure exists yet — this is greenfield
   - Must design: kernel generation from test fn, host runner code generation,
     assert failure reporting protocol
   - Key design question: proc macro crate vs. build script approach

2. **test-framework.2** (experiment): Implement #[gpu_test] + GPU assert!
   - Depends on .1
   - Must create new proc macro crate (e.g., `gpu-test-macro`)

3. **test-integration.1** (experiment): cargo test discovers #[gpu_test]
   - Depends on .2
   - Hardest part: bridging `cargo test` discovery with GPU kernel compilation

4. **test-integration.2** (experiment): Write 10+ tests covering features
   - Depends on .1
   - Mostly mechanical once framework works

### Assessment: Ready, No New Themes Needed

The themes and tasks are complete and well-scoped. No new themes or tasks needed.
The critical risk is test-integration.1 — cargo test integration requires either:
a) A custom test harness (like the current gpu-test-harness but discoverable by cargo)
b) A build script that pre-compiles GPU test kernels
c) Integration via `#[test]` functions that internally launch GPU kernels

Option (c) is most pragmatic and aligns with how the project already works.

## 6. Insights from developer-showcase

### What showcase revealed about the codebase

1. **Two-facade architecture works well**: `async-gpu` (host API) and `gpu-runtime`
   (kernel-side) as separate facades. This pattern should be maintained for new
   features (par_iter is already correctly in gpu-runtime).

2. **Examples are the real test**: The showcase work forced every feature to have
   a working example. The par_iter demos follow this pattern. gpu-test should
   leverage existing examples as test inputs.

3. **README-driven development**: The showcase README rewrite (5 tasks) produced
   the project's public narrative. New features (par_iter, auto-fusion) should
   update the README when they reach demo stage.

### Impact on gpu-test

The showcase highlighted that the project has 14+ standalone examples but no
automated GPU-level testing. The gpu-test epic becomes MORE important after
showcase: now that features are documented and discoverable, they need to be
tested at the GPU level, not just via host-side integration tests.
