## 1. Recommended Split Strategy

### Split into 4 kernel crates

**Crate 1: `gpu-kernel-core`** — Shared helpers + basic primitives

| File | Lines |
|------|------:|
| helpers.rs | 387 |
| basic.rs | 266 |
| compute_math.rs | 54 |
| **Total** | **~707** |

- **Rationale**: helpers.rs is used by almost every other crate. Publishing it as a library crate (not cdylib) that other kernel crates depend on avoids code duplication. basic.rs and compute_math.rs are tiny leaf modules with no complex dependencies.
- **PTX contribution**: Minimal — this crate is primarily a `rlib` dependency. The basic.rs and compute_math.rs entry points would produce <0.5 MB PTX.

**Crate 2: `gpu-kernel-compute`** — ML/HPC compute kernels (stable, rarely changed)

| File | Lines |
|------|------:|
| compute_gemm.rs | 2,609 |
| compute_transformer.rs | 2,288 |
| compute_cnn.rs | 854 |
| compute_search.rs | 1,142 |
| compute_fused.rs | 285 |
| compute_mma.rs (sm_80) | 227 |
| compute_physics.rs | 205 |
| compute_demo.rs | 235 |
| compute_persistent.rs | 183 |
| **Total** | **~8,028** |

- **Rationale**: These are the production ML kernels that the nn module needs. They form a cohesive "pure compute" domain (no hostcall I/O, no std). They are stable (1 commit each in 2 months). The nn::KernelRegistry's ML_KERNELS list maps exactly to these files.
- **Estimated PTX**: ~5-6 MB (the bulk of the current 9.9 MB). This is the largest crate, but it changes the least.
- **Dependencies**: gpu-kernel-core (for helpers), gpu-runtime, gpu-atomics, gpu-protocol.

**Crate 3: `gpu-kernel-io`** — Hostcall, I/O, pipeline, hybrid kernels

| File | Lines |
|------|------:|
| hostcall_kernels.rs | 2,202 |
| pipeline.rs | 1,080 |
| hybrid.rs | 458 |
| **Total** | **~3,740** |

- **Rationale**: These kernels exercise the hostcall/I/O path — they depend heavily on gpu_hostcall_* helpers, grep_buffer, and the hostcall protocol. They form a coherent "I/O + hostcall" domain. pipeline.rs also depends on hybrid.rs.
- **Estimated PTX**: ~2-3 MB.
- **Dependencies**: gpu-kernel-core (for helpers), gpu-runtime, gpu-protocol, gpu-libc.

**Crate 4: `gpu-kernel-test`** — Test/demo kernels (highest churn, fastest rebuild needed)

| File | Lines |
|------|------:|
| lib.rs (std test kernels) | ~1,205 |
| warp.rs | 920 |
| thread_test.rs | 396 |
| sc_demo.rs | 972 |
| par_iter_demo.rs | 517 |
| **Total** | **~4,010** |

- **Rationale**: These are the files that change most frequently. They exercise std features (println!, Vec, File, thread::spawn), warp operations, structured concurrency, and iterator demos. Isolating them means iterating on new features only rebuilds ~2 MB of PTX instead of the full 9.9 MB.
- **Estimated PTX**: ~2-3 MB.
- **Note**: lib.rs's shared infrastructure (stdio_auto_init, gpu_stdout_write, etc.) needs to move to gpu-kernel-core or gpu-runtime so all crates can use it.
- **Dependencies**: gpu-kernel-core, gpu-runtime, gpu-libc, gpu-protocol.

### Shared Infrastructure Problem

The current lib.rs contains both kernel entry points AND shared infrastructure:
- `STDIO_HOSTCALL_BUF`, `STDIO_SIDEBAND_PTR`, `STDIO_PRINT_BUF_READY` statics
- `gpu_stdout_write()`, `gpu_stdin_read()`, `stdio_init()`, `stdio_auto_init()`
- `stdio_print_buffer_init()`, `gpu_print_buffer_flush()`

These are `#[no_mangle]` extern functions called by patched-std's CUDA PAL. They must be present in every kernel crate that uses std I/O. Options:
1. **Move to gpu-runtime** (preferred): These functions logically belong in the runtime. The `gpu_stdout_write`/`gpu_stdin_read` externals are called by std's PAL, so they must be linked into every cdylib. Moving them to gpu-runtime means any kernel crate that depends on gpu-runtime gets them automatically.
2. **Duplicate in each crate**: Simpler but creates maintenance burden.

**Recommendation**: Move stdio infrastructure to gpu-runtime as a `stdio` module. This is a one-time refactor that pays dividends for every future kernel crate.

## 2. Host Loader Changes

### Current state
- `ptx::KERNEL` = `include_str!("../kernel.ptx")` — single 9.9 MB PTX
- `ptx::KERNEL_STD` = same file (alias)
- `gpu.rs::get_kernel()` loads the single PTX via cudarc
- `nn::KernelRegistry` loads the single PTX and extracts ~60 kernel functions
- `gpu::GpuStdModule` takes a PTX string + cubin bytes

### Proposed: Multi-cubin loader with transparent discovery

**Step 1: Multiple PTX/cubin constants**

```rust
pub mod ptx {
    pub const KERNEL_CORE: &str = include_str!("../kernel_core.ptx");
    pub const KERNEL_COMPUTE: &str = include_str!("../kernel_compute.ptx");
    pub const KERNEL_IO: &str = include_str!("../kernel_io.ptx");
    pub const KERNEL_TEST: &str = include_str!("../kernel_test.ptx");

    /// Backward-compat alias: returns the compute PTX (where nn kernels live).
    pub const KERNEL: &str = KERNEL_COMPUTE;
    pub const KERNEL_STD: &str = KERNEL_TEST;

    /// All kernel PTX sources for exhaustive loading.
    pub const ALL: &[(&str, &str)] = &[
        ("core", KERNEL_CORE),
        ("compute", KERNEL_COMPUTE),
        ("io", KERNEL_IO),
        ("test", KERNEL_TEST),
    ];
}
```

**Step 2: KernelRegistry multi-module loading**

The nn::KernelRegistry currently loads all ML kernels from a single PTX. After the split, it only needs `KERNEL_COMPUTE` (plus `KERNEL_CORE` for basic ops). Change:

```rust
impl KernelRegistry {
    pub fn new(device: Arc<CudaDevice>, ptx_src: &str) -> Result<Self> {
        // Load primary (compute) module
        device.load_ptx(Ptx::from_src(ptx_src), "nn_kernels", ML_KERNELS)?;
        Ok(Self { device })
    }
}
```

This is already backward compatible — callers pass `ptx::KERNEL` which will now be `KERNEL_COMPUTE`. The nn module only uses compute kernels.

**Step 3: gpu.rs multi-module fallback**

For `gpu::run()` and `gpu::custom()`, the kernel name might live in any crate. Two approaches:

A. **Explicit PTX selection** (preferred for performance):
```rust
gpu::custom("my_kernel")
    .ptx(ptx::KERNEL_TEST)  // caller knows which crate
    .prepare()
```

B. **Auto-discovery fallback** (for convenience):
```rust
fn get_kernel(dev, kernel_name) -> Result<CudaFunction> {
    for (module_name, ptx_src) in ptx::ALL {
        // Try loading from each module
        if let Ok(func) = try_load_kernel(dev, ptx_src, module_name, kernel_name) {
            return Ok(func);
        }
    }
    Err(KernelNotFound(kernel_name))
}
```

**Recommendation**: Use explicit PTX selection (A) as the primary API, with auto-discovery (B) only for the `gpu::run()` convenience API. This avoids loading unnecessary PTX modules.

**Step 4: Cubin constants**

Each crate gets its own cubin file. The existing cubin infrastructure (`cubin_file()`, `GpuStdModule::load_with_cubin`) already supports this — just point to different files:

```
crates/core/gpu-host/kernel_core.cubin
crates/core/gpu-host/kernel_compute.cubin
crates/core/gpu-host/kernel_io.cubin
crates/core/gpu-host/kernel_test.cubin
```

### Backward Compatibility

- `ptx::KERNEL` still works (aliased to `KERNEL_COMPUTE`)
- `ptx::KERNEL_STD` still works (aliased to `KERNEL_TEST`)
- `gpu::run()` still works (auto-discovers across modules)
- `KernelRegistry::new(dev, ptx::KERNEL)` still works (loads compute)
- `gpu-test-macro` uses `KERNEL_STD` → now `KERNEL_TEST` (alias)

## 3. Build System Changes

### Current: scripts/build-kernel-std.sh
1. Build single crate → single PTX
2. Copy to gpu-host/
3. ptxas → single cubin (~30 min at opt-level 3)

### Proposed: scripts/build-kernels.sh

**Per-crate build + parallel ptxas**:

```bash
CRATES=(gpu-kernel-core gpu-kernel-compute gpu-kernel-io gpu-kernel-test)

# Step 1: Build all kernel crates (sequential — shared deps)
for crate in "${CRATES[@]}"; do
    cargo "+$CHANNEL" build --release -p "$crate"
done

# Step 2: Copy PTX files
for crate in "${CRATES[@]}"; do
    name="${crate/gpu-kernel-/kernel_}"  # kernel_core, kernel_compute, etc.
    cp "target/nvptx64-nvidia-cuda/release/${crate//-/_}.ptx" "$HOST_DIR/${name}.ptx"
done

# Step 3: Parallel ptxas (each crate independently)
for crate in "${CRATES[@]}"; do
    name="${crate/gpu-kernel-/kernel_}"
    ptxas --gpu-name sm_75 -o "$HOST_DIR/${name}.cubin" "$HOST_DIR/${name}.ptx" &
done
wait
```

**Key improvements**:
- Parallel cubin compilation: 4 smaller ptxas runs in parallel instead of 1 giant run
- Each cubin should take ~5-8 min instead of 30 min (PTX is 1/4 the size)
- Wall-clock time: max(individual ptxas times) ≈ 8 min total (parallelized)

### opt-level Strategy

**Dev builds (default)**:
```toml
[profile.release]
panic = "abort"
opt-level = 1
lto = false
```

**Release builds** (explicit `--profile release-gpu`):
```toml
[profile.release-gpu]
inherits = "release"
panic = "abort"
opt-level = 3
lto = "fat"
```

Expected impact:
- opt-level 1 + no LTO: PTX size drops ~30-50%, ptxas time drops ~60%
- Combined with crate split: single-crate rebuild at opt-level 1 should be ~2-3 min total

### Incremental Rebuild

When only `gpu-kernel-test` changes:
1. cargo build: only recompiles `gpu-kernel-test` (~30s)
2. ptxas: only recompiles `kernel_test.cubin` (~3-5 min at opt-level 1)
3. Total: well within the 5-minute litmus test target

## 5. Risks and Mitigations

### Risk 1: Duplicate symbols across cdylib crates
**Problem**: If helpers.rs functions are compiled into multiple cdylib PTX files, ptxas may complain about duplicate symbols when loading multiple modules.
**Mitigation**: Each cubin is loaded as a separate CUmodule — CUDA modules are isolated. Duplicate function names in different modules are fine because `cuModuleGetFunction` scopes by module. Only `#[no_mangle]` device globals (`__HOSTCALL_BUF`) need care — each module gets its own copy, and the host injects the pointer per-module.

### Risk 2: stdio `#[no_mangle]` externals in multiple crates
**Problem**: `gpu_stdout_write` and `gpu_stdin_read` are `#[no_mangle]` functions called by patched-std PAL. If they live in gpu-runtime (rlib), they get compiled into every cdylib — but that is exactly what we want (each module is self-contained).
**Mitigation**: This is actually the desired behavior. Each cdylib gets its own copy of the stdio functions, which read module-local statics. No conflict.

### Risk 3: Feature flag propagation (sm_80)
**Problem**: compute_mma.rs uses `#[cfg(feature = "sm_80")]`. After the split, this feature must be on gpu-kernel-compute's Cargo.toml.
**Mitigation**: Propagate the sm_80 feature to the compute crate. The feature controls a single module inclusion — straightforward.

### Risk 4: Build time may not improve enough
**Problem**: ptxas time scales with PTX size but not linearly. 4 crates at ~2.5 MB each might not be 4x faster than 1 crate at 10 MB.
**Mitigation**: Parallel ptxas is the key win — 4 parallel jobs, each taking ~8 min, finishes in ~8 min instead of 30 min. Combined with opt-level 1 (which typically halves ptxas time), we expect ~4 min for the largest crate. Incremental (single crate) should be ~2-3 min.

### Risk 5: Cross-crate kernel calls
**Problem**: pipeline.rs calls functions from hybrid.rs. After the split, both are in gpu-kernel-io, so this is fine. But if any kernel in one crate calls a function defined in another crate, that breaks.
**Mitigation**: The dependency audit (Task 1.1) explicitly checks for cross-boundary calls. The proposed split keeps all cross-referencing files in the same crate (pipeline + hybrid together in gpu-kernel-io). No cross-crate kernel function calls exist in the proposed split.

### Risk 6: lib.rs monolith
**Problem**: lib.rs has 1,205 lines with both infrastructure (stdio_init, etc.) and test kernels. Splitting it requires careful separation.
**Mitigation**: Task 2.1 extracts infrastructure first (to gpu-runtime), then Task 2.5 keeps the remaining test kernels in gpu-kernel-test. Two clean steps.
