# BS12 Synthesis — Post-Completion Strategic Direction
**Date**: 2026-03-12
**Brainstorm seq**: 12
**Level**: deep (proposer + skeptic)
**Trigger**: All 12 active themes completed (47/47 tasks). Deciding next phase.

---

## Consensus Points

Both proposer and skeptic agree on these key conclusions:

### 1. Benchmarking is the top priority
Cannot make any optimization or architecture decisions without real data. Hardware
register counts (not PTX virtual), occupancy, hostcall latency with percentiles,
and CAS retry rates are all unknown. **Unpark benchmark theme immediately.**

### 2. The host listener is broken at scale
38% duplicate messages at 512 threads, 100% CPU busy-loop. This needs fixing
regardless of direction. Per-packet processed bit + adaptive polling.

### 3. AMD port is premature
Both agree: don't port to AMDGPU until the NVIDIA stack is stable, well-measured,
and well-documented. Park this direction explicitly.

### 4. CI is essential
Zero regression tests, unstable nightly dependency, tier-3 target. One nightly
update could break everything silently. Need GitHub Actions + toolchain pinning.

### 5. Static array sizing for executors must be addressed
Current compile-time fixed arrays don't scale. The slab allocator exists — use it
for dynamic executor allocation.

---

## Disputed Points

### D1: Is the reproduction complete?
- **Proposer**: Yes, VectorWare parity achieved.
- **Skeptic**: 85-90% at best. No verification of VectorWare's thread scheduling model,
  allocator sophistication, or deeper std integration. The OnceLock bypass is a cfg-gate
  hack, not a real port.
- **Resolution**: Call it "functionally complete" — the same demonstrations work. The
  remaining 10% may require VectorWare's rustc fork, which is unavailable. Document this
  gap explicitly rather than claiming full parity.

### D2: Is benchmarking meaningful yet?
- **Proposer**: Yes, it's P0 — everything depends on it.
- **Skeptic**: Architecture might change based on benchmark results (circular dependency).
  Hardware register counts could invalidate all conclusions.
- **Resolution**: **Proposer wins.** The circular dependency is broken by measuring FIRST,
  then deciding. Even if the architecture changes, baseline measurements remain valuable
  for comparison. Do benchmark.1 (methodology) + benchmark.2 (microbenchmarks) immediately.
  Defer benchmark.3 (Nsight Compute) and benchmark.4 (comparison) to Phase 2.

### D3: Per-thread executors — wrong granularity?
- **Proposer**: Fine for I/O-focused kernels; shared executor for mixed compute+I/O.
- **Skeptic**: Fundamentally wrong for GPU. Warp divergence during heterogeneous polling
  reduces throughput to 1/32. Warp-cooperative executor is the correct design.
- **Resolution**: **Deferred pending benchmarks.** The skeptic's concern is valid but
  theoretical. Measure actual warp divergence and occupancy first. If the numbers show
  the per-thread model is viable for the target workloads (I/O-heavy), keep it. If not,
  redesign. Don't prematurely optimize.

### D4: Performance or ergonomics?
- **Proposer**: Both, in phases.
- **Skeptic**: Pick one — they're opposite directions.
- **Resolution**: **Ergonomics first, performance second.** The project's value proposition
  is "write Rust instead of CUDA C++." Without a usable API, performance optimizations
  benefit no one. However, benchmarks (not ergonomics improvements) come FIRST because
  they inform both directions. Order: benchmark → api → warp-coop.

### D5: What is the exit criterion?
- **Skeptic**: "Make it better" is not a goal. Define "done" for the next phase.
- **Resolution**: Define Phase 2 completion as:
  1. Performance characterized with Nsight Compute data
  2. Host listener has 0% duplicates and <5% CPU idle usage
  3. At least one example that a new user can follow without reading internals
  4. CI pipeline catches nightly breakage automatically

1. Hostcall latency measured with p50/p95/p99 (1000+ samples)
2. Hardware register count measured via `cuobjdump`
3. Host listener: 0 duplicates, <5% CPU at idle
4. GitHub Actions CI compiles all PTX on every push
5. `rust-toolchain.toml` pins working nightly
6. One end-to-end example with documented build steps
7. README updated with performance data

## Skeptic Concerns Acknowledged But Deferred

1. **"Is there any workload where this is faster?"** — Valid question. Answer after
   benchmark.4 (comparative). The value may be purely ergonomic, and that's OK.
2. **Warp divergence in heterogeneous async** — Measure first (benchmark.3).
3. **Multiple kernels/streams** — Out of scope for Phase 2.
4. **Slab allocator at 8192 threads** — Out of scope until scaling is a priority.
5. **CUDA library interaction (cuBLAS)** — Out of scope; we're not competing with
   compute libraries.

---

## Key Insight

The project has completed its research mission (VectorWare reproduction). Phase 2
transforms the research artifact into a measurable, stable, and usable system.
The critical path is: **measure → stabilize → package**. Performance optimization
(warp-coop) is explicitly deferred until measurements justify it.
