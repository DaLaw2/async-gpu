**Key gap**: There is NO scheduler abstraction. Currently, the user explicitly chooses
between `gpu::run()` (GPU kernel) and normal Rust (CPU). Data transfer is manual via
`MappedBuffer::new_zeroed()` + `buf.write()` / `buf.read()`. The unified runtime must
bridge this gap: the user writes one `async fn`, the runtime decides where to run each
part and moves data automatically.

### Theme Design: 3 Themes

#### Theme 1: `unified-scheduler` — Scheduler type system

**Goal**: Route work to CPU or GPU based on explicit affinity or automatic heuristics.

The scheduler is the brain of unified-runtime. It must:
1. Expose `CpuScheduler`, `GpuScheduler`, `AutoScheduler` types
2. Let users annotate work affinity (`on_gpu(|| ...)`, `on_cpu(|| ...)`)
3. AutoScheduler makes the decision automatically for unmarked work
4. Build on existing infrastructure: `gpu::run()` for GPU, tokio/std for CPU

**Success criteria**:
- CpuScheduler routes work to tokio/std async runtime
- GpuScheduler routes work to `gpu::run()` / `gpu::launch()` kernel dispatch
- AutoScheduler uses work type heuristics (I/O → CPU, bulk compute → GPU)

#### Theme 2: `unified-transfer` — Automatic data transfer

**Goal**: Data moves between host and device transparently — no manual cudaMemcpy.

This is the hardest technical challenge. Currently:
- Host data: normal Rust allocations (`Vec<f32>`, `Box<[T]>`)
- Device data: `MappedBuffer<T>` (pinned, CUDA-accessible)
- User must explicitly create `MappedBuffer`, write data, pass dev_ptr to kernel, read back

The unified runtime must:
1. Detect when data crosses the CPU ↔ GPU boundary
2. Automatically allocate device memory and copy data
3. Track data location to avoid redundant copies (lazy transfer)
4. Use MappedBuffer under the hood but hide it from the user

**Success criteria**:
- `Vec<f32>` on host automatically available to GPU kernel code
- Results from GPU kernel automatically readable on host
- No explicit MappedBuffer/cudaMemcpy in user code

#### Theme 3: `unified-demo` — End-to-end pipeline demo

**Goal**: Demonstrate the full North Star: read → compute → write with zero GPU concepts.

The capstone demo that proves unified-runtime works. The user writes:
```rust
async fn main() {
    let data = File::read("input.bin").await;  // CPU: file I/O
    let result = data.par_iter()               // GPU: parallel compute
        .map(|x| x * 2.0 + 1.0)
        .collect();
    File::write("output.bin", &result).await;  // CPU: file I/O
}
```
No `gpu::run()`, no `MappedBuffer`, no `cudaMemcpy`, no block/grid config.

**Success criteria**:
- Demo: read → compute → write pipeline, zero explicit memory management
- Performance within 2x of hand-optimized MappedBuffer + gpu::launch path
- User code contains zero GPU-specific types or calls

### Task Breakdown

#### Theme: unified-scheduler (3 tasks)

**unified-scheduler.1** — Investigation: scheduler architecture design
- Survey existing infrastructure: gpu::run, gpu::launch, executor, hostcall
- Design CpuScheduler/GpuScheduler/AutoScheduler trait hierarchy
- Define work affinity detection heuristics for AutoScheduler
- Output: design document with API sketches and decision matrix
- Dependencies: none
- Estimated effort: 1 cycle

**unified-scheduler.2** — Experiment: implement CpuScheduler + GpuScheduler
- Implement concrete scheduler types that route work to CPU or GPU
- CpuScheduler wraps tokio/std async, GpuScheduler wraps gpu::run
- Define the `Schedulable` trait (or similar) for work items
- Verify: explicit affinity routing works (on_cpu/on_gpu markers)
- Dependencies: unified-scheduler.1
- Estimated effort: 1-2 cycles

**unified-scheduler.3** — Experiment: implement AutoScheduler with heuristics
- AutoScheduler picks CPU vs GPU based on work characteristics
- Heuristics: I/O-bound → CPU, data-parallel > threshold → GPU, small data → CPU
- Fallback: if heuristic is uncertain, default to CPU (safe choice)
- Benchmark: AutoScheduler vs manual affinity — should be within 10%
- Dependencies: unified-scheduler.2
- Estimated effort: 1-2 cycles

#### Theme: unified-transfer (3 tasks)

**unified-transfer.1** — Investigation: automatic data transfer architecture
- Survey: how data currently moves (MappedBuffer, dev_ptr, read/write)
- Design: `GpuBuffer<T>` wrapper that tracks data location (host/device/both)
- Define transfer policy: eager vs lazy, zero-copy opportunities
- Consider: pinned memory (MappedBuffer) vs device-only memory vs unified memory
- Dependencies: none
- Estimated effort: 1 cycle

**unified-transfer.2** — Experiment: implement transparent host ↔ device transfer
- Implement GpuBuffer<T> (or similar) with automatic location tracking
- From<Vec<T>> for GpuBuffer<T> — host data becomes GPU-accessible
- Into<Vec<T>> for GpuBuffer<T> — GPU results readable on host
- Under the hood: MappedBuffer for pinned path, cuMemcpy for device-only
- Dependencies: unified-transfer.1
- Estimated effort: 1-2 cycles

**unified-transfer.3** — Experiment: lazy transfer + redundancy elimination
- Track data freshness: if GPU hasn't modified data, skip device→host copy
- If data is already on device, skip host→device copy
- Benchmark: overhead of tracking vs manual MappedBuffer (target: < 5% overhead)
- Dependencies: unified-transfer.2
- Estimated effort: 1 cycle

#### Theme: unified-demo (2 tasks)

**unified-demo.1** — Experiment: read → compute → write pipeline demo
- Combine scheduler + transfer: full pipeline with zero GPU concepts in user code
- File::read on CPU, par_iter on GPU, File::write on CPU — automatic transitions
- Verify correctness: output matches hand-optimized version bit-for-bit
- Dependencies: unified-scheduler.2, unified-transfer.2
- Estimated effort: 1-2 cycles

**unified-demo.2** — Experiment: performance comparison + AutoScheduler demo
- Benchmark unified pipeline vs hand-optimized MappedBuffer + gpu::launch
- Target: within 2x of hand-optimized (transfer overhead is the cost)
- Demonstrate AutoScheduler choosing GPU for large par_iter, CPU for I/O
- Dependencies: unified-scheduler.3, unified-demo.1
- Estimated effort: 1 cycle

## Key Insight

unified-runtime is not a new capability — it is the COMPOSITION of everything built in T0 and T1. The scheduler wraps gpu::run/launch, the transfer layer wraps MappedBuffer, and the demo proves that the user never touches either. Two parallel investigations (scheduler design + transfer architecture) are the ideal first dispatch because they inform each other without blocking.
