#### 2. compile-time-cost (Weighted Score: 3.60)

| Dimension | Score | Rationale |

#### 3. gpu-hot-reload (Weighted Score: 3.30)

| Dimension | Score | Rationale |
|-----------|-------|-----------|
| North Star Fit | 2 | Good DX but orthogonal to North Star. Hot-reload is about iteration speed, not the programming model |
| Technical Readiness | 4 | 3 tasks, 1 theme, well-defined. NVRTC path is known. File watcher is straightforward |
| sm_75 Feasibility | 5 | No SM90+ requirements |
| User Impact | 3 | Edit kernel, see results in <2s. Great for prototyping. But requires NVRTC (runtime compilation), which is a different compilation path from our patched rustc+PTX pipeline |

**Concern**: Hot-reload via NVRTC means recompiling CUDA C/C++ (not Rust) at runtime.
Our kernels are written in Rust, compiled to PTX via patched rustc. NVRTC doesn't compile
Rust. This epic would need to either:
(a) Hot-reload PTX directly (recompile Rust -> PTX, then swap), which means re-running
    the Rust compiler, which takes >> 2 seconds
(b) Support a "CUDA C" path alongside Rust for hot-reloadable kernels (contradicts the
    "pure Rust" vision)

**This epic may need task redesign.** The current tasks assume NVRTC, which is CUDA C-specific.
For a Rust-native hot-reload, the approach would be: file watcher -> cargo build
(incremental, PTX JIT mode) -> swap CUmodule. This is feasible but the "< 2 seconds"
target is ambitious.

## 4. Recommendation

### Activate: gpu-coroutines

**Rationale**: This is the natural second T2 epic, as recommended in bs123. It extends the
core async/await model to generator/yield patterns, which is technically adjacent to
the existing MIR pass work and directly serves the "plain Rust on GPU" vision.

The 4 existing tasks are well-scoped:
1. coro-design.1: Investigation — map Rust generator/coroutine semantics to GPU warp state machines
2. coro-design.2: Design — GpuGenerator trait + MIR pass extension for yield
3. coro-impl.1: Experiment — implement generator compilation to PTX
4. coro-impl.2: Experiment — streaming pipeline demo

**No new tasks needed.** The existing task definitions are correct and complete.

### Staggered Activation: compile-time-cost

**When**: After coro-design.1 investigation completes (estimated cycle 636-637).

**First task**: cost-analysis.1 (Investigation: estimate register + shared memory from MIR/PTX)

This investigation can run in parallel with coro-design.2 or coro-impl.1 without conflict.
The two epics share MIR pass infrastructure but work on different aspects:
- gpu-coroutines: generator state machine transformation
- compile-time-cost: static analysis of resource usage

### Do NOT Activate Yet

| Epic | Why Not | When |
|------|---------|------|
| gpu-hot-reload | Needs task redesign (NVRTC assumption conflicts with Rust-native pipeline) | After hot-reload feasibility investigation |

Key questions for coro-design.1:
- How does Rust's unstable Generator trait (Pin<&mut Self> -> GeneratorState<Yield, Return>) map to warp-cooperative execution?

## 7. Key Insight

gpu-coroutines is the RIGHT next epic because it deepens the core abstraction that makes
async-gpu unique. While unified-runtime proved that I/O + compute can be transparent,
gpu-coroutines extends this to STREAMING patterns — producers yield values to consumers
without buffering, using the same warp-cooperative execution model. This is the kind of
capability that raw CUDA cannot match: cooperative coroutines across GPU warps where
yield is a warp-synchronized operation, not a thread-level one. Combined with
compile-time-cost as a staggered companion, this phase advances both the programming
model (coroutines) and the developer experience (compile-time GPU perf warnings) — the
two facets that make async-gpu more than just another GPU library.
