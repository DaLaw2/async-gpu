## 2. Story Analysis

### gpu-panic — Deep Analysis

**Current state:**
The infrastructure is surprisingly mature. Here's what already exists:

1. **ADR-5 / SERVICE_PANIC (opcode 10)**: Fully implemented hostcall path. GPU thread formats a panic message into a 56-byte PanicBuf, packs threadIdx/blockIdx/msgLen into metadata, sends via Treiber-stack hostcall, host prints `[GPU PANIC] block=N thread=M: message`.

2. **`gpu_runtime::panic_handler!()` macro**: Installs a `#[panic_handler]` for no_std kernel crates. Formats PanicInfo, writes to result buffer, sends hostcall, marks warp trapped, executes `trap;`.

3. **Patched std panic pathway**: The patched std has a full `panic_handler` in `panicking.rs` (line 611) that goes through the standard `default_hook` → `panic_with_hook` → `rust_panic` flow. On GPU, stderr routes through `gpu_stdout_write` (CUDA PAL in `sys/stdio/cuda.rs`), which goes through hostcall.

4. **`gpu_assert!` macro**: Custom macro in gpu-runtime requiring a hostcall buffer parameter — NOT the standard `assert!` macro. Uses SERVICE_ASSERT (separate opcode).

**The gap — what's missing for the story's success criteria:**

| Criterion | Current State | Gap |
|-----------|--------------|-----|
| `panic!()` prints message + location + warp/thread ID | Works via `panic_handler!()` for no_std crates. For std crates, the patched std's panic_handler goes through default_hook which uses `thread::with_current_name` and `thread::current_os_id` — **but on GPU, "thread" is a CUDA thread, not an OS thread.** The output says `thread '<unnamed>' (tid)` not `warp W thread T`. | **Medium gap**: Need to intercept the patched std's panic output to include warp/thread info instead of OS thread info. |
| `unwrap()/expect()` triggers standard panic | These call `panic!()` internally. If `panic!()` works, they work. In no_std crates with `panic_handler!()`, this works. In std crates, it goes through patched std panic handler → stderr → hostcall. | **Small gap**: Verify it actually works end-to-end. May just need a test. |
| `assert!/assert_eq!` without `gpu_assert!` | Standard `assert!` calls `panic!()`. In no_std with `panic_handler!()`, this works. In std crates, this goes through the patched std. The `gpu_assert!` macro is a **separate** thing requiring a buf parameter. | **Key insight**: `assert!()` may already work for std crates. The story asks to make `gpu_assert!` unnecessary — users should use standard `assert!`. |
| Panic output indistinguishable from CPU | CPU: `thread 'main' panicked at src/main.rs:5:5: message`. GPU currently: `[GPU PANIC] block=0 thread=0: panicked at src/...`. The format differs. | **Medium gap**: Need to format GPU panic output to match CPU format, adding warp info to thread identification. |

**Key architectural insight**: There are TWO panic paths:
1. **no_std kernel path**: `panic_handler!()` → format into PanicBuf → SERVICE_PANIC hostcall → host prints. This is the gpu-runtime's own handler.
2. **std kernel path (patched std)**: Standard `panic_handler` → `default_hook` → `panic_output()` (Stderr) → `gpu_stdout_write` extern → hostcall stdout. This uses the full std panic machinery.

The gpu-panic story needs to **unify** these paths so the output format is identical to CPU panic, regardless of which path is taken. The warp/thread ID should be injected into the thread identification.

### feature-audit — Deep Analysis

**Scope**: 56 completed stories, 24 examples (14 std/ + 10 hostcall/), 9 test crates.

**Risk areas** (based on codebase knowledge):

## 3. Concrete Recommendations

### gpu-panic Features and Tasks

#### Feature: `panic-std-intercept`
- **Story**: gpu-panic
- **Title**: Intercept std panic handler for GPU-native output
- **Goal**: Make the patched std's panic handler output include warp/thread IDs and match CPU format
- **Success criteria**:
  - Patched std's `default_hook` on GPU outputs `thread 'main' (warp W, lane L, block B) panicked at <location>:\n<message>` format
  - `panic!("msg")` in a std-enabled kernel produces output indistinguishable from CPU (plus warp info)
  - No separate `panic_handler!()` macro needed when using patched std

**Tasks:**

- **`panic-std-intercept.1`** — Investigation: trace full panic path through patched std on GPU
  - Kind: investigation
  - Depends: []
  - Goal: Map exactly what happens when `panic!()` fires in a std kernel on GPU. Does `default_hook` → `panic_output()` → Stderr → `gpu_stdout_write` actually work end-to-end? What does the output look like? Does `thread::with_current_name` / `thread::current_os_id` produce meaningful values on GPU?

- **`panic-std-intercept.2`** — Experiment: modify patched std default_hook to include GPU warp/thread metadata
  - Kind: experiment
  - Depends: [panic-std-intercept.1]
  - Goal: Modify the `default_hook` in `patched-std/src/panicking.rs` so that on nvptx64, the panic output includes warp ID (threadIdx / 32), lane ID (threadIdx % 32), and blockIdx. Format: `thread 'main' (warp 0, lane 3, block 0) panicked at src/main.rs:5:5:\nmessage`. This likely requires cfg-gating the thread name/ID section for `target_arch = "nvptx64"`.

#### Feature: `panic-unwrap-verify`
- **Story**: gpu-panic
- **Title**: Verify unwrap/expect/assert! work through standard panic path
- **Goal**: Confirm that Option::unwrap(), Result::unwrap(), expect(), assert!, assert_eq! all produce proper panic output on GPU
- **Success criteria**:
  - `None.unwrap()` on GPU prints panic with location and "called `Option::unwrap()` on a `None` value"
  - `Err(e).unwrap()` prints the error value
  - `assert!(false)` and `assert_eq!(1, 2)` produce standard assertion failure messages
  - All tested in both no_std (panic_handler!) and std (patched std) configurations

**Tasks:**

- **`panic-unwrap-verify.1`** — Experiment: test unwrap/expect/assert in no_std kernel with panic_handler!()
  - Kind: experiment
  - Depends: []
  - Goal: Create test kernels that exercise `None.unwrap()`, `Err("bad").unwrap()`, `Some(42).expect("should exist")`, `assert!(false)`, `assert_eq!(1, 2, "values differ")`. Verify the host receives proper panic messages with location info. This can run in parallel with panic-std-intercept.1.

- **`panic-unwrap-verify.2`** — Experiment: test unwrap/expect/assert in std kernel with patched std
  - Kind: experiment
  - Depends: [panic-std-intercept.1]
  - Goal: Same test cases as .1, but in a std-enabled kernel. Verify output format matches CPU panic format (with warp info added). Depends on understanding the std panic path from the investigation.

#### Feature: `panic-deprecate-gpu-assert`
- **Story**: gpu-panic
- **Title**: Deprecate gpu_assert! in favor of standard assert!
- **Goal**: Standard assert!/assert_eq! fully replace gpu_assert!, gpu_assert! is deprecated
- **Success criteria**:
  - `assert!` and `assert_eq!` produce identical output to CPU (with warp info)
  - `gpu_assert!` macro marked `#[deprecated]` with migration note
  - No remaining internal use of `gpu_assert!` in test/example code

**Tasks:**

- **`panic-deprecate-gpu-assert.1`** — Design: migration plan from gpu_assert! to standard assert!
  - Kind: design
  - Depends: [panic-unwrap-verify.1, panic-unwrap-verify.2]
  - Goal: After verifying that standard assert! works properly on GPU, plan the deprecation of gpu_assert!. Inventory all uses of gpu_assert! across the codebase, determine if any rely on features that standard assert! lacks (e.g., the buf parameter for hostcall routing). Design the deprecation path.

- **`panic-deprecate-gpu-assert.2`** — Experiment: deprecate gpu_assert! and migrate all callers
  - Kind: experiment
  - Depends: [panic-deprecate-gpu-assert.1]
  - Goal: Mark `gpu_assert!` as `#[deprecated]`, migrate all internal callers to `assert!`/`assert_eq!`, update documentation. The `gpu_assert!` macro requires a `buf` parameter — standard `assert!` doesn't. This works because the panic handler (either `panic_handler!()` or patched std) already has the buf pointer via `PANIC_BUF` static. So `assert!()` → `panic!()` → panic handler → hostcall is the correct flow.

## 5. Risks and Open Questions

### Risks

1. **Patched std panic handler complexity**: Modifying the `default_hook` in patched std to include GPU metadata requires careful cfg-gating. The `thread::with_current_name` and `thread::current_os_id` calls in `default_hook` may not compile on nvptx64, or may produce meaningless values. Investigation task .1 will resolve this.

2. **Two panic paths divergence**: The `panic_handler!()` macro (no_std) and the patched std panic handler (std) are completely independent code paths. Unifying them so output format matches requires coordinating changes across gpu-runtime and patched-std. The feature structure handles this by verifying both paths separately.

3. **Feature audit scope creep**: 56 stories × N features each = potentially hundreds of things to check. The audit-build feature constrains this to compilation+runtime correctness, not feature-level regression testing. The audit-api feature covers API surface only. This keeps scope manageable.

4. **Thread-local storage on GPU**: The patched std's `panic_count` uses `thread_local!` — this may not work on nvptx64 (no TLS support). If `panic_count` is broken, the panic handler may double-panic or abort unexpectedly. Investigation will reveal this.

### Open Questions

1. **Does the patched std panic handler actually work on GPU today?** The `panic_handler!()` macro in gpu-runtime exists precisely because the std panic handler might not work on nvptx64. If it does work, the story is simpler (just adjust the output format). If it doesn't, we need to make it work first.

2. **Should gpu_assert! be removed or just deprecated?** Some users may prefer the explicit buf-parameter version. Deprecation with `#[deprecated]` is safer — allows migration without breaking existing code.

3. **What's the right thread identification format on GPU?** CPU says `thread 'main' (12345)`. Options for GPU:
   - `thread 'kernel' (warp 0, lane 3, block 0)`
   - `thread 'gpu' (block=0, thread=3, warp=0:lane=3)`
   - `gpu thread block=0 warp=0 lane=3`
   The format should be decided during the investigation.
