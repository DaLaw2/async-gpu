## Q2: Should the abort-path gap become a new task?

The gap: std panic path calls `process::abort()` → `trap;` without calling
`set_warp_trapped()` or `write_panic_to_result()`. This means BlockScope::join_all()
spins forever on std-compiled warp panics, and the host gets no structured error.

**Recommendation**: Yes, but as a NEW feature under gpu-panic, not a task under
panic-deprecate-gpu-assert. Rationale: it's orthogonal to the deprecation work and
affects the std panic path (panic-std-intercept's domain). Create it after the current
two features complete to avoid scope creep mid-story.

Proposed: feature `panic-abort-path` with 1 task — expose `set_warp_trapped` and
`write_panic_to_result` as `extern "C"` from gpu-runtime, call from patched std's
`abort_internal()` on CUDA. This completes the host-side reliability story.
