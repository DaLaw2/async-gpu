## Analysis: Dynamic Dispatch on nvptx64

**What works now**: All GPU traits are monomorphized (static dispatch). `GpuReducible`,
`GpuTransformable`, `RawWakerVTable` — all resolved at compile time. Box<T> works
(heap via hostcall allocator). No `dyn` keyword exists anywhere in kernel-side code.

**The core challenge**: `&dyn Trait` / `Box<dyn Trait>` creates a fat pointer
(data_ptr + vtable_ptr). On nvptx64, vtables are placed in `AddressSpace::ZERO`
(see `rustc_middle/src/mir/interpret/mod.rs:311`). Function pointers use the
instruction address space. The PTX ISA supports indirect calls (`call.uni`), but
vtable function pointer loads must produce valid code pointers. Three risks:
1. Address space mismatch: vtable in addrspace 0, functions in instruction space
2. Indirect calls: LLVM nvptx backend may reject indirect `call` through vtable
3. Fat pointer layout: data + vtable must both be valid 64-bit GPU pointers

**Existing vtable usage on GPU**: `RawWakerVTable` in executor.rs, channel.rs,
std_future.rs — BUT these are `const` vtables with known function pointers,
never called through dynamic dispatch. The compiler inlines them entirely.

## Activation Decision

**Activate gpu-dyn-dispatch** as the primary story. Three features:

1. **dyn-probe** (investigation): Can `&dyn Trait` compile to PTX at all?
2. **dyn-box** (experiment): Box<dyn Trait> end-to-end on GPU
3. **dyn-perf** (experiment): Measure dynamic vs static dispatch overhead

**Second story**: Do NOT activate a second story yet. gpu-dyn-dispatch has
significant unknown risk (compiler-level). Focus resources on one frontier.

## Key Insight

The project already uses vtables on GPU (Waker), but only as inlined constants.
True dynamic dispatch (`&dyn Trait` with runtime vtable lookup + indirect call)
is untested on nvptx64. The critical investigation is whether LLVM's PTX backend
can emit indirect calls through vtable pointers — this determines the entire
approach (works natively vs needs compiler patches vs fundamentally impossible).
