# Brainstorm 131 — Auto-tuning: kernel gap, not framework gap

**Trigger**: transparent-data story #61 completed. auto-tuning at-framework done but "measurable speedup" criterion unmet.
**Cycle**: 642 | **Level**: Standard

---

## Analysis

The auto-tuning framework is solid: warmup search, median timing, occupancy
filtering, cache, reporting. The gap is **kernel**, not framework.

vector_add is memory-bound — block_size barely affects throughput because the
bottleneck is global memory bandwidth, not compute. Need a **compute-bound**
kernel where block_size determines occupancy and thus throughput.

## Candidate: N-body gravity simulation

`gravity_forces` in compute_physics.rs is compute-bound (sqrt, division,
accumulation per pair) and uses a fixed block_dim=256. With N-body's O(N^2)
per-thread work, block_size directly controls occupancy vs register pressure
tradeoff. A tuner searching [64, 128, 256, 512] will find meaningful
differences — potentially 1.5-2x between worst and best.

## Recommendation

Create at-framework.3: write an auto-tune bench for gravity_forces (or a
dedicated compute-intensive kernel like iterative stencil), demonstrate
measurable speedup, and verify the story criterion. This is the last gate
before completing the auto-tuning story.
