# bs134: conv-perf features — Winograd F(4x4,3x3) + channel batching

**Trigger**: conv-perf story activated by 3/3 vote. Previous features archived at cycle 639.

## Key Insight

Current Winograd F(2x2,3x3) achieves 1.5-5.5% of peak (71-276 GFLOPS on GTX 1660).
The bottleneck is NOT the algorithm — it's that each thread serializes over C_in,
doing 16 independent multiply-accumulates per channel with zero data reuse. The fix
is restructuring Winograd as batched GEMM in the transform domain: for each of the
16 Winograd positions, compute a C_out x C_in @ C_in x n_tiles matrix multiply via
cuBLAS. This converts per-tile serial work into GPU-wide parallel GEMM, which is
exactly what cuBLAS excels at. F(4x4,3x3) doubles the output tile (4x4 vs 2x2),
reducing tiles by 4x — but requires 36-point transforms vs 16, so investigation
is needed to determine if F(4x4) or optimized F(2x2) with batched GEMM wins.

## Features

1. **conv-baseline** — Measure current conv2d perf vs cuDNN reference
2. **conv-wino-gemm** — Restructure Winograd as 16 batched GEMMs (the big win)
3. **conv-direct-opt** — Optimize direct conv kernel for non-3x3 (3x3 stride>1, 5x5)

## Plan

Start with baseline measurement (conv-baseline.1) to quantify the gap. Then
restructure Winograd as batched GEMM (conv-wino-gemm.1-3) — this is the highest
leverage. F(4x4) investigation folded into conv-wino-gemm.1. Direct conv
optimization is lower priority since 3x3 stride=1 dominates ResNet/YOLO.
