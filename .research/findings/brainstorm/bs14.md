## Consensus Points

Both agents agree on:

1. **Multi-threaded host listener is P0** — the 28K calls/s ceiling is THE bottleneck. All performance improvements are gated by this.
2. **GPU panic handler is high-value** — debugging `loop {}` hangs is essential for continued development.
3. **Nightly update is P1** — test newer nightlies in isolation, don't block other work.
4. **Large-payload is P1** — enables real workloads, but more complex than initially scoped.
5. **Networking, upstream stay parked** — correct prioritization.
6. **"What NOT to pursue" list** — AMD port, custom rustc, CUDA library interop, full std, WGSL/Vulkan all correctly excluded.

## Resolved Disputes

### 1. gpu-panic priority: P1 → P0
**Proposer**: P1. **Skeptic**: P0, because debugging will be needed during host-scaling development.
**Resolution**: **P0**. Skeptic's argument is compelling — implement panic handler before multi-threaded listener work, since debugging hangs during concurrent code development is critical.

### 2. Host-scaling approach: design-first → profile-first
**Proposer**: Jump to design (host-scaling.1). **Skeptic**: Profile first (host-scaling.0).
**Resolution**: **Profile first**. Skeptic's "measure before optimizing" principle is sound. We don't know if the bottleneck is polling, dispatching, I/O syscalls, or the adaptive sleep. Profiling determines whether we need multi-threading, async I/O (tokio), or just faster polling.

### 3. Warp-coop: conditional unpark → permanently parked
**Proposer**: Unpark after host-scaling. **Skeptic**: ADR-4 (per-lane async) is fundamentally incompatible with warp-cooperative allocation — lanes reach hostcall at different times, can't synchronize without barriers that serialize async execution.
**Resolution**: **Keep permanently parked** (or scope as "sync-only warp-coop" if ever revisited). The ADR-4 incompatibility is architectural, not temporal — it doesn't resolve after host scaling.

### 4. gpu-logging: full framework → metadata enhancement
**Proposer**: Full structured logging theme (P2). **Skeptic**: Just add thread/block/warp ID to println output (single task).
**Resolution**: **Single task** — add metadata to host-side print handler. Structured logging is library development, not research. Can revisit if demand emerges.

### 5. gpu-to-gpu: P2 → dropped
**Proposer**: P2 with hostcall relay. **Skeptic**: No use case identified, requires special hardware, not competitive with NCCL.
**Resolution**: **Drop**. No concrete research question to answer.

### 6. Relaxed atomics and allocator hardening: drop
**Proposer**: Mentioned as possibilities. **Skeptic**: No current code path benefits from gpu-scope atomics; allocator has no concrete failure.
**Resolution**: **Drop both**. Solutions without problems.

### 7. gpu-kernel ABI migration: P1 → investigation only
**Proposer**: Migrate for future-proofing. **Skeptic**: Entire crate ecosystem is NVIDIA-specific, "path to AMD" is a mirage.
**Resolution**: **Investigation only** (part of nightly-update). Test if gpu-kernel ABI works, document differences, but don't migrate unless there's a concrete benefit. Keep ptx-kernel as primary.

## Unresolved (deferred)

- **Large-payload protocol design**: Ring buffer vs multi-packet chain vs bigger slots. Needs investigation task before design. Skeptic correctly notes "shared memory" is a misnomer — it's a second mapped buffer.
- **Local memory spilling impact**: Is it actually hurting performance? Needs measurement before mitigation. Added as investigation within host-scaling profiling scope.

## Summary

The project is product-ready but I/O-throughput-limited. Phase 3 focuses on three axes:
1. **Debugging** (gpu-panic, P0): Make development possible for complex concurrent code
2. **Throughput** (host-scaling, P0): Remove the single-threaded host listener bottleneck
3. **Capability** (large-payload + nightly-compat, P1): Enable real workloads and future-proof the toolchain

Warp-coop is permanently parked (ADR-4 incompatibility). GPU-to-GPU, relaxed atomics, and full logging framework are dropped. The critical path is: panic handler → profile listener → design scaling → implement → benchmark → large-payload → workload demo.
