# BS16 Synthesis — Warp-level Future Feasibility
**Date**: 2026-03-12
**Brainstorm seq**: 16
**Level**: deep (proposer + skeptic)
**Target**: ADR-9 / warp-future theme — WarpFuture trait + proc macro for SIMT-convergent async

---

## Consensus Points

Both proposer and skeptic agree on the following:

### 1. The approach is architecturally sound in principle
- A `WarpFuture` trait with uniform state discriminant broadcast via `shfl.sync.idx.b32` is technically feasible without rustc changes.
- The packet payload layout (32 lanes x 8 slots x 8 bytes) already fits warp-level hostcalls perfectly.
- `bar.warp.sync` and `shfl.sync.idx.b32` are well-established PTX instructions available since SM30/SM70.

### 2. The problem is currently unmeasured
- **No kernel in this project runs per-thread async futures across a full 32-thread warp.** All existing async kernels run thread 0 only.
- The "1/32 throughput" claim is worst-case theoretical. SM70+ independent thread scheduling partially mitigates divergence.
- Actual divergence penalty may be small for our workloads (most time is in spin-wait, which is convergent).

### 3. Hand-written PoC before proc macro
- Both agree: start with a hand-written `WarpFuture` state machine for a single hostcall PRINT, not a proc macro.
- Verify `shfl.sync` and `bar.warp.sync` from inline PTX asm first — entire approach depends on these.

### 4. Proc macro has fundamental limitations
- Cannot handle arbitrary Rust control flow (loops with await, `?` operator, `select!`).
- Must define a restricted subset of supported patterns.
- Phase 2 (rustc changes) will likely be needed for full ergonomics.

---

## Unresolved Disputes

### 1. How severe is the divergence problem in practice?
- **Proposer**: Estimates 60-90% throughput loss due to divergence; "WarpFuture is not merely an optimization — it is the correct way to use async on SIMT hardware."
- **Skeptic**: Natural execution patterns may already be mostly convergent (lanes start together, diverge briefly during host response skew, reconverge). The divergence penalty may be negligible compared to hostcall latency (~13µs).
- **Resolution**: Measure first (skeptic's recommendation #1). Create a 32-thread per-warp async benchmark and measure SIMT efficiency.

### 2. Are simpler alternatives sufficient?
- **Skeptic** proposes three cheaper approaches:
  1. Warp-cooperative scheduling (add `__syncwarp()` between task polls in existing executor)
  2. Warp-cooperative CAS (lane-0-elect for free stack allocation)
  3. Accept hardware predication (SM70+ handles it)
- **Proposer**: These don't address the fundamental problem (state discriminant divergence in the `match` statement).
- **Resolution**: Try warp-cooperative CAS (addresses measured CAS contention) alongside WarpFuture PoC. They are complementary, not competing.

### 3. `__syncwarp()` deadlock risk with conditional yields
- **Skeptic**: Conditional `warp_await!` inside `if` blocks causes deadlock because not all lanes reach the barrier.
- **Proposer**: WarpFuture's contract forbids per-lane control flow divergence — "differences are in data, not control flow."
- **Resolution**: This is a real constraint. WarpFuture restricts the programming model to SIMD-style computation where all lanes follow the same path. This is acceptable for GPU workloads but must be documented explicitly. Conditional operations use predication (all lanes execute, inactive lanes discard results).

---

## Key Decision: Empirical-First Approach

Based on both analyses, the correct path is:

1. **Verify intrinsics** (warp-future.1 completion): Confirm `shfl.sync` and `bar.warp.sync` compile to correct PTX from inline asm. This is a prerequisite for everything else.

2. **Measure the problem** (new task): Create 32-thread per-warp async benchmark. Measure actual SIMT efficiency with per-thread futures. If >70%, WarpFuture may not be justified for current workloads.

3. **Hand-written PoC** (warp-future.3): Regardless of measurement, a minimal WarpFuture demonstrates the concept and validates convergence in PTX.

4. **Proc macro** (warp-future.4): Only after hand-written PoC proves measurable improvement.

## Impact on Tasks

- **warp-future.1** (feasibility): DONE — feasibility confirmed with constraints. Proceed with caution.
- **warp-future.2** (design): Proceed, but keep it minimal — focus on WarpFuture trait + WarpExecutor + warp-cooperative hostcall submit. Skip proc macro design for now.
- **warp-future.3** (implementation): Critical gate — hand-written WarpFuture for single PRINT hostcall. Must verify convergent PTX.
- **warp-future.4** (proc macro): Defer until warp-future.3 demonstrates measurable improvement.

## ADR-9 Status
ADR-9 remains **proposed** — not accepted until empirical data validates the approach (per skeptic recommendation #6).
