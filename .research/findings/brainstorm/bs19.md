# Brainstorm bs19: hybrid-executor next steps + project direction
**Trigger**: interval (86-82=4 >= 3) + hybrid-executor theme needs task planning
**Level**: standard

## Technical Analysis

### hybrid-executor Status
hybrid-executor.1 proved the core concept: a WarpFuture state machine can transition
from warp-cooperative I/O (PRINT hostcall) to per-thread divergent computation and
back. 32 lanes verified, syncwarp() reconvergence works, switching overhead is
negligible (~syncwarp instruction only). The 6-state machine (INIT_PRINT -> WAIT_PRINT
-> COMPUTE -> INIT_PRINT2 -> WAIT_PRINT2 -> DONE) is clean and straightforward.

### Remaining Success Criteria
1. **WarpFuture can transition to per-thread computation and back** -- DONE
2. **syncwarp() correctly inserted at switching points** -- DONE
3. **Switching overhead measured (target: negligible vs hostcall latency)** -- Partially done (trivial workload only)
4. **API makes it hard to misuse switching points** -- NOT YET DONE

### What Still Needs Proving

**Variable-duration per-thread work**: hybrid-executor.1 used identical trivial
computation (`lane_id * lane_id + 1`) across all lanes. Real workloads will have
data-dependent iteration counts (e.g., parsing, search, convergence loops). We need
to verify syncwarp() handles the case where lane 3 finishes in 10 cycles but lane 17
takes 10,000 cycles. This is the SIMT contract, but we should empirically confirm it
in our framework since a bug here would be silent and catastrophic.

**Multiple switching points**: The PoC has exactly one per-thread block. A realistic
kernel might alternate I/O and computation multiple times (read -> compute -> write
intermediate -> compute more -> write final). We should verify the pattern composes
cleanly and that no state corruption occurs with N switching points.

**Safety API**: The biggest footgun is accidentally yielding inside a per-thread block.
If one lane yields (returns Poll::Pending on a hostcall) while others don't, warp
divergence breaks the WarpFuture invariant. The question is whether a macro or type-
level guard is worth it, or whether documentation + code review suffices.

## Skeptic Challenges

### Is hybrid-executor worth more than 2-3 tasks?
**Assessment: No, it is not.** The core mechanism is proven. The SIMT model guarantees
syncwarp() handles variable-duration work -- this is not our invention, it's how GPUs
work. Testing it is a 30-line kernel change (add a loop with lane-dependent iteration
count). The multiple-switching-point test is similarly incremental. A macro for safety
would be premature -- we have no users yet, and the pattern is 6 lines of code.

**Recommendation**: 2 more tasks maximum. One to stress-test with realistic workloads
(variable duration + multiple switches), one design note on the safety API that can
be deferred to when we actually have users.

### Is per_thread_block! macro truly needed?
**No, not now.** The pattern is:
1. Enter state (broadcast)
2. Compute (per-lane, no yield)
3. syncwarp()
4. Lane 0 advances state
5. syncwarp()

This is simple, documented, and identical to all other WarpFuture states except for
step 2. A macro would save ~3 lines but add cognitive overhead ("what does this macro
expand to?"). If we later build a proc macro for WarpFuture state machines (warp-future.5
was planned for this), the per-thread block can be an attribute on a state arm.

**Decision**: Document the pattern. Defer macro to warp-future proc macro work.

### What's the real use case?
The compelling use case is: GPU kernel reads data via hostcall (WarpFuture, warp-
cooperative), processes it per-thread (divergent computation like parsing, filtering,
transformation), then writes results via hostcall (back to WarpFuture). This is the
standard scatter-gather pattern for GPU-accelerated I/O processing.

Without hybrid execution, users would need to either:
- Do all computation in warp-cooperative mode (artificial constraint, wastes SIMT)
- Use only per-thread futures (32x hostcall overhead)

## Candidate Tasks

### hybrid-executor.2: Variable-duration + multi-switch stress test
**Kind**: experiment
**Goal**: Prove the pattern works with (a) lane-dependent iteration counts in per-thread
blocks, and (b) multiple alternating I/O and compute phases in one state machine.
**Approach**: Kernel with 3+ per-thread blocks, each with data-dependent loop counts.
Verify all 32 lanes produce correct results. Measure total kernel time.
**Questions**:
- Does syncwarp() correctly synchronize lanes with 100x duration variance?
- Does the state machine remain clean with 10+ states?
- Any PTX codegen issues with complex per-thread blocks?

### hybrid-executor.3: Safety API design note
**Kind**: design
**Goal**: Document the per-thread block safety contract and evaluate API options.
**Approach**: Write up the invariant ("no yield in per-thread block"), enumerate
enforcement options (macro, type state, lint, documentation), and recommend one.
Record as ADR in decisions.md.
**Questions**:
- What happens if someone accidentally yields in a per-thread block?
- Can we detect this at compile time?
- Is runtime detection feasible (check active_mask after per-thread block)?

## Parked Themes Assessment

### warp-coop (parked)
Warp-cooperative hostcall batching for scaling. This is architecturally interesting
but the project already has WarpFuture which IS warp-cooperative. The original goal
was 512-thread scaling -- but the per-block-sharding theme already solved multi-block
execution. **Keep parked.** The incremental value over current WarpFuture is unclear.

### networking (parked)
TCP/UDP via hostcall. Cool demo but not on the critical path to "product ready."
The hostcall protocol can already carry arbitrary service types -- adding TCP would
be a new service handler on the host side, not a new GPU mechanism. **Keep parked.**
Could unpark later as a showcase.

### upstream (parked)
Contributing fixes upstream. Valuable but not blocking. The LLVM NVVM atomics bug
workaround (inline PTX) is stable. **Keep parked** until the project is more mature
and we have bandwidth for upstream engagement.
