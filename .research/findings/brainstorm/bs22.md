# bs22 — ML Workload Brainstorm: Vector Similarity Search + Persistent Kernel

**Trigger**: New epic `ml-workload` — extend GPU-autonomous async pipeline to real ML workloads
**Level**: standard (single analysis)

---

## 1. Technical Analysis

### 1.1 Sideband Buffer Sizing

**Per-vector cost**: 128 dimensions × 4 bytes (f32) = **512 bytes/vector**.

**Capacity at 1MB (default)**:
- Raw vectors: 1,048,576 ÷ 512 = **2,048 vectors** max
- With metadata overhead (vector ID, norm cache): ~480 bytes usable per entry → ~2,184 vectors
- Practical limit with query vector + result buffer sharing: **~1,800 database vectors + 1 query + top-K output**

**Is 1MB enough?** Yes, for the stated scope (hundreds to low thousands). 1,800 vectors × 128 dims is a meaningful vector database demo. This is intentionally not a production vector DB — it is a proof-of-concept that the GPU can autonomously load, compute, and return results.

**Should sideband be configurable?** Already is — `HostcallBuffer::new_with_sideband(num_packets, sideband_data_size)` exists. For larger databases, the host can allocate 4MB or 16MB sideband trivially. No infrastructure change needed.

**Multi-round bulk read for larger databases**: The sideband bump allocator can be reset between rounds via `sideband_reset()`. A WarpFuture state machine can:
1. Read chunk 1 (e.g., 1MB of vectors) → compute partial similarities → store partial top-K
2. `sideband_reset()` → read chunk 2 → merge top-K
3. Repeat until database exhausted

This streaming approach means the sideband size is not a hard cap on database size — only on per-round throughput. However, for ml-workload.2, a single-round approach (entire DB fits in sideband) is simpler and sufficient for the demo.

**Recommended layout** (single-round, 1MB sideband):
```
Offset 0:        query vector      (512 bytes = 128 × f32)
Offset 512:      database vectors   (N × 512 bytes)
Offset 512+N*512: result buffer     (top-K entries: K × 12 bytes = vec_id:u32 + score:f32 + pad:u32)
```

With K=10 and N=1500: 512 + 768,000 + 120 = 768,632 bytes. Fits in 1MB with room to spare.

### 1.2 Compute Model

**Cosine similarity formula**:
```
cos(a, b) = dot(a, b) / (||a|| × ||b||)
```
where `dot(a, b) = Σ(a_i × b_i)` and `||a|| = sqrt(Σ(a_i²))`.

**f32 on nvptx64**: Fully native. PTX has `mul.f32`, `add.f32`, `fma.f32`, `sqrt.approx.f32`, `div.approx.f32`. The Rust compiler emits these directly — no software emulation needed. `core::f32` operations (add, mul, div) work. For `sqrt`, we need `core::arch::nvptx::_sqrtf` or inline PTX `sqrt.approx.f32` — `f32::sqrt()` may not be available in `no_std` without `libm`.

**Work distribution — two viable strategies**:

| Strategy | Description | Pros | Cons |
|----------|-------------|------|------|
| **Per-lane** | Each of 32 lanes handles one database vector. Process 32 vectors per iteration. | Simple. Full SIMT utilization. No warp reduction needed for dot product. | Need outer loop for N>32. Lane divergence if N%32≠0. |
| **Per-warp** | All 32 lanes cooperate on one vector: each lane does 4 dims (128/32=4), then warp-reduce. | Warp reduction shows off shfl intrinsics. | Complex. Underutilizes ALU (only 4 muls per lane per vector). Slower for this problem size. |

**Recommendation: Per-lane strategy.** Each lane computes the full 128-dim dot product for one database vector. This is the natural SIMT model — same code, different data. For N=1500 database vectors with 32 lanes, we need ⌈1500/32⌉ = 47 iterations. Each lane does 128 FMAs per iteration = 128 × 47 = 6,016 FMAs total. Trivial compute load.

**Top-K selection**:
- K is small (10). No need for parallel sort.
- Each lane maintains a local top-K array (10 entries, insertion sort on each new score).
- After all database vectors processed, lane 0 collects top-K from all lanes via `shfl.sync` and merges.
- Alternatively (simpler): lane 0 maintains the only top-K array, receives scores from all lanes via `shfl.sync` after each batch of 32.
- **Recommendation**: Per-lane top-K with final merge. This keeps all lanes busy and avoids serialization. K=10 means each lane's insertion sort is O(K) = O(10) per vector — negligible.

### 1.3 Persistent Kernel Design

**Core challenge**: The kernel must loop indefinitely, checking for new work, processing it, signaling completion, and waiting again — without being killed by the OS.

**Communication protocol options**:

| Option | Mechanism | Pros | Cons |
|--------|-----------|------|------|
| **A: Reuse hostcall buffer** | Add SERVICE_QUERY_READY / SERVICE_RESULT_READY commands | No new infrastructure. Host listener already polls. | Overloads hostcall semantics. Query data transfer awkward. |
| **B: Separate mailbox in sideband** | Reserve first 64 bytes of sideband as command/status mailbox | Clean separation. GPU reads mailbox via mapped memory. No hostcall overhead. | Must define new protocol. Must handle mailbox race conditions. |
| **C: Separate CUDA mapped buffer** | Dedicated command buffer (small, 4KB) | Cleanest. No contention with sideband data. | One more allocation. Slightly more host setup. |

**Recommendation: Option B (mailbox in sideband).** The sideband is already GPU-mapped. Reserve the first 64 bytes:
```
Offset 0: command  (u32) — IDLE=0, QUERY=1, SHUTDOWN=2
Offset 4: status   (u32) — IDLE=0, PROCESSING=1, DONE=2
Offset 8: query_offset  (u64) — offset of query vector in sideband data
Offset 16: result_offset (u64) — offset of results in sideband data
Offset 24: db_size  (u32) — number of database vectors
Offset 28: top_k    (u32) — K for top-K
Offset 32: reserved (32 bytes)
```

Wait — the sideband already has a 64-byte header (`SIDEBAND_HEADER_SIZE = 64`). The mailbox could be placed in the reserved region of that header (bytes 16-63 are currently reserved). This avoids any layout change.

**GPU loop**:
```
loop {
    spin_load_acquire(command_ptr) until != IDLE
    if command == SHUTDOWN → break
    store_release(status, PROCESSING)
    // read query from sideband, compute similarities, write results
    store_release(status, DONE)
    store_release(command, IDLE)  // ready for next query
}
```

**Host side**:
```
// Submit query:
write query vector to sideband
store_release(command, QUERY)
// Wait for result:
spin_load_acquire(status) until == DONE
read results from sideband
```

**Windows TDR (Timeout Detection and Recovery)**:

This is the **single biggest risk** for ml-workload.3. Windows has a default 2-second TDR timeout (`TdrDelay` registry key). A persistent kernel spinning in a loop **will** trigger TDR and be killed by the OS.

**Mitigations**:
1. **Disable TDR** — Registry: `HKLM\SYSTEM\CurrentControlSet\Control\GraphicsDrivers`, set `TdrLevel = 0`. Works but requires admin + reboot. Not portable.
2. **Extend TDR timeout** — Set `TdrDelay = 60` (seconds). Better but still has a cap.
3. **Use `nanosleep` in spin loop** — `nanosleep.u32` yields the SM but may not be enough to prevent TDR.
4. **Use CUDA compute-exclusive mode** — Doesn't help with TDR directly.
5. **WDDM vs TCC driver model** — TCC (Tesla Compute Cluster) mode disables TDR entirely, but is only available on Tesla/datacenter GPUs, not GeForce.

**Practical assessment**: On a development machine (GeForce GPU + WDDM driver), the persistent kernel will work if TDR is disabled via registry. This is acceptable for a research demo. Document the requirement clearly.

### 1.4 Infrastructure Gaps

**f32 math**:
- Basic arithmetic (+, -, *, /): Works natively in PTX via Rust operators.
- `sqrt`: `core::intrinsics::sqrtf32` should emit `sqrt.approx.f32` on nvptx64. If not available in stable `no_std`, use inline PTX: `asm!("sqrt.approx.f32 {out}, {in};", out = out(reg32) result, in = in(reg32) input)`.
- Division: PTX `div.approx.f32` is fast but less precise (~2 ULP). For cosine similarity, this precision is more than adequate.

**Denormals**: PTX defaults to flush-to-zero (FTZ) mode for f32 on most GPUs. This means very small similarity scores might round to zero. Not a concern for top-K selection — we care about the largest scores.

**Data layout**: Struct-of-arrays (SoA) is better than array-of-structs (AoS) for GPU memory coalescing. However, since we're reading from sideband (mapped CPU memory, not device memory), coalescing is less critical — the bottleneck is PCIe bandwidth, not memory controller efficiency. AoS layout (one contiguous 512-byte vector after another) is simpler and fine for this use case.

## 2. Skeptic Challenges

### Challenge 1: Is vector similarity a good demo for GPU autonomy?

**The compute is indeed trivial.** 128-dim dot product is ~128 FMAs. A single CPU core can do this for 1000 vectors in microseconds. The GPU will almost certainly be slower for this problem size when you factor in kernel launch overhead (~5µs) and PCIe data transfer latency.

**Counter-argument**: The demo is not about compute performance. It's about **autonomy**. The GPU:
1. Reads a query vector from a file (via hostcall I/O)
2. Reads a database from a file (via hostcall I/O)
3. Computes similarities (GPU compute)
4. Writes results to a file (via hostcall I/O)

All in one kernel launch, zero CPU intervention. The CPU doesn't know what files to read, what computation to do, or where to write. The GPU decides. **That** is the demo — not raw throughput.

**Verdict**: Valid concern. Must frame the demo correctly in documentation. The headline is "GPU autonomy" not "GPU performance."

### Challenge 2: CPU would be faster for <1000 vectors

**Yes, absolutely.** The crossover point where GPU beats CPU for this workload is probably around 50,000-100,000 vectors, assuming optimized CPU SIMD code. With our hostcall overhead (~20µs per I/O round-trip), the GPU version adds ~100µs of I/O overhead (5 hostcalls × 20µs) before it even starts computing.

**Why this is irrelevant**: Same as above — the demo proves autonomy, not speed. Frame it explicitly: "This demo intentionally uses a small dataset to prove the architecture. For production vector search at scale, the same pattern applies with larger sideband buffers and more warps."

### Challenge 3: Persistent kernel + Windows TDR

**This is a real risk, not a hypothetical one.** See section 1.3. TDR will kill the kernel after 2 seconds by default.

**Mitigation path**: Document the TDR registry change as a prerequisite. Tag ml-workload.3 as requiring user confirmation of environment change (consistent with CLAUDE.md policy).

**Alternative**: Instead of true persistence, implement "multi-query batch" — host provides N queries in sideband, GPU processes all N, returns all results, kernel exits. This gets 80% of the persistent kernel value (multiple queries, one launch) without the TDR problem.

**Recommendation**: Implement both:
- ml-workload.3a: Multi-query batch (no TDR risk, simpler)
- ml-workload.3b: True persistent kernel (requires TDR disable, stretch)

### Challenge 4: Sideband buffer sharing — race conditions?

**Layout concern**: If query input, database, and result output all share the sideband buffer, can the GPU overwrite input data while computing?

**Answer: No race condition exists.** The WarpFuture state machine is sequential:
1. Read query → store in GPU registers/local memory
2. Read database chunk → compute similarities → update top-K (in registers)
3. Write results to sideband → hostcall BULK_WRITE

Steps 1 and 2 read from sideband. Step 3 writes to sideband. The state machine guarantees ordering — no concurrent read+write to the same sideband region.

**However**, for persistent kernel (ml-workload.3): the host writes a new query while the GPU might still be processing the previous one. The mailbox protocol (section 1.3) prevents this — the host must wait for `status == DONE` before writing the next query.

### 3.1 Task Design for ml-workload.1 (investigation)

**Research questions refined**:
1. **f32 sqrt on nvptx64**: Write a trivial kernel that computes `sqrt(2.0f32)`. Verify PTX output uses `sqrt.approx.f32`. If `core::intrinsics` not accessible, prototype inline PTX wrapper.
2. **Sideband capacity math**: Confirm 1MB fits 1500 vectors + query + results. Calculate exact byte layout.
3. **Per-lane vs per-warp work distribution**: Sketch both approaches, count instructions. Confirm per-lane is simpler.
4. **Identify all new code needed**: List every function/struct that ml-workload.2 requires but doesn't exist yet (e.g., f32 sqrt wrapper, top-K selection logic, vector read/write helpers).

**Deliverable**: A concrete design document for ml-workload.2 — data layout, state machine states, new helper functions needed.

### 3.2 Design Choices for ml-workload.2 (experiment)

**Data layout** (single-round, AoS):
```
Sideband (1MB):
  [0..512)        query vector (128 × f32)
  [512..N*512+512) database vectors (N × 128 × f32)
  [N*512+512..)   result buffer (K × {id:u32, score:f32})
```

**State machine** (WarpFuture, hand-written like FileTransformFuture):
```
State 0:  OPEN_DB       — open database file (warp-cooperative hostcall)
State 1:  READ_DB       — bulk_read database into sideband
State 2:  CLOSE_DB      — close database file
State 3:  OPEN_QUERY    — open query file
State 4:  READ_QUERY    — bulk_read query vector into sideband
State 5:  CLOSE_QUERY   — close query file
State 6:  COMPUTE       — per-thread: each lane processes N/32 vectors, maintains local top-K
State 7:  MERGE_TOPK    — warp-cooperative: merge per-lane top-K via shfl, lane 0 writes to sideband
State 8:  OPEN_OUTPUT   — open output file
State 9:  WRITE_RESULTS — bulk_write top-K results from sideband
State 10: CLOSE_OUTPUT  — close output file
State 11: DONE
```

12 states total. Similar complexity to FileTransformFuture (16 states).

**Top-K algorithm**: Per-lane insertion sort with K=10. After COMPUTE, each lane has its local top-10. In MERGE_TOPK, lane 0 collects via `shfl.sync`, merges 32 lists of 10 into final top-10. Total merge work: 320 candidates → top 10. Simple linear scan.

**Input file format**: Binary for simplicity.
- Database file: `[N:u32][dim:u32][v0_d0:f32][v0_d1:f32]...[v0_d127:f32][v1_d0:f32]...`
- Query file: `[dim:u32][q_d0:f32]...[q_d127:f32]`
- Output file: `[K:u32][id0:u32][score0:f32][id1:u32][score1:f32]...`

**Host-side test harness**: Generate random database + query files, launch kernel, read output, verify against CPU reference implementation.

### 3.3 Risk Assessment for ml-workload.3 (persistent kernel)

| Risk | Severity | Likelihood | Mitigation |
|------|----------|------------|------------|
| Windows TDR kills kernel | **Critical** | **Certain** (default settings) | Disable TDR via registry (requires user action) |
| GPU spin loop wastes power | Low | Certain | `nanosleep.u32` in spin loop |
| Mailbox race condition | Medium | Low | Protocol enforces strict ordering |
| Hostcall buffer exhaustion during long run | Medium | Low | Single warp, 8 packets — plenty |
| GPU memory leak (sideband allocator) | Medium | Medium | Reset allocator between queries |

**Overall**: Medium risk. TDR is the gating issue. If user can disable TDR, the rest is straightforward.

### 3.4 New Tasks / Dependencies

Current task structure is correct:
- `ml-workload.1` (investigation) → no deps → **do first**
- `ml-workload.2` (experiment) → depends on .1 → **main deliverable**
- `ml-workload.3` (experiment) → depends on .2 → **stretch goal**

**Consider splitting ml-workload.3**:
- `ml-workload.3` → multi-query batch (no TDR risk)
- `ml-workload.4` → true persistent kernel (requires TDR disable)

This lets us deliver something for the persistent-query use case without the TDR dependency.

**No other new tasks needed.** The infrastructure is complete — WarpFuture, hostcall, sideband, bulk read/write all exist. ml-workload.2 is purely kernel-side code + host test harness.

### 3.5 Priority Ordering

1. **ml-workload.1** (investigation) — Quick. 1-2 hours. Validates f32 math, finalizes data layout. Unblocks .2.
2. **ml-workload.2** (experiment) — Main deliverable. 4-6 hours. Hand-write the WarpFuture, build test harness.
3. **ml-workload.3** (multi-query batch) — Natural extension of .2. 2-3 hours. Add outer loop + batch input.
4. **ml-workload.4** (true persistent kernel) — Stretch. Requires TDR change. Park until user confirms.

**Rationale**: .1 is fast and de-risks .2. The .2 demo is the star of the epic — prove that a GPU can autonomously run a vector search pipeline. The .3/.4 split avoids blocking on environment changes.

## 4. Summary

The ml-workload epic is well-scoped and achievable with existing infrastructure. Key findings:

1. **1MB sideband fits ~1,800 vectors** — sufficient for the demo, configurable for larger.
2. **f32 math is native on nvptx64** — sqrt needs a small wrapper (inline PTX or intrinsic).
3. **Per-lane work distribution** is the right model — simpler and more efficient than per-warp cooperative.
4. **12-state WarpFuture** mirrors FileTransformFuture pattern — no architectural novelty, just application.
5. **Persistent kernel is feasible but blocked by Windows TDR** — split into batch (safe) + persistent (stretch).
6. **The demo's value is autonomy, not performance** — frame accordingly.
