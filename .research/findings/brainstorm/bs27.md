**Trigger**: EPIC review — 4 gaps remain before GPU-Native Async Pipeline is complete
**Level**: deep (multi-perspective analysis in single document)

---

## 1. Technical Analysis

### Gap 1: `#[warp_async]` Generalization

**Current state**: The proc macro only recognizes `warp_print!(buf, msg)` calls. It extracts byte-literal messages, generates INIT+WAIT state pairs with hardcoded PRINT service logic (cooperative 32-byte write, lane-0 overflow, metadata at payload+64). The macro rejects any non-`warp_print!` statement — no variable bindings, no expressions, no other macro calls.

**What generalization requires**:

Each hostcall service has a different payload layout:
- **OPEN**: slot0 = path_len | (flags << 32), slots 1-7 = path bytes. Response: fd (u64).
- **READ**: slot0 = fd, slot1 = max_bytes. Response: bytes_read + data.
- **WRITE**: slot0 = fd, slot1 = data_len, slots 2-7 = data bytes. Response: bytes_written.
- **CLOSE**: slot0 = fd. Response: 0 or error.
- **BULK_READ/BULK_WRITE**: slot0 = fd, slot1 = sideband_offset, slot2 = length. Response: bytes_transferred.
- **STDIN**: no request payload. Response: bytes_read + data.
- **TIME**: no request payload. Response: seconds + nanoseconds.
- **PRINT**: slot0 = msg_len, slots 1-7 = message, payload+64 = block/thread metadata.

**Concrete approach — macro call per service**:

Rather than parsing arbitrary Rust, define one macro per service:
```rust
#[warp_async]
unsafe fn my_pipeline(buf: *mut u8, sideband: *mut u8) -> bool {
    let fd = warp_open!(buf, b"data.txt", FILE_OPEN_READ);
    let n = warp_bulk_read!(buf, sideband, fd, offset, len);
    warp_close!(buf, fd);
    let fd2 = warp_open!(buf, b"out.txt", FILE_OPEN_WRITE_CREATE);
    warp_bulk_write!(buf, sideband, fd2, offset, len);
    warp_close!(buf, fd2);
    warp_print!(buf, b"done");
}
```

Each `warp_*!()` call expands to an INIT+WAIT state pair. The proc macro must now:
1. Parse `let` bindings (variable = return value from WAIT state)
2. Recognize multiple macro names (`warp_open!`, `warp_close!`, `warp_read!`, `warp_write!`, `warp_bulk_read!`, `warp_bulk_write!`, `warp_print!`, `warp_stdin!`, `warp_time!`)
3. Track variable liveness — `fd` from `warp_open!` must be stored in the struct and available in later states
4. Generate different payload fill/read logic per service type
5. Handle return values (OPEN returns fd, READ returns bytes_read, TIME returns (secs, nanos))

**Variable tracking is the hard part.** The proc macro must:
- Identify which `let` bindings hold hostcall return values
- Add corresponding fields to the generated struct
- In WAIT states, store the response value into the struct field
- In subsequent INIT states, read from the struct field when the variable is used as an argument

This is essentially a mini-compiler for a sequential DSL. The input language is constrained enough (only `let` bindings and `warp_*!()` calls, no control flow) that it is tractable.

**Difficulty**: Medium-high. The proc macro jumps from ~400 lines to ~1200-1500 lines. The type system challenge is that `warp_open!` returns `u64` (fd), `warp_bulk_read!` returns `u64` (bytes), `warp_time!` returns `(u64, u64)`. The macro must infer field types from the macro name.

**Dependencies**: None — purely a proc macro change. The runtime helpers (`warp_hostcall_submit`, `warp_hostcall_wait_u64`) should be moved from `gpu-kernel` to `gpu-runtime` first so the generated code can reference them.

**Alternative approach — builder pattern instead of proc macro**:
```rust
WarpPipeline::new(buf)
    .open(b"data.txt", READ)
    .bulk_read(sideband, |fd, offset, len| ...)
    .close()
    .print(b"done")
    .build()
```
This avoids proc macro complexity but loses the sequential code feel. Given that hand-written WarpFutures already work and the 20-state pattern is proven, the proc macro approach is the right investment — it's the user-facing API that makes the system usable.

**Estimated effort**: 3-5 days for a robust implementation with tests.

### Gap 2: Conditional/Branching Pipelines

**Current state**: All WarpFuture state machines are linear sequences: state 0 → 1 → 2 → ... → N → DONE. The `match` on broadcast state selects exactly one arm per poll. There is no mechanism for a state transition to depend on a runtime value.

**What branching requires**:

Consider: "If file exists, open for read; else create and write."
```
State 0: OPEN_READ → try open file for reading
State 1: CHECK_OPEN → if fd != ERROR → goto READ_DATA (state 3)
                       else → goto CREATE_FILE (state 5)
State 3: READ_DATA → ...
State 5: CREATE_FILE → open for write+create
```

This is a **conditional state transition** — the next state depends on a runtime value (the fd returned by the host). The WarpFuture architecture already supports this. The state is just a `u32` stored in the struct and broadcast via `shfl.sync`. Nothing prevents a WAIT state from setting `self.state = X` or `self.state = Y` based on the response value.

**The constraint is that all 32 lanes must take the same branch.** Since state is broadcast from lane 0, and lane 0 makes the branching decision based on the hostcall response (which is warp-uniform — one response per packet), this works correctly. All lanes see the same fd/error, so all lanes agree on the branch.

**In the proc macro**: Branching is harder to express. Options:
1. **Don't support it in the macro** — require hand-written WarpFuture for branching. This is the pragmatic answer. The macro handles 80% of cases (linear pipelines), the escape hatch is hand-coding.
2. **Add `warp_if!` syntax** — `warp_if!(condition, { true_branch }, { false_branch })`. The proc macro generates forked state ranges. Complexity increases significantly (state numbering becomes a DAG, not a list).
3. **Use closures/combinators** — `pipeline.then_if(|fd| fd != ERROR, read_branch, create_branch)`. Clean but complex to implement.

**Hand-written branching already works.** The existing `warp_hostcall_wait_u64` returns `Option<u64>`, and the calling code can set `self.state` to different values based on the returned value. This is proven — it just isn't automated by the proc macro.

**Concrete approach**:
- Phase 1: Document that branching requires hand-written WarpFuture. Provide a template/example with conditional state transitions.
- Phase 2 (optional): Add `warp_if!` to the proc macro. This is a nice-to-have, not a blocker.

**Difficulty**: Low for hand-written approach (just documentation + example). High for proc macro support.

**Dependencies**: None for hand-written. Depends on Gap 1 completion for proc macro approach.

**Estimated effort**: 1 day for documentation + example. 3-5 additional days for proc macro `warp_if!`.

### Gap 3: Hostcall Pipelining (Overlapping Computation with I/O)

**Current state**: Each hostcall is a full round-trip: submit → spin-wait → release. During the spin-wait (~20µs), all 32 lanes are blocked doing nothing useful. The `warp_hostcall_submit` function allocates a packet and submits it, then the next state (`warp_hostcall_wait_u64`) spin-polls the control word.

**What pipelining requires**:

Submit a request, then instead of immediately waiting, do useful computation, and check for the response later:
```
State 0: SUBMIT_READ → submit hostcall, store pkt_idx, transition to COMPUTE
State 1: COMPUTE → per-thread work (no I/O dependency)
State 2: CHECK_READ → poll control word. If READY → process response + next. If not → back to COMPUTE.
```

**This already works within the current architecture.** The `warp_hostcall_submit` helper separates submission from waiting. A hand-written WarpFuture can:
1. Call `warp_hostcall_submit` in state N
2. Transition to a COMPUTE state in state N+1
3. In the COMPUTE state, do per-thread work AND check the control word
4. When the response arrives, transition to the next I/O state

The key insight: **nothing in the WarpFuture contract requires that the state after SUBMIT be a WAIT state.** The state machine is just a `match` on a u32 — any state can do anything.

**Practical concern — double-buffering packets**: If you want to pipeline two I/O operations (submit A, compute, submit B, compute, wait A, wait B), you need two packet indices stored simultaneously. The current struct only has one `pkt_idx: u16`. For N concurrent in-flight requests, you need N packet index slots.

**GPU occupancy benefit**: During the ~20µs hostcall round-trip, a warp executing 64ns nanosleep polls has ~312 wasted iterations. If instead those iterations do FMAs, you recover significant compute. For FileTransformFuture's COMPUTE state (XOR transform), this would mean overlapping the bulk_read I/O with the transform computation.

**In the proc macro**: This is very hard to express. The sequential appearance of the macro (`let fd = warp_open!(...)`) implies "wait for the result before proceeding." Pipelining breaks this sequential model. Options:
1. **Don't support in macro** — require hand-written WarpFuture for pipelining.
2. **Add `warp_submit!` (non-blocking) + `warp_await!` (blocking) pair** — `let handle = warp_submit_open!(...); /* compute */ let fd = warp_await!(handle);`. This is the most natural Rust-like API.

**Concrete approach**: Provide a hand-written example demonstrating pipelined I/O + compute. This is a documentation/example task, not an infrastructure task. The infrastructure already supports it.

**Difficulty**: Low (example only). Medium if adding proc macro support.

**Dependencies**: None. The `warp_hostcall_submit` helper already exists.

**Estimated effort**: 1 day for hand-written example + test. 2-3 additional days for proc macro `warp_submit!/warp_await!`.

### Gap 4: Per-Thread Yield (Warp Reconvergence for Divergent Async)

**Current state**: All 32 lanes execute the same state in every poll. The state is broadcast from lane 0 via `shfl.sync.idx.b32`. If lane 5 wants to yield (its I/O isn't done) but lane 12 has completed (its I/O finished), they are stuck — both must execute the same match arm.

**What per-thread yield requires**:

Each lane has its own state (not broadcast from lane 0). On each poll:
1. Each lane loads its own state from thread-local storage
2. Each lane executes its own match arm (SIMT divergence)
3. Lanes that complete early wait at a barrier

**This fundamentally breaks the WarpFuture contract.** WarpFuture's entire value proposition is that all 32 lanes share one state, reducing CAS contention from 32x to 1x. Per-thread yield turns WarpFuture into 32 independent per-thread futures — exactly what the Embassy executor already provides.

**The correct solution already exists: use per-thread futures for divergent async.** The project already has a working Embassy executor on GPU (async-pipeline-test). Per-thread futures use `core::future::Future`, per-thread state machines, per-thread CAS for packet allocation. The Embassy executor polls individual futures independently.

**Hybrid approach (ADR-10)**: WarpFuture for uniform warp-cooperative I/O, per-thread Embassy futures for divergent per-lane async. This is already the stated architectural decision.

**Could partial-warp convergence work?** Imagine lanes 0-15 want service A and lanes 16-31 want service B. You could:
1. Use `vote.sync` to partition lanes into groups
2. Each group executes its own hostcall with a partial active mask
3. Reconverge with `bar.warp.sync` when both complete

This is technically feasible on SM70+ (independent thread scheduling) but enormously complex:
- The state machine must track N sub-warp groups, each with its own state
- Packet allocation needs one packet per sub-group (not one per warp)
- Reconvergence is non-trivial — what if group A finishes 3 hostcalls while group B is still on its first?
- The complexity defeats the purpose of WarpFuture (simplicity)

**Concrete approach**: Don't implement per-thread yield in WarpFuture. Instead:
1. Document that WarpFuture is for uniform-path async (all lanes same operations, different data)
2. For divergent-path async, use Embassy per-thread futures
3. Provide an example showing the hybrid: WarpFuture reads data → per-thread futures do divergent processing → WarpFuture writes results

**Difficulty**: N/A (don't implement). The solution is documentation + correct architectural framing.

**Dependencies**: None.

**Estimated effort**: 1 day for documentation + hybrid example.

## 2. Skeptic Challenges

### Challenge 1: The proc macro generalization (Gap 1) may not be worth the complexity

**The case against**: Hand-written WarpFutures work. They are verbose (20 states = ~400 lines) but correct and debuggable. The proc macro hides state machine details, making debugging harder. When something goes wrong (and it will — this is GPU code), the developer needs to understand the generated code.

**How much boilerplate does the macro actually save?** A 10-state pipeline with the macro might be ~15 lines of input. The hand-written equivalent is ~200 lines. That's a 13x reduction. But the macro itself is 1200+ lines of proc macro code that must be maintained, tested, and debugged.

**Counter-argument**: The proc macro is the user-facing API. Without it, every user must understand tagged pointers, CAS, shard arrays, control words, and payload layouts. The macro abstracts all of that. If the project goal is "Rust async/await on GPU," the macro IS the product — the hand-written code is the implementation detail.

**Verdict**: The macro is worth building, but scope it carefully. Start with the 4 most common services (open, close, bulk_read, bulk_write, print). Skip stdin and time initially — they can be added later.

### Challenge 2: Branching (Gap 2) in the proc macro is a tar pit

**The risk**: Adding `warp_if!` to the proc macro transforms it from a linear code generator into a control flow graph compiler. The macro must handle:
- Nested branches
- Variables defined in one branch but used after the merge point
- State numbering across branch arms of different lengths
- Error handling in branches (what if `warp_open!` fails in one branch?)

This is the road to building a custom compiler inside a proc macro. Every language feature you add (loops, branches, error handling) pulls you deeper.

**The untested assumption**: Users actually need branching in WarpFuture pipelines. The three completed examples (VecSearchFuture, FileTransformFuture, BatchSearchFuture) are all linear. BatchSearchFuture has a loop but implemented via manual state transitions. None required branching.

**Counter-argument**: Real-world GPU autonomy inherently involves branching. "Read config file, decide what to do" is the simplest autonomous pattern and requires branching.

**Verdict**: Skip proc macro branching. Document hand-written branching with a good example. Revisit only if multiple users request it.

### Challenge 3: Hostcall pipelining (Gap 3) has a hidden concurrency problem

**The assumption**: You can submit a hostcall and then do compute while waiting. But:

1. **Packet pool exhaustion**: If you submit request A and start computing, you might need to submit request B during compute. But the free pool might be empty (request A's packet hasn't been returned yet). With 8 packets per shard, you can have at most 8 concurrent in-flight requests per block. In practice, pipelining 2-3 requests is safe, but deeper pipelining risks exhaustion.

2. **Sideband buffer coherence**: If you submit a bulk_read via sideband and then start computing on previously-read sideband data, you need to ensure the previous data is fully read before the new bulk_read overwrites the sideband region. The bump allocator helps (different offsets), but `sideband_reset()` between operations would invalidate all previous offsets.

3. **Host-side ordering**: The host listener processes ready-stack packets in LIFO order (stack, not queue). If you submit A then B, B might be processed first. For independent operations this is fine, but for dependent operations (open → read) you must wait for open's response before submitting read.

**What could actually go wrong**: Submitting a `bulk_read` while a previous `bulk_write` is in flight to the same sideband region. The host processes the write (reading from sideband), while the GPU processes the read response (writing to sideband). If regions overlap, data corruption.

**Verdict**: Pipelining is safe for independent operations with separate sideband regions. It is unsafe when operations share sideband regions or have data dependencies. The documentation must make this clear. Don't present pipelining as a general optimization — it's a technique for specific situations.

### Challenge 4: Per-thread yield (Gap 4) — is "just use Embassy" actually viable at scale?

**The assumption**: For divergent async, use per-thread Embassy futures. But:

1. **Per-thread CAS contention**: Each thread does its own `hc_pop_free` CAS. With 32 threads per warp × N warps, contention on the free stack is 32x worse than WarpFuture. The whole point of WarpFuture was to reduce this.

2. **Embassy executor overhead on GPU**: The Embassy executor uses atomics for task scheduling. On CPU, these are fast. On GPU, `atom.cas.sys.global` is ~500ns for system-scope (mapped memory). Each poll of the executor involves multiple CAS operations. With 32 threads each doing this, the GPU spends most of its time on executor overhead.

3. **Has anyone tested Embassy with divergent per-thread I/O at scale?** The existing `async-pipeline-test` runs ONE future on ONE thread. It doesn't test 32 threads each with their own future doing independent I/O. This configuration might deadlock or perform terribly.

**What could go wrong**: 32 threads in a warp each trying to pop from the free stack simultaneously. The CAS loop means only one succeeds per attempt. With 8 packets in the pool, at most 8 of the 32 threads can be in-flight at once. The other 24 threads spin-wait on CAS. Then those 8 complete and the next 8 try. This serializes to ~4 rounds of CAS contention per warp — potentially hundreds of microseconds of pure overhead.

**Verdict**: Per-thread Embassy futures for divergent async are theoretically sound but unproven at warp scale. Before recommending this as the solution for Gap 4, someone should build a test: 32 threads in one warp, each doing independent hostcall I/O via Embassy. Measure contention, throughput, and total latency. If it's unusably slow, the per-block sharding helps (each block gets its own free stack), but intra-warp contention remains.

### Challenge 5: Is Gap 4 even a real problem?

**Question the premise**: When would you actually need 32 lanes doing different async operations? The WarpFuture model is "one warp, one task." If different lanes need different I/O, that suggests they should be different tasks (different warps).

**The SIMT model**: GPU programming means "same code, different data." If lane 3 needs file A and lane 7 needs file B, the program is not SIMT — it's MIMD. GPUs are not designed for MIMD at the thread level. Forcing MIMD into a warp is fighting the hardware.

**Counter-argument**: Data-dependent I/O is natural. "Each lane searches for its query in the database; some find a match, some don't; those that find matches need to fetch additional data." The lanes started with the same code but diverged based on data.

**Verdict**: Gap 4 is real but niche. Most GPU async workloads are uniform-path. The correct answer is "use multiple warps for multiple independent tasks, not multiple lanes within one warp." Document this clearly.

### Challenge 6: Could these 4 gaps be solved by abandoning WarpFuture entirely?

**Devil's advocate**: WarpFuture was invented to reduce CAS contention. But with per-block sharding (already implemented), contention is already low. Each block has its own free/ready stacks. A single warp per block does one CAS per hostcall — same as WarpFuture.

If you launch 1 warp per block and use per-thread Embassy futures:
- Each warp has 32 threads, each can do independent I/O
- Per-block sharding means only intra-block CAS contention
- With 1 warp per block, that's 32 threads contending — same as the worst case

**WarpFuture's real value**: It's not just CAS reduction. It's **code simplicity**. A 20-state linear pipeline is one match statement. 32 independent per-thread futures with an Embassy executor is 32 task spawns, a polling loop, shared state, and coordination logic. WarpFuture is simpler for the common case.

**Verdict**: WarpFuture stays. It's the right abstraction for uniform-path GPU async. The 4 gaps don't invalidate it — they define its boundaries.

## 3. Recommendations

### 3.1 Priority Ordering

| Priority | Gap | Action | Effort | Rationale |
|----------|-----|--------|--------|-----------|
| **1** | Gap 1 | Generalize `#[warp_async]` to all services | 3-5 days | This IS the product. Without it, users must hand-write 200+ line state machines. Highest bang-for-buck. |
| **2** | Gap 3 | Document pipelining pattern + example | 1 day | No code changes needed. The infrastructure supports it. Just prove it with an example. |
| **3** | Gap 2 | Document branching pattern + example | 1 day | Hand-written branching works today. Document and provide template. |
| **4** | Gap 4 | Document hybrid model (WarpFuture + Embassy) + test at scale | 2 days | Don't build new infrastructure. Test existing Embassy at 32-thread scale. Document the boundary. |

### 3.2 Concrete Task Changes

**New tasks**:

1. **`async-pipeline.1`** — Move `warp_hostcall_submit` and `warp_hostcall_wait_u64` from `gpu-kernel` (where they are local functions) to `gpu-runtime` (where generated macro code can reference them). Prerequisite for Gap 1.
   - Kind: experiment
   - Effort: 0.5 days
   - Dependencies: none

2. **`async-pipeline.2`** — Generalize `#[warp_async]` proc macro:
   - Add `warp_open!`, `warp_close!`, `warp_bulk_read!`, `warp_bulk_write!`, `warp_print!` (existing), `warp_write!`, `warp_read!`
   - Support `let` bindings for return values
   - Track variables as struct fields
   - Generate per-service payload fill/read logic
   - Kind: experiment
   - Effort: 3-5 days
   - Dependencies: async-pipeline.1

3. **`async-pipeline.3`** — Write example: branching pipeline (hand-written WarpFuture)
   - "If file exists (open succeeds), read and transform; else create with default data"
   - Demonstrates conditional state transitions
   - Kind: experiment
   - Effort: 1 day
   - Dependencies: async-pipeline.1

4. **`async-pipeline.4`** — Write example: pipelined I/O + compute (hand-written WarpFuture)
   - Submit bulk_read, compute on previous data while waiting, check response
   - Measure latency improvement vs sequential
   - Kind: experiment
   - Effort: 1 day
   - Dependencies: async-pipeline.1

5. **`async-pipeline.5`** — Test Embassy per-thread divergent I/O at warp scale
   - 32 threads in one warp, each doing independent hostcall print
   - Measure CAS contention and throughput
   - Kind: investigation
   - Effort: 1 day
   - Dependencies: none

**Skip/park decisions**:

- **Per-thread yield in WarpFuture (Gap 4 proper)**: PARK. Don't build sub-warp convergence. The complexity is not justified. The hybrid model (WarpFuture + Embassy) covers the use case.
- **Proc macro `warp_if!`**: PARK. Don't add branching to the macro. Hand-written branching is sufficient for the rare cases that need it.
- **Proc macro `warp_submit!/warp_await!`**: PARK. Don't add pipelining to the macro. Too complex for the expected benefit.

### 3.3 Minimal Viable Set to Close the EPIC

The EPIC can be declared "done" with:

1. **async-pipeline.1** (move helpers to gpu-runtime) — required
2. **async-pipeline.2** (generalized proc macro) — required, this is the headline feature
3. **async-pipeline.3** (branching example) — required for completeness
4. **async-pipeline.4** (pipelining example) — nice-to-have, can be deferred

That's 3 required tasks + 1 optional = 5-7 days of work.

**What "done" means**: A user can write:
```rust
#[warp_async]
unsafe fn my_gpu_pipeline(buf: *mut u8, sideband: *mut u8) -> bool {
    let fd = warp_open!(buf, b"input.dat", FILE_OPEN_READ);
    let n = warp_bulk_read!(buf, sideband, fd, 0, 4096);
    warp_close!(buf, fd);
    // ... compute on sideband data ...
    let fd2 = warp_open!(buf, b"output.dat", FILE_OPEN_WRITE_CREATE);
    warp_bulk_write!(buf, sideband, fd2, 0, n);
    warp_close!(buf, fd2);
    warp_print!(buf, b"Pipeline complete");
}
```

...and get a correct, hardware-verified GPU kernel. For branching and pipelining, they hand-write a WarpFuture following documented templates. For divergent per-lane async, they use Embassy futures.

## 4. Summary

The 4 gaps are not equally important:

1. **Gap 1 (macro generalization) is the only gap that matters for the product.** It is the difference between "research prototype" and "usable framework." Prioritize it above everything else.

2. **Gaps 2 and 3 (branching + pipelining) are solved by documentation**, not code. The infrastructure already supports both patterns via hand-written WarpFutures. Write examples, not features.

3. **Gap 4 (per-thread yield) is an anti-goal.** It fights the WarpFuture abstraction. The correct answer is the existing hybrid model (WarpFuture for uniform I/O, Embassy for divergent async). Document the boundary, don't try to erase it.

**Total estimated effort to close the EPIC**: 6-9 days.
**Critical path**: async-pipeline.1 → async-pipeline.2 (4-6 days).
