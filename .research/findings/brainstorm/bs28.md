## Consensus Points

Both agents agree on:

1. **Start with proc macro (Option C)**: Extend `#[warp_async]` to support `if`/`loop`/`match` with `warp_*!()` calls. No compiler fork needed. 2-3 weeks effort. Builds on existing 700-line macro.

2. **Rustc fork is high-risk**: 30-60 min build times, MIR internals change frequently, maintenance burden is real, nvptx64 LLVM backend barely maintained, bus factor = 1.

3. **Warp-uniform invariant is fundamental**: All branches containing `.await` must be warp-uniform (lane 0 decides, broadcasts). Per-lane branching to `.await` is forbidden. This is inherent to the SIMT model, not a limitation of any implementation approach.

4. **Distribution matters**: Proc macro = `cargo` dependency (zero friction). Rustc fork = custom toolchain install (adoption killer).

## Unresolved Disputes

### 1. Should `rustc-warp` be parked or rejected?

- **Proposer**: Park it as Phase 2, activate on proc macro limitations.
- **Skeptic**: Reject outright — the trigger conditions are imaginary, the fork will never be needed.
- **Resolution**: **Park it.** The user explicitly asked about rustc modifications, so documenting the path is valuable even if it's never taken. But set a high bar for activation: concrete evidence that proc macro CFG builder fails on a real workload, not speculative concerns.

### 2. LLVM pass vs MIR pass (if compiler approach ever needed)

- **Proposer**: MIR pass is cleaner (more semantic information).
- **Skeptic**: LLVM pass is more stable (recognizes switch-on-discriminant pattern, doesn't depend on rustc internals).
- **Resolution**: **Both are valid.** If we ever reach Phase 2, investigate both. The LLVM pass argument is strong — LLVM IR is more stable than rustc MIR, and the switch pattern is machine-recognizable.

### 3. Broadcast cost for saved locals

- **Skeptic raises a real concern**: Hand-written WarpFuture broadcasts only what's needed (discriminant + select values). Compiler-generated code would naively broadcast ALL saved-across-yield locals, which can be expensive (14 shuffles for a 56-byte path string).
- **Resolution**: This is a strong argument for the proc macro approach, which can selectively generate broadcasts (since the macro author controls what gets broadcast). A compiler pass would need optimization to avoid broadcasting large locals that could instead be re-read from shared memory.

### 4. Drop semantics, panics, nested async

- **Skeptic identifies real gaps** in the proposer's design: Who runs Drop in warp context? What happens if lane 0 panics? How do nested `#[warp_async]` functions compose?
- **Resolution**: These are genuine complexity that applies to ALL approaches (proc macro, MIR pass, LLVM pass). For the proc macro approach, the answer is simpler: `#[warp_async]` functions don't support arbitrary Drop types in cross-yield positions — restrict to POD types (u32, u64, etc.). Panics trap all lanes. Nested calls inline the inner state machine.

## Decisions

### Epic Definition

**Epic: `warp-control-flow`** — Warp-cooperative async with full control flow

**Goal**: `#[warp_async]` supports `if`/`loop`/`match` containing `warp_*!()` calls, generating correct warp-cooperative state machines.

**Success criteria**:
1. `if`/`else` with `warp_*!()` in arms — compiles and runs on GPU
2. `loop` with `warp_*!()` and `break` — compiles and runs on GPU
3. `match` with `warp_*!()` in arms — compiles and runs on GPU
4. Nested control flow (if inside loop) — works correctly
5. All generated code maintains warp convergence (32 lanes agree on state)

**Note**: This is the user-defined epic. Only the user can close it. The approach (proc macro vs compiler fork) is a tactical decision.

### Theme: `warp-cfg` (active)

Extend `#[warp_async]` proc macro to support control flow.

| Task | Kind | Depends | Description |
|------|------|---------|-------------|
| `warp-cfg.1` | design | — | Design CFG-based state machine generation: how to parse `if`/`loop`/`match` at token level, assign states to a DAG, handle variable scoping, generate broadcast-based branch decisions. Produce examples of generated code for each construct. |
| `warp-cfg.2` | experiment | warp-cfg.1 | Implement `if`/`else` support: parse `if` blocks containing `warp_*!()`, generate forked state ranges with lane-0 broadcast decisions, merge states. Hardware test with "if file exists" branching pipeline. |
| `warp-cfg.3` | experiment | warp-cfg.2 | Implement `loop`/`break` support: parse loop bodies with `warp_*!()`, generate cycle-back transitions, handle `break`. Hardware test with "read until done" pipeline. |
| `warp-cfg.4` | experiment | warp-cfg.2 | Implement `match` support: parse match arms with `warp_*!()`, broadcast discriminant, generate per-arm state ranges. Hardware test with "dispatch command" pipeline. |
| `warp-cfg.5` | experiment | warp-cfg.3, warp-cfg.4 | Nested control flow stress test: `if` inside `loop` with `match`, all containing `warp_*!()`. Verify state correctness and warp convergence on GPU. |

**Activation trigger** (ALL must be true):
- A concrete workload exists that requires control flow the proc macro cannot express
- The limitation is fundamental (not fixable by extending the macro)
- The effort to fork rustc is justified by the number of affected use cases

### Project Organization (for proc macro phase)

No changes needed — `warp-macro` crate already exists. CI already checks it.

### Project Organization (if rustc fork ever activates)

- Separate repo: `github.com/DaLaw2/warp-rustc`
- Pre-built binaries via GitHub Releases
- CI: cache rustc build, only rebuild on fork changes
- `rust-toolchain.toml` would point to custom toolchain
- Consider LLVM pass approach as alternative to MIR pass (more stable API)
