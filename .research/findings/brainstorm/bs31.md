## 2. Technical Analysis

### 2.1 Tensor Core Access: Can Rust asm!() emit WMMA on nvptx64?

**Assessment: Likely feasible, but with significant register constraints.**

The existing `gpu-atomics` crate proves that `core::arch::asm!()` with inline PTX works on nvptx64. The register classes available are `reg32` (32-bit) and `reg64` (64-bit). The WMMA instructions require a different story:

**WMMA instruction set (SM70+)**:
```ptx
wmma.load.a.sync.aligned.m16n16k16.shared.row.f16 {%r0, ..., %r7}, [addr], stride;
wmma.mma.sync.aligned.m16n16k16.row.col.f32.f16.f16.f32
    {%r0, ..., %r7}, {%r8, ..., %r15}, {%r16, ..., %r23}, {%r24, ..., %r31};
wmma.store.d.sync.aligned.m16n16k16.shared.row.f32 {%r0, ..., %r7}, [addr], stride;
```

**The critical question is register operands.** WMMA fragments are represented as groups of 8 registers. In CUDA C, these are opaque `nvcuda::wmma::fragment` types. In PTX, they are explicit register lists. Rust's inline asm on nvptx64 supports `reg32` and `reg64` — these map to individual PTX registers. To emit WMMA, we need to:

1. Declare 8+ output registers (for each fragment)
2. Pass them as a brace-enclosed list to the WMMA instruction
3. Use string formatting to construct the register list in the asm template

**Feasibility concern**: Rust's `asm!()` doesn't have a native way to express "a group of 8 registers." We would need to declare 8 separate `reg32` operands and manually format them into the PTX brace syntax:
```rust
core::arch::asm!(
    "wmma.mma.sync.aligned.m16n16k16.row.col.f32.f16.f16.f32
        {{{d0}, {d1}, {d2}, {d3}, {d4}, {d5}, {d6}, {d7}}},
        {{{a0}, {a1}, {a2}, {a3}, {a4}, {a5}, {a6}, {a7}}},
        {{{b0}, {b1}, {b2}, {b3}, {b4}, {b5}, {b6}, {b7}}},
        {{{c0}, {c1}, {c2}, {c3}, {c4}, {c5}, {c6}, {c7}}};",
    d0 = out(reg32) d[0], d1 = out(reg32) d[1], // ... 32 operands total
    a0 = in(reg32) a[0], // ...
    // etc.
);
```

This is ugly but should work — the PTX assembler doesn't care how the registers were named, only that the syntax is correct. **The risk is that LLVM's register allocator may not handle 32+ simultaneous register operands gracefully on nvptx64.** This needs an experiment.

**Alternative: MMA instructions (SM80+, more efficient)**:
The newer `mma.sync.aligned.m16n8k16` instructions use fewer registers (4 per fragment instead of 8) and are what cuBLAS actually uses. These are better targets for Rust inline PTX. The RTX 3090 (SM86) supports these.

**Verdict**: Tensor Core access from Rust is *probably* feasible via inline PTX asm with many register operands. The MMA instructions (SM80+) are a better fit than WMMA due to smaller fragment sizes. This MUST be validated experimentally before building anything on top of it.

### 2.2 Shared Memory: Can Rust allocate .shared on nvptx64?

**Assessment: Feasible with inline PTX, but limited.**

In CUDA C, shared memory is declared as `__shared__ float tile[256]`. In PTX, this becomes:
```ptx
.shared .align 4 .f32 tile[256];
```

From Rust, there are two approaches:

**Approach A — Static shared memory via module-level asm**:
```rust
core::arch::global_asm!(".shared .align 16 .b8 smem_tile[4096];");
```
Then reference `smem_tile` from inline asm blocks. This is how static shared memory works in PTX — it's a module-level declaration. The question is whether `global_asm!()` on nvptx64 correctly emits `.shared` directives. This is untested.

**Approach B — Dynamic shared memory via kernel parameter**:
CUDA supports extern shared memory (`extern __shared__ float smem[]`) where the size is set at kernel launch time. In PTX, this is declared as `.extern .shared .align 4 .b8 dynamic_smem[];` and the kernel launch specifies the size as the third parameter to `<<<blocks, threads, smem_bytes>>>`. cudarc's `LaunchConfig` supports `shared_mem_bytes`. The GPU kernel accesses it via a pointer.

**Approach B is more practical** — the host decides the shared memory size, and the kernel receives a base pointer. The GPU code can then use typed pointer arithmetic within the shared memory region. No special Rust declarations needed — just pointer math on the address provided by the hardware.

**Risk**: The address space qualifier matters. Shared memory lives in address space 3 in LLVM's NVPTX backend. A raw pointer obtained from `%dynamic_smem` needs to be in the `.shared` address space for loads/stores to hit shared memory (not global memory). From inline PTX, we can explicitly use `ld.shared` and `st.shared` instructions, which forces the shared memory path regardless of the pointer's LLVM address space.

**Verdict**: Dynamic shared memory via kernel launch parameter + explicit `ld.shared`/`st.shared` inline PTX is the practical path. This needs an experiment to verify the full round-trip: host sets shared_mem_bytes in launch config, kernel reads/writes via inline PTX shared loads/stores.

### 2.3 CPU Assumptions That Break at Scale

Several assumptions in the current stack become problematic for compute-heavy kernels:

1. **Sideband buffer size (1 MB)**: For inference, model weights are 1-70+ GB. The 1 MB sideband is irrelevant — weights must be pre-loaded into global memory by the host before kernel launch. The sideband remains useful for small I/O (configs, prompts, responses).

2. **Single-kernel architecture**: The current model is one persistent kernel. For compute-heavy workloads, the kernel needs much more VRAM (for weights, KV cache, activations). The host must pre-allocate this via `cuMemAlloc` and pass pointers as kernel parameters. This is a straightforward extension but changes the launch protocol.

3. **Register pressure**: Current WarpFuture state machines use ~40-60 registers. A GEMM kernel with WMMA fragments needs 32+ registers just for the matrix fragments, plus control flow registers. Combined with a WarpFuture state machine, this could exceed 128 registers per thread, dropping occupancy to 25% or lower. The question is whether reduced occupancy matters for compute-bound kernels (it may not — compute-bound kernels are less sensitive to occupancy than memory-bound ones).

4. **Warp-level vs block-level coordination**: Current WarpFuture operates at warp level (32 lanes). GEMM requires block-level coordination — multiple warps collaborating to compute tiles of the output matrix. The WarpFuture model doesn't address inter-warp synchronization within a block. A `__syncthreads()` equivalent (`bar.sync`) would be needed.

## 3. Skeptic Challenges

### Challenge 1: Is GPU-autonomous inference realistic, or a research dead-end?

**The honest assessment**: Every production inference engine (TensorRT-LLM, vLLM, SGLang) is host-orchestrated. The host decides what to compute; the GPU does the math. The reason is not laziness — it's that the host has:
- A scheduler with full visibility into all pending requests
- Access to tokenizer libraries (Rust/Python, not GPU-friendly)
- Simple debugging and profiling tools
- Ability to handle errors gracefully (OOM, timeout, bad input)

The GPU-autonomous model moves ALL of this onto the GPU, where debugging is hard, error handling is limited, and the programming model is constrained. The potential benefit (zero kernel launch overhead, no CPU-GPU sync between layers) is real but may not justify the engineering cost.

**Counter-argument**: The async_gpu stack already demonstrated GPU-autonomous I/O orchestration. The GPU reads a file, makes a decision, writes output — all without host involvement. This IS valuable for edge computing, embedded GPU systems, and scenarios where the host CPU is a bottleneck. The question is whether scaling from I/O to compute is a natural extension or a category error.

**Verdict**: GPU-autonomous inference is a legitimate long-term research goal but should NOT be the near-term priority. The project should instead:
1. Validate the compute primitives (WMMA, shared memory) as independent capabilities
2. Build a small but complete compute example (e.g., small matrix multiply)
3. Only then assess whether a full inference pipeline is viable

### Challenge 2: Register pressure with WMMA + WarpFuture

A WarpFuture state machine for a transformer layer would need:
- 8 registers per WMMA fragment × 4 fragments (A, B, C, D) = 32 registers for matrix ops
- State machine fields (state, fd, pkt_idx, etc.) = 10-20 registers
- Loop counters, pointers, temporaries = 10-20 registers
- Total: 60-70+ registers per thread

With 64K registers per SM (RTX 3090), 70 registers/thread allows 64K/70 ≈ 914 threads = 28 warps per SM. The RTX 3090 supports 48 warps/SM, so occupancy drops to ~58%. For compute-bound kernels this is acceptable, but if memory-bound operations (weight loading) are involved, low occupancy could hurt.

**The real concern is that WarpFuture adds overhead on top of compute.** A pure CUDA GEMM kernel uses all registers for matrix fragments and loop variables. A WarpFuture wrapping a GEMM adds state machine bookkeeping. This may not be the right abstraction for pure compute — WarpFuture shines for I/O coordination, not for arithmetic.

**Verdict**: Consider separating the concerns — WarpFuture for I/O orchestration (load weights, save results), direct kernel functions for compute (GEMM, softmax). The WarpFuture calls into compute functions as "compute states" per ADR-10, but the compute functions themselves are regular GPU code without async overhead.

### Challenge 3: What assumptions are untested?

| Assumption | Status | Risk |
|-----------|--------|------|
| `asm!()` can emit WMMA/MMA instructions | **UNTESTED** | High — if register lists don't work, inference path is blocked |
| `global_asm!()` can declare .shared memory | **UNTESTED** | Medium — workaround exists (dynamic shared memory via launch config) |
| Dynamic shared memory accessible via inline PTX ld.shared/st.shared | **UNTESTED** | Medium — critical for tiled algorithms |
| WMMA fragments fit in Rust's register allocator | **UNTESTED** | High — 32 simultaneous reg32 operands in one asm block is unprecedented |
| Block-level `bar.sync` works from Rust inline PTX | **UNTESTED** | Low — simple single instruction, similar to existing membar.sys |
| Multiple warps can coordinate via shared memory atomics | **UNTESTED** | Medium — needed for multi-warp GEMM tile distribution |
| Host can pre-allocate multi-GB buffers and pass to persistent kernel | **UNTESTED** | Low — cudarc supports cuMemAlloc, just needs integration |

**The two highest-risk untested assumptions are WMMA register handling and shared memory access.** These should be the immediate next experiments.

### Challenge 4: Should the project focus on I/O pipelines instead?

GPU-autonomous I/O orchestration is already proven and differentiated:
- No other Rust framework offers `#[warp_async]` for GPU-driven file pipelines
- The hostcall + WarpFuture model is unique
- Edge computing, GPU-driven ETL, and sensor processing are practical use cases

GPU-autonomous inference is competing with TensorRT-LLM, vLLM, and SGLang — mature engines backed by large teams. Even if async_gpu achieves Tensor Core access, it would be a toy compared to these engines.

**Counter-argument**: The goal is research reproduction of VectorWare's claims, not production competition. Demonstrating that Rust async on GPU CAN do inference — even a single transformer layer — is scientifically valuable regardless of production viability.

**Verdict**: Pursue the compute primitives (WMMA, shared memory) as capability demonstrations, not as a production inference engine. Frame the gpu-autonomous epic as "prove it's possible" rather than "build a competitive system."

### 4.2 New Tasks for gpu-compute Theme

Priority ordering:

**P0 — gpu-compute.3: Tensor Core feasibility via inline PTX (DECISION GATE)**
- Kind: experiment
- Epic: gpu-autonomous
- Description: Write a minimal kernel that performs a 16x16x16 FP16 matrix multiply using `mma.sync.aligned.m16n8k16` via inline PTX `asm!()`. Verify correct output. Measure register usage.
- Research questions:
  1. Can `asm!()` with 32+ `reg32` operands compile on nvptx64?
  2. Does MMA produce correct results (compare with CPU reference)?
  3. What is the register count for a single MMA operation?
  4. DECISION: If MMA via inline PTX fails, GPU-autonomous inference is not viable with this stack.
- Dependencies: none
- Effort: 2-3 days
- Risk: HIGH — this is the single biggest unknown. If it fails, the inference path is closed.

**P1 — gpu-compute.4: Shared memory access from Rust (DECISION GATE)**
- Kind: experiment
- Epic: gpu-autonomous
- Description: Allocate dynamic shared memory via kernel launch config. Read/write it from inline PTX (`ld.shared`/`st.shared`). Verify data survives a round-trip through shared memory. Test `bar.sync` for inter-warp synchronization within a block.
- Research questions:
  1. Does cudarc's LaunchConfig support shared_mem_bytes?
  2. Can inline PTX `ld.shared`/`st.shared` access the dynamic shared memory region?
  3. Does `bar.sync 0;` correctly synchronize all threads in a block?
  4. Can multiple warps share data via shared memory (write from warp 0, read from warp 1)?
- Dependencies: none (parallel with gpu-compute.3)
- Effort: 1-2 days
- Risk: MEDIUM — workaround exists even if dynamic approach fails (explicit address computation).

**P2 — gpu-compute.5: Tiled GEMM combining Tensor Cores + shared memory**
- Kind: experiment
- Epic: gpu-autonomous
- Description: Implement a basic tiled matrix multiply: load tiles from global to shared memory, compute via MMA, store back. Single block, 4-8 warps.
- Dependencies: gpu-compute.3 (MMA works), gpu-compute.4 (shared memory works)
- Effort: 3-5 days
- Risk: MEDIUM — integration risk, register pressure risk

**P3 — gpu-compute.6: Element-wise GPU compute kernels (softmax, RoPE, LayerNorm)**
- Kind: experiment
- Epic: gpu-autonomous
- Description: Implement softmax, RoPE, and LayerNorm as pure Rust GPU functions (no Tensor Cores needed — these are element-wise ops). Use shared memory for reduction (softmax denominator). Test with known inputs.
- Dependencies: gpu-compute.4 (shared memory for reductions)
- Effort: 2-3 days
- Risk: LOW — standard parallel algorithms, well-understood

### 4.5 Decision Gate After gpu-compute.3 + gpu-compute.4

After these two experiments complete, one of three outcomes:

**Outcome A — Both succeed**: Proceed to gpu-compute.5 (tiled GEMM). The inference path remains open. The gpu-autonomous epic is viable.

**Outcome B — MMA fails, shared memory works**: GPU-autonomous inference is NOT viable with the current Rust nvptx64 stack. Pivot the gpu-autonomous epic to "GPU-autonomous data processing" — the GPU drives complex multi-step data pipelines using I/O + element-wise compute (no Tensor Cores). This is still valuable and differentiated. Softmax, reductions, sorting, and filtering are all feasible without MMA.

**Outcome C — Both fail**: The gpu-autonomous epic should be parked. The project is already product-ready for its current scope (Rust std + async/await on GPU for I/O orchestration). Focus on ecosystem (more examples, documentation, community).

## 5. Summary

The project has reached a natural inflection point. The original VectorWare reproduction goal is achieved — Rust std and async/await work on GPU with a robust hostcall protocol, warp-cooperative state machines, and production-quality CI/documentation. The product-ready epic should be marked completed.

The next frontier (gpu-autonomous compute) hinges on two untested hardware capabilities: Tensor Core MMA instructions and shared memory access, both via inline PTX from Rust. These are the highest-priority experiments. Their results determine whether GPU-autonomous inference is a viable research direction or whether the project should consolidate around its proven strength: GPU-autonomous I/O orchestration.

The recommended batch is gpu-compute.3 + gpu-compute.4 (parallel execution), followed by a decision gate.
