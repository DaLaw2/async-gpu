# BS35 — Native GPU Inference: Epic Feasibility Analysis

**Date**: 2026-03-13
**Trigger**: User evaluating "Native GPU Inference" as a potential new epic
**Level**: Deep (comprehensive multi-perspective analysis)

---

## Executive Summary

"Native GPU Inference" would mean running a transformer forward pass entirely on the GPU using only Rust async/await and inline PTX — no CUDA runtime, no cuBLAS, no cuDNN, no Python. The project has individually verified every primitive needed (MMA, multi-tile GEMM, softmax, shared memory, hostcall I/O, WarpFuture). The question is whether assembling them into an actual inference pipeline yields sufficient research and narrative value to justify the engineering effort, which ranges from ~1 week (minimal PoC) to ~2 months (real model with text generation).

---

## What "Native GPU Inference" Could Mean — Scope Options

### Option A: Minimal PoC (single attention head, tiny dimensions)

**What**: Implement Q×K^T → softmax → attn×V for a single attention head with synthetic weights. Dimensions: d_model=64, seq_len=16, 1 head. No real model weights, no tokenizer, no sampling.

**Effort**: 1-2 weeks

**Research value**: Low-medium. Proves compose-ability of existing primitives into the attention pattern. The individual pieces are already verified — this is integration work, not new research. The GEMM→softmax pipeline (gpu-pipeline.3) already demonstrates the core pattern.

**Narrative value**: Medium. "We computed self-attention on GPU using only Rust and inline PTX" is a meaningful milestone, but without real weights or text output, it's still a proof-of-concept.

**Technical risk**: Low. All required primitives are proven. The main risk is scaling GEMM to 64×64 matrices (current largest verified: 16×32 × 32×8), which requires block-level tiling (multiple warps computing different output tiles). This is a known algorithm but has not been implemented.

**Key deliverables**:
- Multi-warp block-tiled GEMM for arbitrary M×K × K×N
- Single-head attention kernel: Q×K^T → scale → softmax → attn×V
- Correctness verification against CPU reference

### Option B: Single Transformer Layer (realistic dimensions, single layer)

**What**: Implement a complete transformer layer: multi-head attention + FFN (two linear layers + activation). Realistic dimensions: d_model=768, n_heads=12, d_head=64, d_ffn=3072. Load real weights from a pretrained model (e.g., first layer of GPT-2 small). Verify output matches PyTorch/HuggingFace reference.

**Effort**: 3-5 weeks

**Research value**: Medium. Exercises several unproven capabilities:
- Multi-head attention with head-parallel execution
- LayerNorm (new reduction kernel)
- GELU activation (new SFU-based kernel)
- Weight loading via hostcall bulk transfer (1MB sideband, weights ~7MB per layer for GPT-2)
- Memory management for intermediate activations (~400KB per layer)
- Numerical accuracy at realistic scale

**Narrative value**: High. "We ran a GPT-2 layer on GPU using only Rust" is compelling. Verifiable against PyTorch makes the claim credible.

**Technical risk**: Medium-high.
- **GEMM scaling**: 768×768 matrix multiply requires block-level tiling with multiple CTAs. Current implementation is single-warp. This is a substantial engineering effort.
- **Weight loading**: GPT-2 small layer 0 weights total ~7MB. With 1MB sideband buffer, need 7 transfers per layer. Round-trip ~20µs each = ~140µs overhead. Acceptable but needs implementation.
- **Numerical accuracy**: f16 MMA with f32 accumulation should be sufficient for a forward pass, but edge cases (large activations, LayerNorm stability) could cause divergence from the reference.
- **Memory management**: Intermediate tensors (Q, K, V, attn_weights, FFN intermediates) total ~400KB for GPT-2 dimensions. Must fit in GPU memory allocated via cuMemAlloc. No dynamic allocator on GPU — need pre-allocated buffer with offset management.

### Option C: Full Model Inference (multiple layers, real weights, text generation)

**What**: Run a complete small model (GPT-2 small, 12 layers, 117M params) end-to-end: tokenize on host → transfer tokens → GPU runs all 12 layers → transfer logits → sample on host → repeat for autoregressive generation. Produce coherent text.

**Effort**: 6-10 weeks

**Research value**: Medium. The research insight per unit effort diminishes sharply after the first layer. Layer 2-12 are identical to layer 1 (same code, different weights). The new challenges are:
- KV cache management (grows with sequence length)
- Weight streaming (117M params × 2 bytes = ~234MB, far exceeding GPU memory in current architecture)
- Autoregressive loop coordination between GPU and host
- Tokenizer integration (keep on host, trivial)
- Sampling (argmax/top-p — reduction kernel, similar to softmax)

**Narrative value**: Very high. "We ran GPT-2 and generated coherent text using only Rust async/await on GPU" is a headline result. This would be the most compelling demonstration of the entire project.

**Technical risk**: High.
- **Weight storage**: 234MB of weights cannot fit in GPU memory in the current architecture. Options: (a) stream weights per layer via hostcall (234MB / 12 layers = ~20MB per layer, 20 sideband transfers per layer at 1MB each), (b) increase sideband buffer, (c) use cuMemAlloc for a large weight buffer and pass pointer to kernel. Option (c) is most practical but requires host-side changes.
- **KV cache**: Grows as O(n_layers × seq_len × d_model). For GPT-2 with seq_len=128: 12 × 128 × 768 × 2 × 2 (K+V) = ~4.7MB. Manageable but needs pre-allocation and index management.
- **Performance**: Without optimized GEMM (no double-buffering, no warp specialization, no vectorized loads), inference will be very slow — possibly 100-1000x slower than cuBLAS. A single token could take seconds. This is acceptable for a PoC but may make iterative debugging painful.
- **Numerical divergence**: 12 layers of f16 MMA with f32 accumulation may accumulate enough error to produce garbage text. Would need careful validation layer-by-layer.

## Technical Gap Analysis

### Gap 1: Block-level Tiled GEMM (multiple warps, large matrices)

**What's missing**: Current GEMM operates on a single warp (32 threads) computing a 16×8 output tile. Real inference needs matrices of size 768×768 (GPT-2) or larger. This requires: (a) multiple warps per block, each computing a different output tile, (b) multiple blocks for very large matrices, (c) output tile writeback coordination.

**Difficulty**: Moderate. The algorithm is well-documented (CUTLASS tutorials, GPU GEMM optimization guides). The building blocks (MMA, shared memory, bar.sync) are all proven. The implementation is ~200-400 lines of PTX-heavy Rust.

**Reuses existing primitives**: Yes — MMA, shared memory tiling, bar.sync, multi-tile K-accumulation loop (gpu-pipeline.2).

**Specific sub-tasks**:
1. Multi-warp output tiling: each warp computes a 16×8 tile, 4 warps cover 16×32
2. Thread-block tile assignment: blockIdx maps to output region
3. Shared memory sizing: A tile + B tile per K-iteration, scaled for block size
4. Global memory coalescing for tile loads

### Gap 2: LayerNorm / RMSNorm

**What's missing**: Reduction to compute mean and variance across the feature dimension, then per-element normalization. Same pattern as softmax but with two reduction passes (sum for mean, sum-of-squares for variance).

**Difficulty**: Trivial. The softmax kernel (gpu-compute.6) already implements shared-memory tree reduction with bar.sync. LayerNorm is the same pattern with different arithmetic. RMSNorm is even simpler (no mean subtraction, only root-mean-square).

**Reuses existing primitives**: Directly. Shared memory reduction, bar.sync, per-element arithmetic.

### Gap 3: GELU / SiLU Activation Functions

**What's missing**: GELU(x) = x × Φ(x) where Φ is the CDF of standard normal. Approximation: GELU(x) ≈ 0.5x(1 + tanh(sqrt(2/π)(x + 0.044715x³))). SiLU(x) = x × sigmoid(x).

**Difficulty**: Trivial. Both reduce to element-wise arithmetic using `ex2.approx.f32` (already proven) and basic multiply/add. No reduction, no shared memory needed. The tanh approximation can use `ex2.approx.f32` via tanh(x) = (e^2x - 1)/(e^2x + 1).

**Reuses existing primitives**: `ex2.approx.f32`, per-thread computation.

### Gap 4: RoPE (Rotary Positional Encoding)

**What's missing**: Per-element operation: rotate pairs of dimensions by position-dependent angles. For each pair (x_{2i}, x_{2i+1}) at position p: apply rotation by angle p × θ_i where θ_i = 10000^(-2i/d).

**Difficulty**: Trivial. Pure element-wise computation. Needs sin/cos which can be approximated via `sin.approx.f32` and `cos.approx.f32` PTX instructions (both exist on SM86).

**Reuses existing primitives**: Per-thread computation, SFU instructions.

### Gap 5: Multi-head Attention Coordination

**What's missing**: Running n_heads (e.g., 12) attention computations in parallel. Each head: Q_h×K_h^T → scale → softmax → attn_h×V_h. Then concatenate and project.

**Difficulty**: Moderate. Two approaches:
- **Sequential**: One head at a time in a loop. Simple but slow. Works within existing single-block architecture.
- **Parallel**: Different thread blocks compute different heads. Requires multi-block kernel launch (already proven with up to 512 threads). Coordination for the output concatenation needs shared memory or global memory staging.

**Reuses existing primitives**: GEMM, softmax, multi-block execution (proven in multi-warp-test crate).

### Gap 6: Weight Loading from Host

**What's missing**: Loading model weights from host memory (file or pre-loaded) into GPU-accessible memory. Two sub-problems: (a) getting weights to GPU memory, (b) accessing them from the kernel.

**Difficulty**: Trivial for small models, moderate for large models.
- **Small models (< sideband buffer)**: Use existing `SERVICE_BULK_READ` hostcall. Already proven.
- **Large models (> 1MB)**: Either increase sideband buffer (host-side config change) or pre-allocate via `cuMemAlloc` and pass pointer as kernel argument. The latter is cleaner and avoids hostcall overhead entirely.

**Reuses existing primitives**: Hostcall bulk read (proven), or cuMemAlloc (host-side only, trivial CUDA driver API).

### Gap 7: KV Cache Management

**What's missing**: For autoregressive generation (Option C only), need to cache K and V tensors from previous positions. Requires: pre-allocated buffer, position-indexed write, efficient read of the growing cache.

**Difficulty**: Moderate. The cache is a simple 2D array indexed by (layer, position). No complex data structure. But sizing and lifetime management need design — the buffer grows with sequence length and must persist across token generation steps (which means across kernel launches, or within a single long-running kernel).

**Reuses existing primitives**: Global memory access (proven), kernel arguments for buffer pointers.

### Gap 8: Sampling (argmax / top-p / top-k)

**What's missing**: Selecting the next token from logits. Argmax is a simple reduction (same as softmax max-finding). Top-p/top-k requires sorting, which is more complex on GPU.

**Difficulty**: Trivial for argmax (same reduction pattern as softmax). Moderate for top-p/top-k (sorting on GPU is well-studied but non-trivial in inline PTX).

**Reuses existing primitives**: Shared memory reduction (for argmax).

### Gap 9: Scaling GEMM Performance

**What's missing**: The current GEMM has no performance optimizations: no double-buffered shared memory, no `ldmatrix.sync.aligned`, no vectorized global loads (`ld.global.v4`), no software pipelining. For 768×768 GEMM, this will be extremely slow.

**Difficulty**: Hard (for competitive performance), trivial (for correctness-only). If the goal is "it works, not fast," skip all optimizations. If the goal is "usable for iterative debugging," need at least `ldmatrix` and vectorized loads to bring runtime from minutes to seconds.

**Reuses existing primitives**: MMA (proven), but needs new PTX instructions (`ldmatrix`, `cp.async`).

### Gap 10: Numerical Precision at Scale

**What's missing**: All current tests use uniform or small matrices. Real model weights have diverse magnitudes. f16 input precision + f32 accumulation is standard practice (even cuBLAS uses this), but the custom GEMM kernel lacks numerical stabilization (e.g., Kahan summation) and has not been tested with realistic value distributions.

**Difficulty**: Low risk. f16 compute with f32 accumulation is the standard for inference. If numerical issues arise, they are likely bugs in the implementation (wrong index mapping) rather than fundamental limitations.

## Skeptic Challenges

### Challenge 1: "You're building a worse cuBLAS — why?"

The entire GEMM stack (block tiling, shared memory management, fragment mapping, vectorized loads) is replicating what NVIDIA has spent years optimizing in cuBLAS/CUTLASS. The Rust implementation will be 100-1000x slower than cuBLAS for large matrices. The research value of "we wrote a slow GEMM in Rust PTX" is minimal — everyone knows you CAN write a GEMM in PTX; the hard part is making it fast.

**Counter**: The goal is not to compete with cuBLAS. It is to demonstrate that Rust's async/await model can orchestrate GPU inference autonomously — the GPU kernel decides when to load weights, compute, and produce output, using WarpFuture for I/O and plain functions for compute. No host-side framework (PyTorch, TensorRT) is involved. The GEMM is a means to an end, not the end itself. Performance does not need to be competitive; it needs to be correct and demonstrate the autonomy thesis.

**Verdict**: Valid concern about effort-to-insight ratio. Mitigate by keeping GEMM implementation minimal (correctness only, no optimization) and focusing on the orchestration story.

### Challenge 2: "The sideband buffer bottleneck makes real inference impractical"

Loading GPT-2 small weights (234MB) through a 1MB sideband buffer requires 234 transfers at ~20µs each = ~4.7ms just for I/O overhead, plus the actual data transfer time. For per-token inference, this means weights must either be cached in GPU memory (requiring ~234MB allocation, which is fine on RTX 3090 with 24GB) or re-streamed each token (impractical).

The practical solution (pre-allocate 234MB via cuMemAlloc, pass pointer) bypasses the hostcall protocol entirely, which undermines the "GPU autonomy" narrative. The GPU becomes dependent on the host to pre-stage weights.

**Counter**: Weight pre-staging is how every GPU inference system works — cuBLAS, TensorRT, PyTorch all pre-allocate weight buffers on device. The autonomy claim is about compute orchestration (which layer runs when, how data flows between layers), not about weight provisioning. The GPU is autonomous in the same way a CPU program is autonomous even though the OS loaded its code into memory. Furthermore, per-layer weight streaming via hostcall IS a valid alternative for smaller models — the GPU requests weights when it needs them, which is genuinely autonomous.

**Verdict**: Fair point. The architecture should support both pre-staged weights (for performance) and hostcall-streamed weights (for autonomy demonstration). The demo can use pre-staged weights with a note that streaming is also possible.

### Challenge 3: "Diminishing returns — the thesis is already proven"

The project has already demonstrated:
1. Rust std on GPU (Vec, String, format!, file I/O)
2. Async/await on GPU (Embassy, WarpFuture, #[warp_async] proc macro)
3. GPU autonomous compute (GEMM, softmax, GEMM→softmax pipeline)

What does "GPU runs a transformer layer" add to the thesis? The abstraction boundary is already validated. Going from "GEMM + softmax works" to "attention + FFN works" is just more of the same — more GEMMs, more element-wise ops, more shared memory reductions. The pattern is established.

**Counter**: There is a qualitative difference between "each primitive works in isolation" and "a real ML workload runs end-to-end." Integration reveals unforeseen issues: memory management between layers, numerical stability across many operations, register pressure when all components are combined, and scheduling decisions (which warp does what). These integration challenges are where the real engineering complexity lives, and they have NOT been tested.

More importantly, the narrative impact is substantial. "We ran GPT-2 on GPU using only Rust" is a result that people remember. "We proved each primitive works" is a result that experts appreciate but nobody else cares about.

**Verdict**: The strongest argument for proceeding is narrative, not technical. If the project aims to influence the Rust+GPU ecosystem (demonstrate that the approach is viable), a concrete inference demo is far more compelling than a collection of passing unit tests.

### Challenge 4: "Single-warp GEMM does not generalize"

All current GEMM work uses a single warp (32 threads). Real inference requires multi-warp, multi-block GEMM. The jump from 1 warp to 128+ threads per block introduces new synchronization complexity: bar.sync across multiple warps, shared memory bank conflicts, warp scheduling effects on occupancy. None of this has been tested.

**Counter**: Multi-block execution IS proven (multi-warp-test crate, up to 512 threads). bar.sync IS proven across warps (gpu-compute.4). The main new challenge is shared memory bank conflict avoidance, which is a well-studied optimization problem with known solutions (padding, swizzled addressing). This is engineering, not research.

**Verdict**: Low risk. Multi-warp synchronization primitives are proven. Bank conflict optimization is optional for a correctness-focused PoC.

### Challenge 5: "You have no way to debug numerical issues on GPU"

When the GEMM output is wrong for non-trivial matrices, how do you debug it? There's no GPU-side printf with formatting flexibility (hostcall print is limited), no GPU debugger integration, no way to inspect intermediate values in shared memory. Debugging a 768×768 GEMM with 98304 output elements by reading raw hex dumps is impractical.

**Counter**: The hostcall print service with format! macro IS available (gpu-std-test demonstrates this). Debugging strategy: (a) verify on tiny matrices first (already done for 16×8), (b) scale up incrementally (32×32, 64×64, 128×128), (c) compare against CPU reference for each scale, (d) use hostcall to dump intermediate values (shared memory contents after each GEMM phase). The approach is tedious but proven — every existing kernel was debugged this way.

**Verdict**: Annoying but manageable. The incremental scaling strategy has worked for all previous kernels.

## Recommended Epic Structure

### Epic: Native GPU Inference

**Success criteria** (scoped and measurable):
1. A single transformer attention mechanism (multi-head self-attention) runs correctly on GPU with real (non-uniform) weight values, verified against CPU reference implementation
2. A single complete transformer layer (attention + FFN + LayerNorm) produces output matching a PyTorch reference within f16 tolerance (atol=1e-2, rtol=1e-2)
3. The GPU autonomously orchestrates the computation — host only provides weights and input, kernel decides execution order

**Decision gate after Theme 2**: If single-layer inference works and the user wants text generation, add Theme 3 (multi-layer + autoregressive). Otherwise, declare epic complete.

### Theme 1: Scalable GEMM (`gemm-scale`)

**Goal**: Scale the existing single-warp GEMM to handle arbitrary matrix dimensions (at least 768×768).

**Success criteria**: M×K × K×N GEMM produces results matching CPU reference for M,K,N up to 768, with non-uniform f16 input values.

| Task | Kind | Description |
|------|------|-------------|
| gemm-scale.1 | experiment | Multi-warp output tiling — 4 warps compute 4 adjacent 16×8 tiles (output: 16×32) |
| gemm-scale.2 | experiment | Multi-block GEMM — different blocks compute different output row-ranges |
| gemm-scale.3 | experiment | Correctness validation at 768×768 against CPU reference with random f16 weights |
| gemm-scale.4 | experiment | (Optional) `ldmatrix.sync.aligned` for efficient fragment loading — skip if register approach works |

### Theme 2: Transformer Layer (`transformer-layer`)

**Goal**: Implement a complete transformer layer and verify against PyTorch reference.

**Success criteria**: Single-layer forward pass matches PyTorch GPT-2 layer 0 output within f16 tolerance.

| Task | Kind | Description |
|------|------|-------------|
| transformer-layer.1 | experiment | LayerNorm kernel (mean + variance reduction, per-element normalize) |
| transformer-layer.2 | experiment | GELU activation kernel |
| transformer-layer.3 | experiment | Multi-head attention: Q/K/V projection → split heads → attention → concatenate → output projection |
| transformer-layer.4 | experiment | FFN block: linear → GELU → linear |
| transformer-layer.5 | design | Weight loading strategy: pre-allocate via cuMemAlloc vs hostcall streaming |
| transformer-layer.6 | experiment | End-to-end single layer: LayerNorm → MHA → residual → LayerNorm → FFN → residual |
| transformer-layer.7 | experiment | Numerical validation against PyTorch GPT-2 layer 0 |

### Theme 3: Autoregressive Generation (`text-gen`) — CONDITIONAL

**Goal**: Generate text token-by-token using multiple transformer layers.

**Success criteria**: Given a prompt, produce grammatically plausible text (not necessarily coherent — model is small).

**Only proceed if**: Theme 2 succeeds AND user explicitly requests it.

| Task | Kind | Description |
|------|------|-------------|
| text-gen.1 | design | KV cache architecture (pre-allocated buffer, position indexing) |
| text-gen.2 | experiment | Multi-layer forward pass (loop over 12 layers, same code, different weights) |
| text-gen.3 | experiment | Argmax sampling kernel |
| text-gen.4 | experiment | Host-side tokenizer + generation loop (tokenize → send to GPU → receive logits → sample → repeat) |
| text-gen.5 | experiment | End-to-end text generation demo |

### Decision Gates / Off-Ramps

1. **After gemm-scale.3**: If 768×768 GEMM is correct but register spilling causes compilation failure or extreme slowness, STOP. Document the scaling limit and declare the epic "feasibility proven with scaling constraints."

2. **After transformer-layer.3**: If multi-head attention has unacceptable numerical divergence from PyTorch (>5% relative error), STOP. Document the precision limitation.

3. **After transformer-layer.6**: Natural decision point. Single-layer success is a complete result. User decides whether to continue to text generation.

### Explicit Exclusions

- **Performance optimization**: No double-buffered shared memory, no warp specialization, no software pipelining, no `cp.async`. Correctness only.
- **Quantization (INT8/INT4)**: Out of scope. Use f16 compute throughout.
- **Flash Attention**: Out of scope. Standard attention with materialized attention matrix.
- **Tensor parallelism / multi-GPU**: Out of scope. Single GPU only.
- **Training / backward pass**: Out of scope. Forward inference only.
- **ONNX / safetensors parsing on GPU**: Out of scope. Host parses model files, GPU receives raw weight tensors.
- **Competitive benchmarking against cuBLAS/TensorRT**: Out of scope. No performance claims.

## Recommendation

**Proceed at Option B scope (single transformer layer), with an off-ramp to Option C.**

The reasoning:

1. **Option A is too small.** A single attention head with synthetic weights is barely distinguishable from the existing GEMM→softmax pipeline (gpu-pipeline.3). It does not exercise weight loading, LayerNorm, or activation functions. The marginal value over what's already proven is minimal.

2. **Option B is the sweet spot.** A single GPT-2 layer with real weights verified against PyTorch exercises every gap in the technical stack (scaled GEMM, LayerNorm, GELU, weight loading, memory management, multi-head coordination) while remaining achievable in 3-5 weeks. The result — "Rust runs a GPT-2 layer on GPU using only async/await and inline PTX" — is a strong, verifiable claim.

3. **Option C is high-risk but high-reward.** If Option B succeeds cleanly, Option C (full text generation) is an incremental extension (multi-layer loop + KV cache + sampling). The additional effort is ~3-5 weeks. The narrative value ("GPT-2 generates text in pure Rust on GPU") is exceptional. But this should be a user decision after seeing Option B results, not a commitment upfront.

4. **The primary risk is the GEMM scaling gap** (Gap 1). Scaling from single-warp 16×8 to multi-block 768×768 is the largest engineering task. If this fails (e.g., register spilling at large tile sizes, shared memory exhaustion), the entire epic is blocked. This is why `gemm-scale` is its own theme with a decision gate.

5. **The project's unique value proposition is autonomy, not performance.** The demo should emphasize that the GPU kernel autonomously orchestrates a complete ML forward pass — deciding execution order, managing memory, loading weights via hostcall — using standard Rust async/await patterns. This is fundamentally different from host-orchestrated frameworks (PyTorch, TensorRT) where the host schedules every kernel launch.

**Bottom line**: The research primitives are all proven. The question is no longer "can this work?" but "does assembling them into a real workload reveal new insights?" The answer is likely yes — integration challenges (memory management, numerical stability, multi-warp coordination at scale) are where real systems diverge from toy demos. A single transformer layer is the minimal scope that exercises all integration challenges without the diminishing returns of multi-layer repetition.
