## Technical Analysis

### Critical Discovery: MMA Already Uses f32 Accumulation

The user context states "f16 accumulation in Tensor Cores is the root cause" — this
is **incorrect**. Examining the actual PTX in `compute.rs`, all GEMM kernels use:

```
mma.sync.aligned.m16n8k16.row.col.f32.f16.f16.f32
```

The format is `D_type.A_type.B_type.C_type`. This means:
- **A, B operands**: f16 (inputs to multiply)
- **C, D operands**: f32 (accumulator input and output)

The accumulation is already f32. The precision loss comes from the f16 **multiplication**
(`f16 × f16`), not the accumulation. Each multiply produces a result with only 10-bit
mantissa precision before being added to the f32 accumulator.

**Implication**: Switching to "f32 accumulation" is not an option — we already have it.
The user's proposed fix #1 (f32 accumulator MMA) is what we already use. The proposed
fix #3 (mixed precision with f32 accumulation) is also already what we have.

### Is TF32 MMA Feasible?

TF32 uses `mma.sync.aligned.m16n8k8.row.col.f32.tf32.tf32.f32`:
- **TF32**: 19-bit mantissa (vs f16's 10-bit), 8-bit exponent (same as f32)
- **K dimension per instruction**: 8 (vs f16's 16), so 2x more MMA instructions needed
- **Precision improvement**: ~4x better per-multiply (19 vs 10 mantissa bits)
- **Hardware requirement**: SM 80+ (Ampere) — RTX 3090 is SM 86, so supported

**Changes needed**:
1. New kernel `full_gemm_tf32` with m16n8k8 MMA instruction
2. Input conversion from f32 to tf32 (truncate mantissa: `cvt.rn.tf32.f32`)
3. Shared memory tile size changes: K=8 instead of K=16 per MMA
4. Register layout changes: 4 A registers (tf32), 2 B registers (tf32)
5. All downstream kernels that feed into GEMM need to output f32 (already do)

**Estimated effort**: Medium — kernel structure is similar but register mapping and
tile dimensions differ. The inline PTX requires careful register allocation.

### Would TF32 Fix the NaN Issue?

**Likely yes, but not guaranteed.** The NaN at position 0 comes from a specific
mechanism: in causal self-attention, position 0 only attends to itself (no averaging).
The attention output equals V[0] scaled by softmax(Q[0]·K[0]/sqrt(d)). If Q·K produces
a value that overflows f16 range (~65504) during the GEMM that computes Q, K, or V
projections, the downstream values go NaN.

With TF32's 19-bit mantissa (same 8-bit exponent as f32), overflow is far less likely
because the intermediate products are more precise. But the exponent range is identical
to f32, so the overflow threshold is the same as f32 (not f16).

**Wait — there is a subtlety**: The f16 overflow is happening in the MMA inputs (A
and B matrices), not the accumulator. The f32-to-f16 conversion truncates values
outside [-65504, 65504] to infinity. If any activation exceeds f16 range after several
layers, the f16 conversion produces Inf, and Inf × anything in MMA produces NaN/Inf.

TF32 has the same exponent range as f32 (±3.4e38), so it would **eliminate the
overflow entirely**. This is likely the actual fix.

### Pure f32 GEMM (No Tensor Cores)

A pure f32 GEMM using `fma.rn.f32` in a loop would:
- **Eliminate all precision concerns**: f32 × f32 → f32, matching PyTorch's CPU path
- **Performance cost**: ~8-16x slower (no Tensor Core throughput, scalar FMA units only)
- **Estimated speed**: ~78ms/token × 8 ≈ 624ms/token (still usable for PoC)
- **Implementation**: Simpler than TF32 — just scalar multiply-accumulate in a tiled loop

For a research PoC, this is a valid approach. It would definitively prove whether
the precision issue is the only thing preventing correct output.

**Minimal script** (user runs this externally):

```python
from transformers import GPT2LMHeadModel, GPT2Tokenizer
import torch, struct
model = GPT2LMHeadModel.from_pretrained("gpt2")
tokenizer = GPT2Tokenizer.from_pretrained("gpt2")
input_ids = tokenizer("The capital of France is", return_tensors="pt").input_ids
with torch.no_grad():
    logits = model(input_ids).logits
    # Save last-position logits
    last_logits = logits[0, -1].numpy()
    with open("models/reference_logits.bin", "wb") as f:
        f.write(struct.pack(f"{len(last_logits)}f", *last_logits))
    # Save top-10 predictions
    top10 = torch.topk(logits[0, -1], 10)
    for i, (idx, score) in enumerate(zip(top10.indices, top10.values)):
        token = tokenizer.decode([idx])
        print(f"{i+1}. {repr(token)} ({score:.2f})")
    # Generate
    out = model.generate(input_ids, max_new_tokens=20, do_sample=False)
    print(tokenizer.decode(out[0]))
```

This would answer the critical question: **does HuggingFace GPT-2 (f32, CPU)
actually predict "Paris"?** GPT-2 small is a weak model — it might not.

## Skeptic Challenges

### Challenge 1: Is the NaN Really from f16 Precision?

**Untested assumption**: The NaN is attributed to f16 precision without definitive
proof. Alternative causes:

1. **Flash attention numerics at position 0**: Position 0 in causal mode only has 1
   valid attention score (itself). The online softmax computes exp(s - max) where
   s = max = Q[0]·K[0]/sqrt(64). If this dot product is large (e.g., >10), then
   `l = exp(0) = 1.0` and the output is simply V[0]. This is numerically fine. But
   if the Q or K values are already NaN/Inf from GEMM, the attention propagates it.

2. **LayerNorm with extreme values**: If GEMM output has even one NaN, LayerNorm
   computes mean and variance over the row including NaN, producing NaN for the
   entire row. This is a NaN amplifier, not a NaN source.

3. **f32-to-f16 conversion overflow**: The most likely NaN source. After layer N,
   if any activation value exceeds 65504 (f16 max), the `cvt.rn.f16.f32` in
   `full_gemm_f32in` produces f16 infinity. The next MMA computes Inf × finite = Inf,
   and eventually Inf - Inf = NaN in softmax or LayerNorm.

**Recommendation**: Add diagnostic instrumentation to dump intermediate values after
each layer. Check whether values exceed f16 range before NaN appears.

### Challenge 2: Would GPT-2 Small Even Predict "Paris"?

GPT-2 small (124M params) is a relatively weak model. Its factual knowledge is
unreliable. The success criterion "produces text containing Paris" may be unachievable
even with perfect f32 precision.

**Evidence**: The HuggingFace model card for GPT-2 warns about factual accuracy. A
quick check (user can verify) would determine if GPT-2 small reliably predicts "Paris"
for this prompt with greedy decoding.

If GPT-2 small does not predict "Paris" even in PyTorch, the epic's success criteria
need revision — this is not an implementation bug but an unrealistic expectation.

### Challenge 3: Token-for-Token Match is Extremely Stringent

Even if we achieve correct top-1 for "The capital of France is", matching HuggingFace
token-for-token for "3+ test prompts" requires:
- Identical numerical computation at every step
- Identical tokenization (verified — already done)
- Identical generation loop logic (temperature=0, greedy argmax)

Any floating-point divergence that changes a single argmax in the sequence creates
a cascade: the wrong token feeds into the next step, producing entirely different
output. Token-for-token matching requires near-exact numerical agreement.

With Tensor Core GEMMs (even TF32), achieving identical output to PyTorch's CPU f32
computation is unrealistic. The criterion should be: "greedy output produces
semantically equivalent text" or "top-5 predictions contain the same tokens."

### Challenge 4: Is the " (" Prediction Wrong, or Just Different?

The model predicts " (" with 20.1% probability. This is a structurally valid GPT-2
output — GPT-2 often generates parenthetical completions like "The capital of France
is (or was) Paris." Without a reference output, we cannot distinguish between:
- (a) f16 error changed the top-1 from "Paris" to " ("
- (b) GPT-2 small genuinely predicts " (" with f32 too

Only a reference comparison can resolve this.

## Summary of Key Insights

1. **The MMA already uses f32 accumulation** — the original diagnosis of "f16
   accumulation" is wrong. The precision bottleneck is f16 multiplication, and
   the NaN likely comes from f16 range overflow (>65504), not rounding.

2. **We need a reference output** before any further precision work. Without it,
   we cannot distinguish "our implementation is wrong" from "GPT-2 small is wrong."

3. **Pure f32 GEMM is the fastest path to certainty** — it eliminates all precision
   questions at the cost of ~8x performance, which is acceptable for a PoC.

4. **The epic criteria may need revision** — "produces Paris" is a factual accuracy
   requirement on a model known for unreliable factual knowledge.
