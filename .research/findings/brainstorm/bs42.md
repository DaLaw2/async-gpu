## Technical Analysis

### 1. NaN at Step 22: Root Cause and Fixes

**Mechanism**: Hidden state norms grow through residual connections — 56.5 at layer 0
to 429.6 at layer 11 (measured in CPU f64 for 5-token input). At 27 tokens (seq=22+5),
norms are larger. When values exceed ~65504 during intermediate computation, f32
softmax overflows (exp of large values → Inf, then Inf - Inf → NaN).

**Three feasible fixes (not mutually exclusive)**:

1. **Online softmax (numerically stable)**: Replace `exp(x) / sum(exp(x))` with the
   online algorithm: track running max, compute `exp(x - max)`. This is standard in
   FlashAttention and eliminates softmax overflow regardless of input scale.
   - Effort: low-medium (modify attention kernel)
   - Impact: directly prevents the NaN mechanism
   - Already partially implemented? Check if current attention uses online softmax.

2. **f32 attention scores with clamping**: Clamp QK^T/sqrt(d) to [-50, 50] before
   softmax. This is a pragmatic guard against overflow without changing the softmax
   algorithm. Some precision loss for extreme values but prevents NaN entirely.
   - Effort: very low (add a clamp instruction)
   - Impact: prevents NaN but may mask real numerical issues

3. **KV cache**: Currently the generation loop recomputes all 12 layers for the full
   sequence at each step. With KV cache, only the new token passes through the model,
   dramatically reducing the number of operations and thus floating-point error
   accumulation. Also a major performance win.
   - Effort: high (significant architecture change)
   - Impact: reduces error accumulation AND improves performance

**Recommendation**: Start with online softmax (fix 1). It directly addresses the
overflow mechanism with minimal code change. KV cache is a larger project that
should be a separate theme.

### 2. MMA Kernel Bug: Fix or Accept f32 GEMM?

**Current state**: `full_gemm_f32in` MMA (tensor core) kernel produces wrong results.
`gemm_f32` (pure f32 FMA) produces correct results matching CPU f64 exactly.

**Arguments for fixing MMA**:
- Tensor cores are 8-16x faster than scalar FMA
- For inference at seq=128+, the performance difference is significant (~78ms vs ~10ms per GEMM)
- The bug is likely an indexing/layout issue in the MMA register mapping (full-inference.11 analysis)
- The kernel worked for simpler test cases (gpu-compute/gpu-pipeline themes), suggesting
  a dimension-dependent bug

**Arguments for accepting f32 GEMM**:
- f32 GEMM is proven correct — zero debugging needed
- Performance is acceptable for PoC (~600ms/token)
- MMA debugging requires understanding complex PTX register layouts for m16n8k16
- MMA with f16 inputs introduces precision concerns even when fixed

**Recommendation**: Accept f32 GEMM for now. The NaN and generation correctness are
higher priority than performance. Fixing MMA should be a separate, optional theme
(not blocking any epic criterion). When fixed, it can be swapped in as a drop-in
replacement since the GEMM interface is the same.

### 3. Is the "Paris" Criterion Realistic?

**No. The CPU f64 reference is definitive.**

Evidence from full-inference.8:
- CPU f64 top-1: " the" (logit -100.25)
- CPU f64 "Paris" rank: 5 (logit -101.21, gap 0.97 from top-1)
- Other prompts prove the model works: "Tokyo", "John", "United" are all correct top-1
- Layer 9-10 show "France"/"Paris" as top predictions, but layer 11's large attention
  residual (norm=200.26) overwrites this

GPT-2 small (124M params) is not a strong factual model. The prompt completion is
structurally ambiguous — "The capital of France is" can continue with " the" (→ "the
capital"), " a" (→ "a city"), etc. The model prefers syntactic continuations over
factual ones.

**The criterion must be revised.** Proposed alternatives:
- "Forward pass output matches CPU f64 reference for top-5 tokens" (implementation correctness)
- "Generation produces coherent English text for 50+ tokens" (numerical stability)
- "Top-5 tokens for 3+ prompts match CPU f64 reference" (precision validation)

## Skeptic Challenges

### Challenge 1: Is NaN Truly Just Precision, or Is There a Bug?

**Untested assumption**: The NaN is attributed to f32 softmax overflow from growing
hidden state norms. But there could be bugs in:

1. **Attention mask at long sequences**: The causal mask implementation was tested at
   seq<=128 (attention-scale theme). At seq=27 in generation, it should work, but
   edge cases in the tiled attention kernel for non-power-of-2 sequence lengths are
   possible. Has anyone verified seq=27 specifically?

2. **Position embedding overflow**: GPT-2 supports seq up to 1024, and position
   embeddings are loaded for positions 0-1023. At seq=27, this should be fine, but
   verify that the position index is correctly incremented during generation.

3. **Residual connection accumulation**: The growing norms (56→430 over 12 layers) are
   expected for GPT-2, but verify this by checking the CPU f64 generation at step 22.
   Does CPU f64 also show norm growth at seq=27? If CPU f64 produces NaN at step 22
   too, the issue is fundamental to f32 (not a bug). If CPU f64 continues fine, the
   issue might be f32-specific precision loss in a specific operation.

**Recommended test**: Run CPU f64 generation for 50+ tokens. If it survives, the NaN
is f32-specific and online softmax is the right fix. If it also NaNs, there is a
deeper numerical issue.

Five active themes have all tasks done:

For full-inference: keep active. full-inference.5 (decision gate) needs to be

### Challenge 3: Are We Optimizing for the Wrong Metric?

The epic asks for "token-for-token match with HuggingFace for 3+ prompts." This is
a reproducibility criterion that assumes identical numerical computation. But:

- PyTorch CPU uses f32 with specific operation ordering (matmul, then bias add, etc.)
- Our GPU pipeline uses f32 FMA with different tiling and accumulation order
- Even PyTorch GPU vs CPU can diverge token-for-token due to floating-point non-associativity
- The proper criterion is **functional equivalence** (same semantic output), not bit-exact match

If we fixate on token-for-token matching, we may spend weeks chasing floating-point
differences that have no semantic impact. The more productive path is to validate
top-k agreement and ensure generation doesn't NaN.

### Challenge 4: Is host-sdk.3 Premature?

The standalone example (host-sdk.3) depends on a stable API. But the gpu-inference
work may require API changes (new kernel types, different memory management for
generation loops, KV cache support). Building the example now risks rework.

Counter-argument: the example validates the API design. If it is hard to write, the
API needs improvement — that is valuable feedback.

**Recommendation**: Defer host-sdk.3 until the NaN issue is resolved and generation
works. The public-api epic is lower priority than gpu-inference.
