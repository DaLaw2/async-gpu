## Technical Analysis

### 1. MMA Kernel Bug Diagnosis

The `full_gemm_f32in` kernel (line 924 of compute_gemm.rs) works for small test matrices
(32x768 x 768x16 = 32x16 in `run_full_gemm_f32in_test`) but fails at GPT-2 scale.
The `full_gemm` kernel (line 772) with pre-packed f16x2 inputs shares the same MMA
fragment loading and output-writing logic, so the bug likely lives in a shared code path.

**Key observation**: Both `full_gemm` and `full_gemm_f32in` use identical fragment loading:

```
a0 = a_smem[(a_off + group) * 8 + lane]
a1 = a_smem[(a_off + group) * 8 + lane + 4]
a2 = a_smem[(a_off + group + 8) * 8 + lane]
a3 = a_smem[(a_off + group + 8) * 8 + lane + 4]

b_col = warp_n * 8 + group
b0 = b_smem[b_col * 8 + lane]
b1 = b_smem[b_col * 8 + lane + 4]
```

This indexing was validated against the NVIDIA PTX ISA for m16n8k16. The single-tile
and multi-warp tests pass, so the fragment loading itself is correct.

**Likely bug location — B-matrix shared memory loading for large N:**

In the B-loading loop (`if tid < 128`):
```
let col = tid / 8;      // 0..15 (local column)
let k_pair = tid % 8;   // 0..7
let global_idx = col * k_half + t * 8 + k_pair;
*b_smem.add(tid as usize) = *b_block.add(global_idx as usize);
```

The shared memory layout stores B as `b_smem[col * 8 + k_pair]` = `b_smem[tid]`.
But the fragment loading reads `b_smem[b_col * 8 + lane]` where `b_col = warp_n * 8 + group`.

With `group` ranging 0..7 and `warp_n` being 0 or 1:
- `b_col` ranges over {0..7} (warp_n=0) and {8..15} (warp_n=1)
- Each `b_col` value addresses `b_smem[b_col * 8 + 0..3]` and `b_smem[b_col * 8 + 4..7]`
- This covers `b_smem[0..127]` which is exactly 128 entries — matches the load.

**So the fragment indexing is consistent.** The problem is more subtle.

**Hypothesis 1: k_half computation mismatch.** In `full_gemm`, the parameter `k_tiles` is
K/16 and `k_half = k_tiles * 8` = K/2. For 768x768, k_tiles=48, k_half=384. This is
correct for B column-major packed: each column has K/2 = 384 u32s. The loading accesses
`col * 384 + t * 8 + k_pair` which is correct.

**Hypothesis 2: Grid dimension mismatch on the host side.** For 768x768:
- grid_dim.x = M/32 = 24 (row blocks)
- grid_dim.y = N/16 = 48 (column blocks)

If the host launches with grid_dim = (24, 48, 1) but the kernel reads block_n via
`%ctaid.y`, this should work. But if the host passes grid_dim = (24, 1, 1) (forgetting
the Y dimension), all blocks would compute the same 16 output columns.

**Hypothesis 3: Shared memory bank conflicts or race conditions.** The `bar_sync()` between
load and compute should prevent races. But if `bar_sync()` is warp-level (`bar.warp.sync`)
rather than block-level (`bar.sync 0`), the 4 warps would not synchronize properly. This
would explain why single-warp (32-thread) tests pass but multi-block tests fail.

**Recommended diagnosis approach:**
1. Add a diagnostic kernel that dumps B-matrix shared memory contents after loading for
   block (0,0) and block (0,1) — verify data integrity across tile boundaries.
2. Run `full_gemm` (not f32in) at 768x768 — if it also fails, the bug is in the shared
   tiling logic, not in f32->f16 conversion.
3. Check the host-side launch config for `full_gemm_f32in` — verify grid_dim.y is set.
4. Verify `bar_sync()` implementation generates block-level synchronization, not warp-level.

### 2. KV Cache Architecture

Current inference loop (`tests_inference.rs`) recomputes all 12 transformer layers for
every generated token. For a 50-token generation:
- Without KV cache: 50 * 12 layers * 4 GEMM per layer = 2400 GEMM ops
- With KV cache: 12 layers * 4 GEMM for first token, then 12 * 2 small GEMM per step
  (only Q needs full recompute; K and V are cached and appended)

Architecture changes needed:
1. **Device-side KV buffers**: Pre-allocate `[12][max_seq_len][768]` for K and V per layer
   (12 * 2 * 1024 * 768 * 4 bytes = ~72 MB for max_seq=1024).
2. **Split attention kernel**: Separate Q-projection (full GEMM) from K/V-projection
   (append-only: compute for new token, copy to cache).
3. **Causal attention with cached K/V**: Attention scores = Q_new * K_cached^T, then
   softmax + V_cached multiply.
4. **Host orchestration**: Track sequence position, launch appropriate kernels per step.

This is a significant refactor but offers the largest latency reduction (potentially 10-20x
for longer sequences).

## Skeptic Challenges

### On MMA kernel diagnosis
- **Challenge**: "The fragment indexing was already validated — why assume it is the bug?"
  Fair point. The fragment indexing passes for small matrices. The bug more likely lives
  in host-side launch configuration (grid dimensions, shared memory size) or in `bar_sync()`
  scope. A diagnostic that prints launch config would be cheaper than re-auditing fragments.
- **Risk**: Spending cycles re-deriving MMA register mapping that is already correct, while
  the actual bug is a one-line host-side grid_dim.y mistake.

### On KV cache priority
- **Challenge**: "KV cache is a massive refactor. Should you fix MMA first?"
  Yes. KV cache is pointless if the MMA kernel is broken — you would build on a broken
  foundation. MMA fix must come first. But KV cache design can proceed in parallel as a
  design task (no code).

### On example extraction
- **Challenge**: "The tests depend on internal crate APIs (hostcall::HostcallBuffer, mapped_mem).
  Can they really become standalone examples?"
  Only if gpu-host exports these APIs, which host-sdk.1/.2 already did. The examples
  should use the public SDK API. If the API is insufficient, that feeds back into host-sdk
  work.

### On PTX gitignore
- **Challenge**: "If PTX files are not in the repo, how does CI build?"
  There is no CI currently. The PTX build is manual. Gitignoring PTX is correct — the
  build documentation must specify the PTX compilation step. This is already documented
  in CLAUDE.md's build commands.

### On the 20ms latency target
- **Challenge**: "Current latency is ~143ms. MMA gives 8-16x speedup. KV cache gives
  another 10-20x for long sequences. Is 20ms realistic?"
  For short sequences (< 50 tokens), MMA alone might reach ~9-18ms. For longer sequences,
  KV cache is essential. The 20ms target is achievable for short generation but may need
  further optimization (kernel fusion, occupancy tuning) for longer sequences.

### Key Insight

The MMA bug is most likely a host-side launch configuration issue (grid_dim.y not set)
or a `bar_sync()` scope problem (warp-level instead of block-level), not a fragment
indexing error. The diagnosis task should start by checking these two hypotheses before
re-auditing the MMA register mapping. A single printf-equivalent diagnostic kernel
dumping block_idx and shared memory state for the first tile would likely pinpoint
the issue in one experiment cycle.
