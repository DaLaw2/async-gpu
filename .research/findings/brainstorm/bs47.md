## Technical Analysis

### Option A: TF32 MMA for gpu-perf criterion 3

- sm_86 supports TF32 MMA via `mma.sync.aligned.m16n8k8.row.col.f32.tf32.tf32.f32`
- TF32 format: 19 bits total (1 sign + 8 exponent + 10 mantissa)
- Key advantage: full f32 exponent range avoids overflow/underflow issues
- Key disadvantage: **mantissa is 10 bits, same as f16** — the precision bottleneck is mantissa width, not exponent range
- TF32 K-dimension is k=8 (vs k=16 for bf16/f16), requiring different tiling strategy
- Prediction: TF32 will behave similarly to f16 MMA since both have 10-bit mantissa products

### Option B: f32 FMA latency optimization for gpu-perf criterion 2

- f32 FMA forward pass: 35ms → need ~1.75x speedup to hit 20ms
- Possible optimizations:
  - Persistent kernel (reduce launch overhead)
  - Better occupancy tuning (register pressure, shared memory usage)
  - Reduced synchronization (fewer barriers between layers)
  - Fused kernels (combine GEMM + bias + activation into single launch)
- Risk: 1.75x is a significant speedup; may require fundamental architectural changes

### Option C: public-api focus

- Un-park host-sdk theme, create host-sdk.2 (API type extraction)
- Clean up existing public modules in gpu-host
- Add GpuDevice wrapper, document existing functionality
- Create 2+ additional examples
- Directly serves the user's stated goal

## Skeptic Challenges

### 1. TF32 is likely a dead end

TF32 mantissa is 10 bits — identical to f16. The mixed-precision findings showed that the precision failure is caused by mantissa quantization error cascading through 12 residual layers. Exponent range (which TF32 improves) is not the bottleneck. If f16 MMA fails inference, TF32 will almost certainly fail too.

**Counter**: TF32 accumulates into f32 registers and has f32 exponent range, so intermediate values won't overflow/underflow. The failure mode might be different. A single experiment (2 tasks) would definitively resolve this.

**Verdict**: Worth one quick experiment, but set expectations low.

### 2. The 20ms target may be unrealistic for this hardware/approach

- BF16 MMA at 24ms is the fastest option, and it fails criterion 3
- f32 FMA at 35ms needs 1.75x improvement — aggressive for a single-SM workload
- KV cache path (68ms) has overhead from per-token kernel launches
- The bottleneck is likely not just GEMM speed but also kernel launch overhead, device synchronization, and memory bandwidth

**Counter**: There are known unexplored optimizations (persistent kernels, fused ops) that could yield significant gains.

**Verdict**: Possible but requires significant engineering investment with uncertain ROI.

### 3. public-api has clearer ROI and user alignment

- gpu-perf is hitting diminishing returns: precision vs speed tradeoff with no clear win
- The user explicitly asked for reusable utilities
- public-api work is mostly engineering (not research), so outcomes are more predictable
- Completing public-api makes the entire project more useful to others
