## Technical Analysis

### Gap: std-build-test (working) vs gpu-kernel (no_std)

The two crates represent fundamentally different approaches:

| Dimension | std-build-test | gpu-kernel |
|-----------|---------------|------------|
| Build mode | `-Zbuild-std=std` + patched-std | `-Zbuild-std=core` (no_std) |
| Allocator | Slab in patched std (`sys::alloc::cuda`) | Separate GpuAllocator via gpu-libc bump allocator |
| I/O | `writeln!(std::io::stdout())` | Manual `gpu_hostcall_print` via inline PTX |
| Panic | std panic handler → hostcall | gpu-runtime panic handler → hostcall |
| Formatting | `format!()`, `println!()` from std | Manual byte array construction |
| Dependencies | gpu-libc (for libc stubs) | gpu-runtime, gpu-protocol, gpu-atomics |
| Kernel count | ~10 test kernels | 65+ production kernels |

**Key insight**: std-build-test duplicates ALL hostcall inline PTX locally (430+ lines of `gpu_hostcall_print_raw` and `gpu_hostcall_stdin_raw`) because it cannot depend on gpu-runtime (which is no_std). This duplication is a code smell that will get worse.

### Can gpu-kernel migrate to -Zbuild-std=std?

**What would need to change:**

1. **Cargo.toml**: Remove `#![no_std]`, add `#![feature(restricted_std)]`
2. **Allocator**: Remove GpuAllocator from gpu-std-test; patched std's slab allocator takes over
3. **I/O functions**: Export `gpu_stdout_write()` and `gpu_stdin_read()` as `#[unsafe(no_mangle)]` functions (same pattern as std-build-test)
4. **Panic handler**: Remove `gpu_runtime::panic_handler!()` — std provides its own
5. **Dependencies**: gpu-libc becomes required (for libc stubs that std needs)
6. **Build command**: Switch from `-Zbuild-std=core` to `-Zbuild-std=std`

**What would break:**

1. **OnceLock/ReentrantLock**: println!() was fixed (bypasses OnceLock), but stdin() still broken. Any std API using OnceLock internally will fail.
2. **Thread-local storage**: std assumes TLS exists. GPU has no TLS. Patched std must stub this.
3. **Code size**: std pulls in significantly more code — PTX size will increase substantially.
4. **Compilation time**: `-Zbuild-std=std` is much slower than `-Zbuild-std=core`.
5. **Feature gates**: Some std features crash LLVM NVPTX backend (e.g., float formatting had issues).
6. **65+ existing kernels**: Pure compute kernels (GEMM, softmax, MMA) gain nothing from std but inherit all the risk and code bloat.

### How to replace gpu-libc stubs with real hostcall implementations

The current architecture has two parallel I/O paths:

- **Path A (std-build-test)**: std → PAL (`cuda.rs`) → extern `gpu_stdout_write` → inline PTX hostcall
- **Path B (gpu-kernel)**: kernel → `gpu_runtime::hostcall::gpu_hostcall_print` → inline PTX

For file I/O (criterion 3 of real-std), the approach should be:

1. **Add new hostcall services** to gpu-protocol: `SERVICE_FS_OPEN`, `SERVICE_FS_READ`, `SERVICE_FS_WRITE`, `SERVICE_FS_CLOSE`
2. **Implement host-side handlers** in gpu-host that translate hostcall packets to real file I/O
3. **Two options for GPU-side routing**:
   - **Option A: PAL-level**: Add `patched-std/library/std/src/sys/fs/cuda.rs` that calls extern functions (`gpu_fs_open`, `gpu_fs_write`, etc.) — same pattern as stdio
   - **Option B: libc-level**: Make `gpu-libc/src/stub.rs` `write()`/`read()`/`open()` call hostcall instead of returning ENOSYS — std's existing POSIX fs implementation handles the rest

**Option B is better** because it doesn't require patching more std code, and std's fs module already knows how to talk to POSIX libc. The challenge: gpu-libc functions need access to the hostcall buffer pointer, which is currently per-kernel-launch, not global.

### Result<T, E> propagation from GPU kernel to host

The PTX kernel ABI restriction (`extern "ptx-kernel" fn(...) -> ()`) means we CANNOT return Result directly. Options:

1. **Error output buffer** (simplest): Add a `*mut GpuResult` parameter to every kernel. On success, write `GpuResult::Ok`. On error, write `GpuResult::Err(category, message_ptr, message_len)`. Host reads this after kernel completion.

2. **Hostcall error channel**: GPU sends error info via a dedicated `SERVICE_ERROR` hostcall before executing `trap;`. Host captures the error before `CUDA_ERROR_LAUNCH_FAILED`. Problem: trap kills the CUDA context, so recovery is still impossible.

3. **Cooperative exit**: Instead of `trap;`, the kernel writes to an error buffer AND returns normally (no trap). The `?` operator desugars to "write error to buffer + return early." This requires modifying the panic handler to NOT trap.

**Option 3 is the most viable**: define a convention where every kernel has an error output parameter, the `?` operator writes to it, and early return is cooperative (not a trap). A proc macro like `#[gpu_kernel]` could inject the error buffer parameter automatically.

### What order: error handling first, or std migration first?

**Error handling first.** Rationale:

1. std::io returns `Result<T, io::Error>`. If we migrate gpu-kernel to std without error handling, every I/O call must `.unwrap()` or be silently ignored — exactly the current problem.
2. The error output buffer pattern is independent of std vs no_std. It works in both worlds.
3. std::fs errors (criterion 4 of gpu-error) depend on std::fs working (criterion 3 of real-std), but the error propagation *mechanism* doesn't.
4. Doing error handling first means we can migrate to std with proper error semantics from day one.

**Recommended order**: gpu-error mechanism → real-std migration (with errors) → std::fs implementation (combines both epics)

## Skeptic Challenges

### Is migrating gpu-kernel to std even desirable?

**Challenge**: gpu-kernel has 65+ kernels that work perfectly with no_std. The compute kernels (GEMM, softmax, MMA, transformer layers) don't need Vec, String, or println. Adding std increases PTX size, compilation time, and attack surface for LLVM bugs.

**Counter**: The migration doesn't have to be all-or-nothing. Options:
- **Hybrid approach**: Keep compute kernels in gpu-kernel (no_std). Create a new `gpu-kernel-std` crate for kernels that need std features (hostcall I/O, file access, async pipelines).
- **Selective migration**: Only migrate hostcall/pipeline kernels that already use format strings and I/O. Pure compute kernels stay no_std.
- **Feature gate**: `#[cfg(feature = "std")]` vs `#[cfg(not(feature = "std"))]` within gpu-kernel.

**Verdict**: Do NOT migrate all 65+ kernels. Hybrid approach is correct — separate crate or feature gate.

### Will OnceLock/ReentrantLock block real usage?

**Challenge**: std::io::stdin() doesn't work because it wraps the PAL Stdin in `OnceLock<ReentrantLock<BufReader<Stdin>>>`. println!() was fixed by bypassing OnceLock in `_print()`, but any new std API using OnceLock will hit the same wall.

**Counter**: This is the single biggest risk. OnceLock ultimately calls `futex_wait`/`futex_wake` via the `syscall` stub, which returns ENOSYS. Options:
1. **Patch more of std**: Make OnceLock on CUDA use a spinlock instead of futex (already partially done for println).
2. **Fix the futex stub**: Implement `syscall` in gpu-libc to use GPU atomic spinlocks for futex-like behavior. This is architecturally correct but complex.
3. **Accept the limitation**: Document that `std::io::stdin()` must be called via the PAL extern directly. This is what std-build-test already does.

**Verdict**: Option 1 is incremental and proven (println fix worked). Each broken API can be patched as encountered. This is manageable risk, not a blocker.

### Can bump allocator (no real free) support real std workloads?

**Challenge**: gpu-libc's bump allocator has `free()` as a no-op. std uses alloc/dealloc extensively (String::drop, Vec::drop, etc.). Long-running kernels will OOM.

**Counter**: The patched std already has a slab allocator (`sys::alloc::cuda.rs`) with proper deallocation! It uses 8 size classes (16B-4096B) with atomic bitmap allocation, plus overflow bump for large allocations. This is already proven working in std-build-test with concurrent allocation stress tests (32 threads, alloc/dealloc cycles).

**Verdict**: NOT a concern. The slab allocator in patched std solves this. Only gpu-libc's bump allocator (used by the no_std path) has this limitation.

### Is Result propagation through PTX kernel ABI actually possible?

**Challenge**: `extern "ptx-kernel" fn` CANNOT return non-unit types. CUDA kernels are launched with `cuLaunchKernel` which has no return value mechanism. So `Result<T, E>` literally cannot be a return type.

**Counter**: True, but the *semantic* goal is achievable:
1. **Error output buffer**: Every kernel takes `result: *mut GpuKernelResult`. This is already the pattern — most kernels take `result: *mut u32` and write status there.
2. **Proc macro sugar**: `#[gpu_kernel] fn my_kernel() -> Result<(), GpuError>` desugars to `fn my_kernel(__error_buf: *mut GpuKernelResult)` where `?` writes to `__error_buf` and returns.
3. **Host SDK integration**: `KernelBuilder::launch()` returns `Result<T, GpuKernelError>` by reading the error buffer after synchronization.

This isn't "real" Result<T, E> propagation, but it provides the same developer ergonomics.

**Verdict**: Possible with proc macro + convention. The pattern already exists informally (result pointers). Formalizing it is engineering, not research.

## Recommendations

### Priority Order

1. **gpu-error: Error propagation mechanism** (unblocks everything else)
2. **real-std: Selective std migration** (builds on error handling)
3. **public-api: host-sdk extraction** (can parallel with #1-2)
4. **gpu-perf**: No action (effectively parked)

### Theme 1: `gpu-error-propagation` (epic: gpu-error)

**Goal**: Define and implement GPU→host error propagation using output buffer convention.

**Success criteria**:
- `GpuKernelResult` type defined with Ok/Err variants, encodable in 64 bytes
- Hostcall callers check `CONTROL_ERROR` and return `Result` instead of bool/panic
- Host SDK reads error buffer after kernel launch and returns `Result<(), GpuKernelError>`
- Panic handler writes to error buffer instead of (or before) trapping

**Tasks**:

**Goal**: Migrate hostcall/IO kernels to use patched std while keeping compute kernels as no_std.

**Success criteria**:
- New `gpu-kernel-std` crate builds with `-Zbuild-std=std` and can use `println!()`, `Vec`, `format!()`

## Key Decisions Needed

1. **Separate crate vs feature gate**: Should std-capable kernels live in `gpu-kernel-std` (new crate) or `gpu-kernel` with `#[cfg(feature = "std")]`? Recommendation: new crate — cleaner separation, avoids conditional compilation complexity.

2. **gpu-libc route vs PAL route for fs**: Should file I/O go through gpu-libc's POSIX stubs (option B) or new PAL modules (option A)? Recommendation: gpu-libc route — less std patching, more conventional.

3. **Error buffer ownership**: Should the error buffer be a kernel parameter or a global? Recommendation: kernel parameter — explicit, no global state, composable with multi-kernel launches.
