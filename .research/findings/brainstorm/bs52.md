## 2. Technical Analysis: ThreadLocal on GPU

### Background: What `no_threads` Does

In `std/src/sys/thread_local/mod.rs`, the `no_threads` path provides `EagerStorage` and `LazyStorage` as plain static variables. There is no per-thread isolation — the variable is a single global. This is correct for targets like `zkvm` and `trusty` where only one thread of execution exists.

On CUDA, this is only correct for `block_dim: (1,1,1), grid_dim: (1,1,1)` launches — exactly one hardware thread.

### Option A: PTX `.local` Memory

**Concept**: PTX has a `.local` address space that provides per-thread storage. Each CUDA thread gets its own local memory region (backed by registers or L1 cache).

**Implementation path**:
- Use `#[thread_local]` attribute or LLVM `thread_local(localexec)` to place variables in `.local` address space
- LLVM's nvptx backend maps `thread_local` globals to PTX `.local` address space

**Problems**:
1. **Destructor execution**: `thread_local!` in std expects to run destructors at "thread exit." GPU threads don't have a thread exit — they simply stop executing. The `no_threads` path's destructor behavior (calling destructors at "runtime shutdown") maps to... nothing on GPU. Kernels don't have an atexit mechanism.
2. **LLVM support**: The nvptx LLVM backend's support for `thread_local` is questionable. Nightly Rust may or may not lower `#[thread_local]` correctly for nvptx64. Needs investigation.
3. **Static initialization**: `.local` variables cannot have dynamic initialization. `LazyStorage` pattern (init on first access) would need the init closure to run per-thread, which is correct, but the storage location must be `.local`.

**Verdict**: Theoretically the cleanest solution. High uncertainty about LLVM/nvptx support. Needs an experiment: compile a `#[thread_local] static X: u32 = 0` for nvptx64 and inspect the PTX output.

### Option B: Thread-ID Indexed Array

**Concept**: Allocate a global array indexed by a flattened thread ID: `tid.x + tid.y * blockDim.x + tid.z * blockDim.x * blockDim.y + (block_id * threads_per_block)`.

**Implementation path**:
- Replace `no_threads` storage with a `CudaThreadLocal<T>` that:
  1. Allocates `[T; MAX_THREADS]` in global memory
  2. Reads `%tid.x`, `%ntid.x`, `%ctaid.x`, `%nctaid.x` via inline PTX
  3. Computes flat index and returns `&T` / `&mut T`
- For std integration, this would require a new `thread_local` backend in `std/src/sys/thread_local/` (e.g., a `cuda.rs` module)

**Problems**:
1. **MAX_THREADS unknown at compile time**: CUDA max is 1024 threads/block × 65535 blocks = ~67M threads. Cannot statically allocate that much for every thread_local.
2. **Dynamic allocation**: Could allocate the array in the bump allocator at init time, but need to know the launch configuration. This requires the kernel entry point to pass `gridDim * blockDim` to the TLS init code.
3. **Memory overhead**: Each `thread_local!` variable gets an array of `N` copies. If N=1024 (single block), overhead is moderate. If N=65535*1024, it's catastrophic.
4. **Complexity**: Requires a new std patch for a `cuda` thread_local backend, plus coordination between kernel entry and TLS init.

**Verdict**: Feasible for single-block launches (up to 1024 threads). Impractical for multi-block. Would be a significant patch to std.

### Option C: Avoid thread_local Entirely

**Concept**: Audit all thread_local usage in std and bypass each one, similar to how `io_stdio.patch` already bypasses OnceLock/ReentrantLock for println!.

**Known thread_local users in std**:
1. **stdio** (`io/stdio.rs`): Already bypassed by `io_stdio.patch` — writes directly through PAL Stdout.
2. **panic infrastructure** (`panicking.rs`): Uses `thread_local!` for panic count and panic hook. Panic count tracks recursive panics (panic-in-panic → abort). On GPU, a panic already calls `abort()` (trap instruction), so recursive panic detection is moot.
3. **HashMap random seed** (`collections/hash/map.rs` → `sys/random`): Uses `thread_local!` for the random seed cache. The `sys_random_mod.patch` routes to `unsupported`, which means `HashMap::new()` will **panic** at runtime ("not supported on this platform"). This is a known gap but not a thread_local issue — it fails even in single-thread.
4. **thread::current()** / thread name: Returns thread info. Stubbed via pthread stubs, irrelevant.
5. **LocalKey** destructor list: The `no_threads` path maintains a destructor list as a static. With multi-thread, destructors from different threads would collide. But since GPU threads don't exit, destructors never run anyway.

**Bypass strategy**:
- Panic count: Add a `#[cfg(target_arch = "nvptx64")]` bypass that always returns 0 (first panic → abort, no recursion tracking needed since abort is immediate)
- HashMap seed: Already handled by `unsupported` random — HashMap panics regardless. Could provide a fixed seed (no security concern on GPU).
- Other thread_locals: Most are for features that don't apply to GPU (signal handling, thread parking).

**Verdict**: Most pragmatic approach. The io_stdio bypass is already a proven pattern. Additional bypasses for panic count and HashMap seed would cover the remaining cases. Does NOT make thread_local "work" in general — user code using `thread_local!` would still get a shared global. But std internals would be safe.

### Option D: Accept Single-Thread Limitation

**Concept**: Document that `std` on GPU requires single-thread launch. Multi-thread GPU code should use `no_std` + `gpu-runtime` (the existing 65+ kernels in `gpu-kernel` work fine with multi-thread).

**Rationale**:
- The primary use case for std on GPU is "scripting" — one GPU thread doing I/O operations (file read/write, print, stdin) that are inherently serial via hostcall
- Multi-thread GPU compute doesn't need std — it uses `no_std` + inline PTX + shared memory
- The 65+ kernels in `gpu-kernel` demonstrate that serious GPU compute works perfectly without std
- Fixing ThreadLocal for multi-thread is significant effort with diminishing returns

**What this means**:
- `gpu-kernel-std` stays single-thread only
- `gpu-kernel` (no_std) handles multi-thread compute
- README updated with clear single-thread limitation
- real-std epic success criteria amended to explicitly state single-thread scope

**Verdict**: Lowest effort, highest pragmatism. The question is whether this is acceptable for the real-std epic's goals.

## 3. Skeptic Challenges

### "Is multi-thread std on GPU even useful?"

**Answer: Probably not.** Consider what std provides on GPU:
- `println!` → hostcall PRINT → serial (one message at a time through the hostcall buffer)
- `std::fs::File` → hostcall OPEN/READ/WRITE → serial (host filesystem is serial)
- `Vec`, `String`, `Box` → bump allocator → would need atomics for concurrent alloc
- `stdin` → hostcall STDIN → serial
- `format!` → heap allocation → same allocator issue

Every I/O operation goes through hostcall, which is fundamentally serial (CAS-based packet acquisition). Having 1024 threads all doing println! would serialize at the hostcall buffer anyway. The only benefit of multi-thread std would be having multiple threads do independent Vec/String work and then merge results — but that's better served by `no_std` + shared memory.

### "Would fixing ThreadLocal unlock real multi-thread std usage?"

**Answer: No.** Even with perfect thread_local, these remain broken:
1. **Bump allocator** (`BUMP_STATE`): Not thread_local — it's a `static mut` in gpu-libc, not in std's thread_local system. Concurrent malloc would race. Fix: use atomics (CAS on bump pointer). This is independent of ThreadLocal.
2. **errno** (`GPU_ERRNO`): Same — `static mut` in gpu-libc. Fix: thread-ID indexed array or PTX `.local`.
3. **Mutex/RwLock**: std's Mutex uses futex on Linux. The `syscall` stub returns ENOSYS. Any std code path that tries to lock a Mutex will fail. Fix: implement futex via GPU atomics (spinlock).
4. **OnceLock**: Used pervasively in std for lazy init. Already bypassed for stdio, but other users (e.g., `sys_common::thread_info`) would still hit the broken futex.

**Conclusion**: ThreadLocal is ONE of several multi-thread blockers. Fixing it alone doesn't help.

### "What about allocator thread-safety?"

The bump allocator in `gpu-libc/src/memory.rs` uses `static mut BUMP_STATE` with no synchronization:
```rust
BUMP_STATE.current = new_current as *mut u8;
```
Two threads calling `malloc` simultaneously will read the same `current`, compute overlapping `new_current` values, and return overlapping memory regions. This is a **critical data race** even before ThreadLocal is considered.

Fix: Use `AtomicU64` with `compare_exchange` (CAS) for the bump pointer. This is straightforward and would make the allocator thread-safe. Cost: ~1 CAS per allocation, negligible for bump allocator.

### "What about panic infrastructure?"

GPU panic already calls `abort()` → PTX `trap` instruction. The trap kills the entire kernel (all threads, all blocks). So:
- Panic in thread A → trap → all threads die. No partial failure.
- Recursive panic detection (panic count in thread_local) is irrelevant — first panic already traps.
- Panic hook (also thread_local) is irrelevant — no one can observe the hook on GPU.

This is actually **fine** for GPU. No fix needed.

### "What about Drop ordering and cleanup?"

On GPU, when a kernel exits (normally or via trap), all allocations are "freed" because the bump allocator heap is host-managed. The host reclaims the entire device memory allocation. So:
- Vec/String destructors running or not running doesn't matter for memory
- File handles: std::fs::File's Drop calls close(). If the kernel traps, close() never runs, and the host-side fd table leaks an entry. This is a minor issue — host could clean up all fds after kernel completion.

## 4. Other std Gaps

### HashMap: Will Panic
`sys_random_mod.patch` adds `target_os = "cuda"` to the `unsupported` path, which means `fill_bytes()` panics with "not supported on this platform". `HashMap::new()` calls `RandomState::new()` → `hashmap_random_keys()` → `fill_bytes()` → panic.

**Impact**: Any code using `HashMap` (directly or transitively) will panic at runtime. This is a silent trap — the code compiles fine but panics.

**Fix options**:
1. Provide deterministic seed (e.g., `(0, 0)` or based on thread ID). No security concern on GPU.
2. Implement random via PTX's `%clock` + thread ID for pseudo-random seeds.

### Mutex/RwLock: Will Deadlock or Error
`std::sync::Mutex` on Linux uses futex via `syscall(SYS_futex, ...)`. The stub returns ENOSYS/-1. Depending on std's error handling:
- Mutex::lock() may spin forever (if it retries on EINTR)
- Or may return an error (if it propagates the ENOSYS)
- Or may work if std's Mutex implementation falls back to spinning (unlikely for Linux target)

**Impact**: Any std code path that uses Mutex internally will break. This includes:
- `std::io::stdout()` (the non-bypassed path) uses ReentrantLock
- `once_cell::sync::OnceCell` / `std::sync::OnceLock`
- Any user code using `std::sync::*`

The `io_stdio.patch` already bypasses the Mutex for println!. Other paths are not bypassed.

### Time: Stubbed
`clock_gettime` returns ENOSYS. `std::time::Instant::now()` and `SystemTime::now()` will fail. Could be implemented via PTX `%clock64` or `%globaltimer` for elapsed time.

### Environment: Stubbed
`getenv` returns null. `std::env::var()` always returns `Err(NotPresent)`. Acceptable — no environment on GPU.

### Process: Stubbed
`fork`, `getpid` (returns 1). No process management on GPU. Acceptable.

#### P1: Atomic Bump Allocator (real-std epic, multi-thread foundation)
**Theme**: `alloc-safety` — Make bump allocator thread-safe
**Tasks**:
- `alloc-safety.1`: Investigation — measure cost of AtomicU64 CAS vs current non-atomic bump in single-thread
- `alloc-safety.2`: Implement AtomicU64 CAS bump allocator in gpu-libc/src/memory.rs
- `alloc-safety.3`: Multi-thread allocation test — launch with block_dim=(32,1,1), each thread allocates a Vec, verify no overlap

**Rationale**: Even if we accept single-thread std, making the allocator atomic is trivial (one CAS) and removes the most dangerous data race. It also unblocks future multi-thread exploration.

#### P2: errno Thread-Safety (real-std epic, multi-thread foundation)
**Theme**: `errno-safety` — Per-thread errno on GPU
**Tasks**:
- `errno-safety.1`: Investigation — test if `#[thread_local] static mut ERRNO: c_int = 0` compiles and produces `.local` in PTX output for nvptx64
- `errno-safety.2`: If #[thread_local] works, migrate GPU_ERRNO to use it. If not, implement thread-ID indexed errno array.
- `errno-safety.3`: Multi-thread errno test — concurrent file operations that set different errno values

**Rationale**: errno is the second critical data race after allocator. Independent of std's ThreadLocal — this is gpu-libc internal.

#### P3: HashMap Seed Fix (real-std epic, usability)
**Theme**: `hashmap-fix` — Provide deterministic HashMap seed for GPU
**Tasks**:
- `hashmap-fix.1`: Implement `fill_bytes()` in patched std's `sys/random/cuda.rs` using PTX `%clock64 + %tid.x` for pseudo-random, or a fixed seed
- `hashmap-fix.2`: Test `HashMap::new()` + insert/get in gpu-kernel-std

**Rationale**: HashMap is extremely common in Rust code. Having it silently panic is a trap for users.

#### P4 (OPTIONAL): Explore #[thread_local] on nvptx64 (real-std epic, research)
**Theme**: `gpu-tls` — Investigate native thread_local for CUDA
**Tasks**:
- `gpu-tls.1`: Compile `#[thread_local] static X: Cell<u32> = Cell::new(0)` for nvptx64, inspect PTX output for `.local` address space
- `gpu-tls.2`: If `.local` works, prototype a new `std/src/sys/thread_local/cuda.rs` that uses `#[thread_local]` instead of `no_threads`
- `gpu-tls.3`: Multi-thread test — each thread sets its own thread_local value, verify isolation

**Rationale**: This is the "proper" fix that would make thread_local actually work. But it's high-risk (LLVM/nvptx support uncertain) and the benefit is unclear given that std on GPU is primarily for single-thread I/O scripting.

#### NOT RECOMMENDED: Full multi-thread std
Fixing ThreadLocal alone doesn't help — Mutex/futex, OnceLock, allocator, errno all need independent fixes. The combined effort is massive and the use case is weak (multi-thread I/O on GPU serializes at hostcall anyway). The no_std kernel path already handles multi-thread compute well.
