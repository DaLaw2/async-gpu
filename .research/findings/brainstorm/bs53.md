## Epic Proposal 1: GPU-Native Concurrent Data Structures

### Title
**GPU-Native Concurrent Data Structures — Lock-Free Collections for Multi-Thread Kernels**

### Why It Matters
The project has proven that Rust's type system and inline PTX can express GPU atomics, CAS loops, and warp-cooperative patterns. But there are no reusable data structures beyond the bump allocator. Real GPU programs need work queues, concurrent hash maps, and ring buffers — all built on the atomic primitives already in `gpu-atomics`. This fills the gap between "raw atomics work" and "I can write a useful multi-thread kernel without reimplementing everything from scratch." It also stress-tests the multi-thread hardening (allocator, errno) under real contention.

### Success Criteria
1. **Lock-free work queue**: A multi-producer/multi-consumer queue in GPU global memory, usable across warps within a block. Demonstrated with a producer-consumer kernel where N threads enqueue and M threads dequeue, with no data loss.
2. **Concurrent hash map**: An open-addressing hash map using CAS for insert, supporting at least 1024 concurrent threads. Demonstrated with a kernel that inserts N unique keys and verifies all are retrievable.
3. **Warp-cooperative reduction/scan**: Reusable `warp_reduce()` and `warp_scan()` primitives using `__shfl_sync` intrinsics, packaged as library functions in a `gpu-collections` crate.
4. **Benchmark**: Side-by-side throughput comparison of the concurrent hash map vs. serial (single-thread) HashMap from std, showing the scaling behavior.

### Estimated Scope
- 3 themes (work-queue, concurrent-hashmap, warp-primitives), ~8-10 tasks
- Medium effort — builds directly on `gpu-atomics` infrastructure

### Key Technical Risks
- **Memory reclamation**: Lock-free data structures on GPU cannot use epoch-based reclamation (no thread-local epoch counters since `#[thread_local]` is broken). Must use hazard pointers or accept leak-tolerant designs (bump allocator means all memory is reclaimed at kernel exit anyway).
- **ABA problem**: CAS on 32-bit pointers is vulnerable to ABA. PTX supports 64-bit CAS (`atom.cas.b64`), so tagged pointers (index + generation counter) can solve this, but increases complexity.
- **Hash function**: No `std::hash` available in `no_std`. Need a simple, deterministic hash (FNV-1a or similar) implemented in the crate.
- **Testing**: Verifying correctness of lock-free structures under GPU's massive parallelism is hard. Linearizability testing is impractical — rely on invariant checks (no lost items, no duplicates) over many iterations.

## Epic Proposal 2: Multi-Kernel Pipeline — Cross-Launch State & Kernel Composition

### Title
**Multi-Kernel Pipeline — Persistent State, Kernel Chaining, and Reusable GPU Libraries**

### Why It Matters
Every kernel in the project today is standalone: launch, run, exit. Real GPU applications compose multiple kernel launches — a preprocessing kernel writes results that a compute kernel reads, which writes results for a postprocessing kernel. The hostcall buffer already lives in CUDA mapped memory that persists across launches. Extending this to user data (persistent device buffers, shared state across kernel launches) would enable pipelines like: tokenize → embed → transform → decode, each as a separate Rust kernel, with zero host-side data marshaling between steps. This also opens the door to **GPU function libraries** — crates of reusable `#[no_mangle] pub extern "ptx-kernel"` functions that can be loaded and composed by the host SDK.

### Success Criteria
1. **Persistent device buffer**: Host allocates a `MappedBuffer<T>` that survives across multiple kernel launches. Kernel A writes to it, Kernel B reads from it, without host-side copy. Demonstrated with a 2-stage pipeline.
2. **Kernel composition API**: `GpuRuntime` gains a `Pipeline` builder: `.stage("kernel_a", config_a).stage("kernel_b", config_b).run(args)` that launches kernels sequentially, sharing device memory. At least one working pipeline example.
3. **Reusable GPU library crate**: A `gpu-math-lib` (or similar) crate containing common GPU functions (vector add, dot product, matrix multiply) compiled to PTX, importable by other kernel crates. Demonstrated by `gpu-kernel` calling functions defined in the library.
4. **Cross-kernel hostcall**: The hostcall buffer persists across kernel launches within a pipeline, so kernel B can do file I/O or print without re-initializing the buffer.

### Estimated Scope
- 3 themes (persistent-state, pipeline-api, gpu-library), ~9-12 tasks
- Medium-high effort — requires host-side SDK changes + kernel-side coordination

### Key Technical Risks
- **PTX linking**: CUDA's PTX JIT does not support cross-module linking. A "library" crate's PTX cannot be linked with the main kernel's PTX at the PTX level. Workaround: compile everything into a single PTX module (LTO), or use `cuModuleLoadData` per module and call across modules via function pointers (complex). The `#[inline(always)]` requirement for cross-crate GPU functions (already known) means library functions must be inlined at compile time, which is workable but constrains the design.
- **Device memory lifetime**: `cudarc` ties buffer lifetimes to the `CudaDevice`. Sharing buffers across launches is straightforward (same device), but the Rust borrow checker may fight against multiple kernel launches holding references to the same buffer. May need `unsafe` or interior mutability patterns.
- **Synchronization between kernels**: CUDA guarantees that kernel B sees kernel A's writes only if they are in the same stream (implicit synchronization) or explicit `cuStreamSynchronize`. The host SDK must enforce this ordering — incorrect ordering causes data races invisible to Rust's type system.
- **Hostcall buffer re-use**: The hostcall polling thread must be kept alive between kernel launches. Currently, `run_hostcall_blocking()` returns when the kernel exits. Need a "session" mode that keeps polling across multiple launches.

## Epic Proposal 3: GPU Debugging & Observability — printf-Level Insight into GPU Execution

### Title
**GPU Debugging & Observability — Structured Tracing, Assertions, and Post-Mortem Analysis**

### Why It Matters
Debugging GPU code is notoriously painful. `printf` debugging (via `println!`) works but is single-thread only and serial through the hostcall buffer. When a 1024-thread kernel goes wrong, there is no way to observe what happened. This project has a unique advantage: the hostcall protocol already provides a GPU→host communication channel. Building structured tracing (not just print, but timestamped, thread-identified, leveled log events) on top of this channel would be genuinely novel — no existing CUDA project offers Rust-style `tracing` on GPU. Combined with GPU-side `assert!` that reports the failing expression + thread ID to the host (instead of just trapping), this creates a debugging experience far better than raw CUDA.

### Success Criteria
1. **Structured trace events**: A `gpu_trace!("msg", key=value)` macro that emits a trace event with thread ID, block ID, warp ID, and `%clock64` timestamp to the host via a dedicated hostcall service. Host side collects and prints events in chronological order. Works with multi-thread launch (32+ threads).
2. **GPU assert with diagnostics**: A `gpu_assert!(condition, "message")` macro that, on failure, sends the assertion message + thread coordinates + expression string to the host before trapping. Host displays a formatted assertion failure (like Rust's `assert!` but with GPU context).
3. **Post-mortem dump**: When a kernel panics or asserts, the host automatically dumps the last N trace events from that block/warp, providing a "flight recorder" of what happened before the crash.
4. **Conditional tracing**: Trace events can be compiled out (`#[cfg(feature = "gpu-trace")]`) for zero overhead in release builds. Demonstrated with a kernel that runs at full speed with tracing disabled.

### Estimated Scope
- 2-3 themes (trace-protocol, gpu-assert, flight-recorder), ~7-9 tasks
- Medium effort — hostcall infrastructure exists, this is a new service + host-side collection

### Key Technical Risks
- **Hostcall bandwidth**: Each trace event requires a hostcall round-trip (CAS acquire → fill → push → host poll → respond). At ~1-2 μs per hostcall, 1024 threads each emitting 10 events = 10K hostcalls = ~10-20ms overhead. This is acceptable for debugging but not production. The `#[cfg]` gate is essential.
- **Event ordering**: GPU threads execute in arbitrary order. Timestamps from `%clock64` are per-SM, not globally ordered. Cross-SM event ordering requires `%globaltimer` (system-scope timer), which has lower resolution. Must document that event ordering is approximate across SMs.
- **Buffer overflow**: If threads emit events faster than the host can consume them, the hostcall packet pool will be exhausted. Threads will spin-wait on CAS, effectively stalling the kernel. Need backpressure or a drop policy (skip events when buffer is full).
- **Warp divergence**: If some threads in a warp hit `gpu_assert!` (and trap) while others don't, the warp is divergent. PTX `trap` kills the entire device, so partial assertion failure within a warp is not observable — the trap kills everything. This is actually fine (fail-fast), but surprising for users expecting per-thread assertion semantics.

## Comparative Analysis

| Criterion | Epic 1: Data Structures | Epic 2: Multi-Kernel Pipeline | Epic 3: Debugging & Observability |
|-----------|------------------------|-------------------------------|-----------------------------------|
| Novelty | Medium — GPU lock-free structures exist in CUDA C, but Rust type safety is new | High — Rust kernel composition with type-safe pipelines is unexplored | High — structured tracing on GPU via hostcall is genuinely novel |
| Builds on existing infra | Strong — gpu-atomics, atomic allocator | Strong — GpuRuntime, MappedBuffer, hostcall | Strong — hostcall protocol, panic handler |
| Practical value | High — directly useful for multi-thread kernels | High — enables real applications (multi-stage pipelines) | High — dramatically improves developer experience |
| Risk level | Medium — correctness verification is hard | Medium-high — PTX linking limitation is a hard constraint | Low-medium — mostly new hostcall services |
| Scope | ~8-10 tasks | ~9-12 tasks | ~7-9 tasks |

## Recommendation

**Start with Epic 3 (Debugging & Observability)**. It has the lowest risk, highest novelty, and directly improves the development experience for all future work. The trace infrastructure would also benefit Epics 1 and 2 — debugging lock-free data structures and multi-kernel pipelines is much easier with structured tracing.

**Follow with Epic 2 (Multi-Kernel Pipeline)**, which unlocks the most practical applications and makes the project feel like a real SDK rather than a collection of demos.

**Epic 1 (Data Structures)** is valuable but can be deferred — individual data structures can be built as-needed within other epics.
