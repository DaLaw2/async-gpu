## Consensus

Both agents agree on several key points:

1. **Hostcall session persistence (criterion 4) is the highest-value work** — real engineering complexity, no existing solution, clear practical benefit
2. **Windows TDR is a hard blocker for indefinitely-running persistent kernels** — 2-second default timeout, registry hack violates host env policy
3. **Cross-launch persistent state is trivially achievable** — CUDA memory persists until freed, same-stream ordering guarantees visibility
4. **GPU-driven autonomous workflow is largely already demonstrated** — file_transform_pipeline, branching_pipeline, autonomous_pipeline all show GPU-driven multi-step workflows

## Disputes & Resolution

### Criterion 1: Persistent Kernel
- **Proposer**: "Soft persistent" pattern (batch commands then exit, relaunch) avoids TDR
- **Skeptic**: Even soft-persistent is "just a regular kernel" — not genuinely persistent. Proposes "Multi-Command Kernel" instead
- **Resolution**: **Adopt skeptic's framing**. A "multi-command kernel" that processes a batch of heterogeneous commands from a command buffer is genuinely useful and TDR-safe. The command buffer protocol (host→GPU signaling) is the novel infrastructure. Drop the word "persistent" from the criterion.

### Criterion 2: Cross-Launch Persistent State
- **Proposer**: Start here (lowest risk), verify CUDA property
- **Skeptic**: This is trivially true, not research. Proposes "Typed Pipeline Builder" instead
- **Resolution**: **Adopt skeptic's counter-proposal partially**. The raw verification is too trivial, but a full typed pipeline builder is over-engineered for the current stage. Compromise: demonstrate cross-launch state AND build a minimal pipeline API (`Pipeline::new().stage(kernel_a, &buf).stage(kernel_b, &buf).run()`). The API adds real value; the raw memory persistence is the mechanism.

### Criterion 3: GPU-Driven Autonomous Workflow
- **Proposer**: Acknowledges existing demos, suggests extending with data-dependent decisions
- **Skeptic**: Already met by 3 existing kernels. Proposes data-dependent iteration (convergence loop) or multi-file orchestration
- **Resolution**: **Adopt skeptic's counter-proposal**. Replace with "data-dependent iteration loop" — a kernel that reads data, processes iteratively until a convergence condition is met, then writes results. This pattern (iterative solver, gradient descent step) is NOT demonstrated by any existing kernel and is a genuinely new autonomous capability.

### Criterion 4: Hostcall Session Persistence
- **Both agree**: This is the centerpiece of the epic
- **Skeptic adds**: Specific failure modes — leaked READY packets, race between kernel exit and listener, doorbell counter wrapping
- **Resolution**: Keep as-is, expand to be the primary theme. Address skeptic's failure modes as explicit sub-tasks.

## Revised Success Criteria

Based on synthesis, the gpu-autonomous v2 criteria should be:

1. **Multi-command kernel**: Kernel processes 3+ different command types (COMPUTE, PRINT, EXIT) from a mapped memory command buffer in a single launch. Host submits commands via atomic write_idx. TDR-safe (finite batch, not indefinite).

2. **Cross-launch pipeline**: Two kernels share a device buffer — Kernel A writes, Kernel B reads, zero host copy. Demonstrated with a minimal Pipeline API (`session.stage(kernel_a).stage(kernel_b).run()`).

3. **Data-dependent iteration**: Kernel autonomously loops — reads data, processes, checks convergence condition, decides whether to iterate again or finalize. Host only provides launch + hostcall. Pattern NOT yet demonstrated by any existing kernel.

4. **Hostcall session persistence**: HostcallSession keeps listener thread + fd table + hostcall buffer alive across multiple kernel launches. Packet pool correctly reinitialized between launches. File handles opened by Kernel A are usable by Kernel B.

## Priority Rationale

1. **hc-session** first — criterion 4 is the foundation. cmd-buffer and cross-pipeline both need session persistence. Without this, persistent kernels can't use hostcall, and cross-launch demos need per-launch buffer setup.

2. **cmd-buffer** second — the most novel component. Host→GPU command channel is new infrastructure that doesn't exist in the codebase. Depends on session persistence for hostcall integration.

3. **cross-pipeline** third — demonstrates practical value of session mode. Lower novelty but important for the "SDK feel" of the project.

4. **iter-workflow** last — builds on all prior work. The convergence loop pattern is the capstone demo of GPU autonomy.

## Key Risks

| Risk | Impact | Mitigation |
|------|--------|------------|
| Packet pool corruption across launches | High | Explicit reinit_packets() with drain-then-reset protocol |
| In-flight packets at kernel exit | High | Host waits for listener to drain ready stack before reinit |
| Command buffer race conditions | Medium | Use proven sys_* CAS pattern from hostcall protocol |
| Windows TDR on command buffer kernel | Low | Batch processing, not indefinite loop |
| cudarc API limitations for pipeline | Low | Raw CUDA driver API via cudarc::driver::sys if needed |
