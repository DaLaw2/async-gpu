# BS56 — Synthesis: Aligning `#[warp_async]` with Rust Native `async/await`

**Level**: Deep (proposer + skeptic)
**Epic**: gpu-autonomous v3
**Cycle**: 232
**Date**: 2026-03-14

---

## Consensus

Both proposer and skeptic agree on these points:

1. **WarpFuture and core::future::Future are fundamentally incompatible** — SIMT lockstep (32 lanes sharing state) vs independent per-thread progress. No syntax sugar bridges this at the semantic level.

2. **rustc modification is impractical** — 3-6 months minimum, near-zero upstream acceptance, LLVM nvptx backend has no warp concept so compiler-generated warp-cooperative code could be silently broken by optimizations.

3. **`.await` on GPU is primarily cosmetic** — the real value isn't in the syntax but in the execution model. `warp_print!(buf, b"msg")` vs `gpu_print(buf, b"msg").await` is negligible difference.

4. **Single-thread Embassy async is proven but has limited value** — `async-hostcall-test` already demonstrates this. Nobody has reused it since, suggesting the approach was found insufficient for real workloads.

## Unresolved Disputes

### Should we build async-io (Approach A)?

- **Proposer**: Yes — delivers real `.await`, composable Futures, 90% of the dream at 2-3 weeks cost
- **Skeptic**: No — single-thread async on GPU is strictly worse than synchronous std, which already works. Creates a confusing 3-way API surface (sync std / async wrapper / warp_async)

**Resolution**: Skeptic is more convincing here. The async-hostcall-test crate already proved this works but wasn't reused — strong signal that the approach lacks practical value.

### What should the next direction be?

- **Proposer**: async-io theme (immediate) + rustc-research theme (strategic)
- **Skeptic**: Improve `#[warp_async]` (error propagation, composition, iterators) + explore multi-warp synchronous hostcall

**Resolution**: Skeptic's counter-proposal is stronger because it:
1. Extends a working, proven system instead of building a parallel one
2. Multi-warp synchronous hostcall could make async unnecessary entirely
3. `?` operator in `#[warp_async]` closes the biggest ergonomic gap

### Is rustc research worth investigating?

- **Proposer**: Yes — 2 investigation tasks to map the coroutine transform pipeline
- **Skeptic**: LLVM's nvptx backend can't emit warp-cooperative code; compiler research is wasted effort

**Resolution**: A lightweight investigation (1 task, not a theme) is worthwhile — understanding the compiler pipeline informs whether this project's long-term goal is achievable. But do NOT invest in implementation.

## Decision

**Direction**: Improve `#[warp_async]` + explore multi-warp synchronous hostcall

### Theme 1: `warp-ergonomics` (gpu-autonomous v3)
**Goal**: Make `#[warp_async]` more expressive — error propagation, nested calls, compute blocks
**Success criteria**:
1. `?` operator works in `#[warp_async]` — hostcall errors propagate as `Result`
2. Nested warp_call: one `#[warp_async]` fn calls another
3. Arbitrary compute code between hostcall points (not just if/match/loop)

### Theme 2: `multi-warp-sync` (gpu-autonomous v3)
**Goal**: Multi-warp synchronous hostcall — each warp blocks independently, CUDA schedules concurrency
**Success criteria**:
1. 4+ warps each do synchronous `println!()` concurrently (no async, no executor)
2. Warp-level synchronous file I/O (open/write/read) with hostcall buffer handling concurrent requests
3. If this works: document that async is unnecessary for warp-level concurrency

### Theme 3: `rustc-survey` (gpu-autonomous v3) — lightweight
**Goal**: Map rustc's `async fn` → coroutine → state machine pipeline, assess feasibility
**Success criteria**:
1. Document the exact MIR transform files and insertion points
2. Write a 1-page feasibility assessment (not a full ADR)

### Priority
1. **multi-warp-sync** — highest impact. If multi-warp synchronous hostcall works, it eliminates the need for async entirely and validates the "hostcall-as-syscall" model
2. **warp-ergonomics** — closes the biggest UX gap in the current system
3. **rustc-survey** — informational only, lowest priority

## Key Insight

The skeptic's "hostcall-as-syscall" framing is the most important insight: instead of making GPU async look like CPU async, treat hostcalls as blocking system calls where CUDA's warp scheduler provides concurrency automatically. This is already how the synchronous std path works for single-thread — the question is whether it scales to multi-warp. If yes, the entire async abstraction layer may be unnecessary for I/O-bound GPU code.
