# BS57 — Synthesis: Warp-Cooperative Async via rustc Modification

**Level**: Deep (proposer + skeptic)
**Epic**: gpu-autonomous v3 / native-warp-async
**Cycle**: 232
**Date**: 2026-03-14

---

## The Key Insight (Proposer)

**Warp cooperation is a property of the CALLER's state machine, not of the individual futures being awaited.**

This means:
- Inner futures (`GpuFile::create()`, `gpu_println()`) are standard `impl Future` — no warp knowledge needed
- The OUTER async fn is marked `#[warp_cooperative]`
- The compiler (or proc macro) generates a state machine where:
  - Lane 0 polls inner futures
  - Results are broadcast to all lanes via `shfl.sync`
  - All lanes agree on state transitions via discriminant broadcast
  - `syncwarp` barriers enforce convergence

This is architecturally identical to what `#[warp_async]` does today, but with a crucial difference: inner operations don't need to be warp-aware macros.

## Consensus

1. **LLVM problem is not real** — 40+ tests confirm LLVM treats inline asm as opaque barriers. No warp-cooperative code has ever been broken by LLVM optimizations.

2. **The minimal rustc change is ~1000 lines** — `#[warp_cooperative]` attribute + post-StateTransform MIR pass. No existing compiler code modified.

3. **Phased approach is correct** — prove manually first, then proc macro, then rustc fork. Each phase is independently valuable.

4. **The recommended approach is Option D** (attribute-driven) — `#[warp_cooperative]` triggers the pass only for annotated async fns.

## Technical Risks (Skeptic)

| Challenge | Severity | Resolution |
|-----------|----------|------------|
| MIR can't directly emit PTX | Medium | Use function calls to `gpu_atomics` intrinsics, mark as lang items (~2-3 weeks) |
| State struct broadcasting (multi-word, overlapping) | **High** | Minimal approach: broadcast discriminant only, data stays in lane 0. Full approach: per-state field liveness analysis (4-8 weeks) |
| Pin + self-referential state | Low | Non-leader lanes never dereference broadcast pointers — constrained but safe |
| Drop glue | Medium | Restrict warp-cooperative futures to run-to-completion (acceptable for GPU) |
| Nested .await composition | **High** | MIR pass must handle nested state machines recursively (2-3 weeks) |
| Fork cost (~5 months + 3 months/year) | Strategic | Acceptable for research proof; proc macro remains production path |

## Decision: Three-Phase Plan

### Phase 1: Manual Proof (1-2 weeks) — THE CRITICAL EXPERIMENT

Write BY HAND:
1. `GpuPrintFuture` as a standard `impl Future` (per-thread, no warp knowledge)
2. A warp-cooperative wrapper that polls it from lane 0, broadcasts `Poll` result
3. Chain two futures in a hand-coded warp-cooperative state machine
4. Add `Result<T, E>` with `?`-style error broadcasting

**If this works**: the concept is proven. Both proc macro and rustc paths are viable.
**If this fails**: we learn exactly where warp cooperation breaks with standard futures.

### Phase 2: Enhanced Proc Macro (2-3 weeks)

Extend `#[warp_async]` to:
- Accept `async fn` syntax with `.await`
- Support `?` operator for error propagation
- Generate WarpFuture from `.await` expressions (same state machine as today)

This is the pragmatic production path regardless of Phase 3.

### Phase 3: rustc Fork (2-4 months, after Phase 1-2 succeed)

Minimal spike first (2-3 weeks):
- Fork rustc, implement discriminant-broadcast + syncwarp for a single-yield async fn
- If spike succeeds → full implementation
- If spike reveals blockers → stop, document findings

Full implementation:
- `#[warp_cooperative]` attribute + `WarpCooperativeTransform` MIR pass
- Intrinsic plumbing (shfl_sync, syncwarp, lane_id as lang items)
- Handle nested .await, error propagation
- Integration test on real GPU hardware

## Target Syntax (Level 3)

```rust
#[warp_cooperative]
async fn gpu_pipeline(buf: *mut u8) -> Result<(), GpuIoError> {
    gpu_println(buf, b"start").await;
    let fd = GpuFile::create(buf, "data.txt").await?;
    fd.write_all(buf, b"GPU output").await?;
    fd.close(buf).await?;
    gpu_println(buf, b"done").await;
    Ok(())
}
```

- `async fn` is REAL — compiler generates real `impl Future` state machine
- `.await` is REAL — standard Rust desugaring
- `?` works naturally
- `#[warp_cooperative]` triggers the MIR pass that adds warp synchronization
- Inner futures (`GpuFile`, `gpu_println`) are standard `impl Future`

## Key Insight

The difference between this project and CUDA C++ is fundamental: CUDA provides cooperative groups as a library API within a C++ framework. This project proposes making warp cooperation a COMPILER CONCERN — the compiler understands SIMT semantics and generates correct code automatically. No other language has done this. If successful, this is a genuine contribution to programming language design for heterogeneous computing.
