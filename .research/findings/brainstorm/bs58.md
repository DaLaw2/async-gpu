## Technical Analysis

### What the Discovery Actually Means

rustc-warp.1 proved: `async fn` → PTX works with zero modifications. LLVM fully optimizes the state machine (constant-folded to a single store in the trivial case). This eliminates the concern that LLVM's nvptx backend cannot handle coroutine-generated code.

However, this does NOT simplify the core problem:

**The hard part was never compilation — it was warp-cooperative execution.**

Standard async fn generates a per-thread state machine. For warp cooperation, you need:
1. Lane 0 polls the future (exclusive execution)
2. Discriminant broadcast via shfl.sync (all lanes agree on state)
3. Per-state field broadcasting (only live fields, decomposed to 32-bit chunks)
4. syncwarp barriers at yield points
5. Conditional field liveness analysis on the transformed MIR

The proc macro (#[warp_async]) already does all of this for the patterns it supports. The rustc MIR pass would generalize it to arbitrary control flow.

### Constraint Analysis for Each Option

**Option A: Full rustc fork**
- Minimum viable: ~3 months (intrinsic plumbing: 2-3 weeks, state broadcast: 4-8 weeks, nested .await: 2-3 weeks, integration: 2 weeks)
- Ongoing cost: ~3 months/year maintenance (nightly breakage, MIR representation changes)
- Host policy consideration: User would need to install custom toolchain, but CLAUDE.md says "MUST NOT modify anything outside this repository." A rustc fork stored as patches inside the repo (rustc-patches/) with a build script could comply.
- The result is a research artifact proving compiler-level SIMT async is feasible.

**Option B: Proc macro evolution**
- Already 80% done (#[warp_async] with .await and ? operator)
- Remaining work: async fn keyword recognition, nested .await, more complex control flow
- Limitation: cannot handle arbitrary patterns (loops with .await, match arms with .await, trait objects)
- But: covers 90%+ of practical GPU async patterns (sequential .await chain with error handling)
- Time estimate: 2-3 weeks for meaningful improvements

**Option C: Hybrid — MIR study + design doc**
- Write the MIR transformation specification (rustc-warp.2) without building the fork
- Manually construct the before/after MIR for representative async fns
- Document exactly where shfl.sync/syncwarp would be inserted
- Proves theoretical feasibility, guides future implementation
- Time estimate: 1-2 weeks

**Option D: Pivot to remaining epics**
- real-std multi-thread: thread-ID-indexed ThreadLocal replacement (2-3 weeks)
- codebase-health: workspace consolidation, build automation (1-2 weeks)
- public-api: PTX build automation (1 week)
- Does not close native-warp-async or gpu-autonomous's final criterion

## Skeptic Challenges

### Challenge 1: The proc macro IS the practical solution

The #[warp_async] proc macro already handles:
- async fn syntax with .await
- ? operator for error propagation
- Sequential .await chains
- Result broadcasting

A rustc fork adds generality (loops, nested async, trait objects) that GPU kernels rarely need. GPU async patterns are overwhelmingly sequential: open → read → process → write → close. The proc macro handles this. The fork is a massive investment to handle edge cases.

**Untested assumption**: That users actually need arbitrary control flow in warp-cooperative async fns. No evidence supports this. All demonstrated use cases are sequential chains.

### Challenge 2: MIR pass state broadcasting is genuinely hard

BS57-skeptic identified this correctly: the MIR pass must:
- Decompose arbitrary types into 32-bit shfl.sync chunks
- Perform per-state field liveness analysis on the TRANSFORMED MIR
- Handle overlapping storage from compute_storage_conflicts()
- Know which fields are "leader-only" vs "all-lanes"

This is 4-8 weeks of compiler engineering for a problem the proc macro sidesteps entirely (the programmer specifies what to broadcast by using warp_print!, warp_file!, etc.).

**Untested assumption**: That automatic field liveness analysis can be made correct without false positives (broadcasting fields that don't need it) or false negatives (missing broadcasts). The proc macro is correct by construction because the programmer explicitly chooses broadcast points.

### Challenge 3: Fork maintenance is a real cost

rustc changes the MIR representation regularly. A fork targeting StateTransform will break on roughly every other nightly release. Rebase cost is ~1-2 days per breakage. At ~6 breakages per year, that's 12-24 person-days annually just for maintenance.

**Untested assumption**: That a fork can be maintained alongside the project's other research goals. The project has historically been solo-researcher scale — adding compiler maintenance may crowd out other work.

### Challenge 4: "Research complete, implementation deferred" is a valid outcome

The three-phase plan from BS57 was designed to produce independent value at each phase:
- Phase 1 (DONE): Proved standard Future can be polled warp-cooperatively
- Phase 2 (DONE): Practical tool for writing warp-cooperative async code
- Phase 3 (NOT DONE): Theoretical completeness — "a compiler CAN do this automatically"

Phase 3's value is primarily academic. If the goal is a working system, Phase 2 already provides it. If the goal is a research contribution ("first compiler-level SIMT async"), Phase 3 is necessary but Phase 2 is a sufficient demonstration of the concept.

### Challenge 5: real-std multi-thread may be more impactful

ThreadLocal on GPU is a real unsolved problem with practical consequences. Every std feature (println!, File, etc.) is currently single-thread-only. Solving this with thread-ID-indexed arrays would:
- Make all std features work with multi-thread launches
- Remove the biggest caveat in the project
- Be directly useful (not just a research proof)

This may deliver more practical value per hour than a rustc fork.

## Concrete Recommendations

### Recommendation 1: Complete the MIR spec (Option C) — serves native-warp-async, gpu-autonomous

**Do**: rustc-warp.2 — Write the MIR transformation specification for a 2-yield async fn. Document:
- Input MIR (standard StateTransform output)
- Output MIR (with shfl.sync calls, syncwarp barriers, discriminant broadcast)
- The state broadcasting algorithm (discriminant-first, conditional field broadcast)
- Where the transformation is impossible (self-referential state, trait objects)

**Rationale**: This closes the research question "could a compiler do this?" with a concrete specification, not just hand-waving. It's the minimum work to make the native-warp-async and gpu-autonomous epics' final criterion "research complete" rather than "abandoned." Cost: 1-2 weeks.

**Priority**: HIGH. This is the cheapest way to add substance to the final criterion.

### Recommendation 2: Skip the rustc fork (Option A) — defer indefinitely

**Skip**: rustc-warp.3 through rustc-warp.5. Mark as "deferred — research specification complete, implementation out of scope for current project."

**Rationale**: 3+ months of compiler engineering plus ongoing maintenance, for a feature the proc macro already provides practically. The MIR spec (Recommendation 1) proves the concept theoretically. The proc macro (Phase 2) provides it practically. The fork adds implementation proof but at disproportionate cost.

**Exception**: If the user explicitly wants the fork as a research deliverable (e.g., for a paper or thesis), this recommendation reverses.

### Recommendation 3: Fix real-std multi-thread — serves real-std

**Do**: New theme `std-multithread` with tasks:
- `std-multithread.1`: Design thread-ID-indexed ThreadLocal replacement for gpu-libc
- `std-multithread.2`: Implement ThreadLocal using tid-indexed array (reuse errno pattern)
- `std-multithread.3`: Test all std features (println, File, Vec) with multi-thread launch (32,1,1)

**Rationale**: This is the biggest remaining gap in real-std. All 5 criteria are surface-level met but single-thread-only. Thread-ID-indexed arrays are proven (already used for errno). The pattern is straightforward. Cost: 2-3 weeks. Impact: removes the biggest caveat in the entire project.

**Priority**: HIGH. More practical impact than any Phase 3 work.

### Recommendation 4: Enhance proc macro incrementally (Option B, partial) — serves native-warp-async

**Do**: If time permits after Recommendations 1 and 3, extend #[warp_async] to handle:
- `warp-async-v2.5`: Nested .await (chained futures returning futures)
- `warp-async-v2.6`: Loop with .await (bounded iteration with async body)

**Rationale**: These are the most-requested patterns after sequential chains. They make the proc macro more useful without the cost of a compiler fork. Each is an independent, testable improvement.

**Priority**: MEDIUM. Nice-to-have, not blocking any epic criterion.

### Recommendation 5: Leave gpu-perf, codebase-health, public-api as-is

**Skip**: No new work on gpu-perf (parked criteria are justified), codebase-health (working but imperfect), or public-api (nearly complete).

**Rationale**: These epics are at diminishing returns. The remaining gaps are either out-of-scope (gpu-perf quantization) or low-impact (workspace consolidation, PTX build automation). Focus should be on the two high-value items: MIR spec and multi-thread std.

**Priority**: LOW (evergreen, address opportunistically).

## Decision on Epic Criteria

After the MIR spec (Recommendation 1), the native-warp-async and gpu-autonomous epics would have their final criterion in one of two states:

**Option I: Reword criterion** — Change "#[warp_cooperative] async fn compiles via rustc MIR pass and runs on GPU" to "#[warp_cooperative] async fn MIR transformation specified and proven feasible; implementation deferred." This acknowledges the research contribution without requiring the fork.

**Option II: Keep criterion, mark as deferred** — Leave the criterion as-is but note that Phase 3 implementation is out of scope. The spec is a stepping stone, not a completion.

**Recommendation**: Option I (reword). The spec IS the research deliverable. The implementation is engineering, not research. The research question ("can a compiler automatically generate warp-cooperative state machines from standard async fn?") is answered by the spec, not the implementation.

This is ultimately the user's decision — only the user can close epics.
