## 1. Gap Analysis

### 1.1 What's Missing for External Usefulness

| Gap | Severity | Why it matters |
|-----|----------|----------------|
| **No AMD/Intel GPU support** | High | NVIDIA-only limits audience to ~60% of discrete GPU market. ROCm and oneAPI both have HIP/SYCL backends that could theoretically host the hostcall protocol. |
| **No crates.io publishable crate** | High | Users cannot `cargo add gpu-host` — the project requires cloning the repo and manually building PTX. This is the single biggest adoption barrier. |
| **No multi-GPU or multi-kernel concurrency** | Medium | Real workloads distribute across multiple devices. Current architecture assumes one GPU, one kernel at a time (HostcallSession is single-device). |
| **Networking stubs** | Medium | `std::net` is stubbed — GPU kernels cannot make HTTP requests or open sockets. For autonomous compute, network I/O is the natural next step after file I/O. |
| **No async runtime interop** | Medium | Host side uses raw threads for hostcall polling. No integration with tokio/async-std — host programs cannot `await` GPU completion ergonomically. |
| **Thread spawning stubbed** | Low | `std::thread::spawn()` doesn't work on GPU. Multi-thread launches work, but dynamic thread creation is impossible (CUDA limitation, not a fixable gap). |
| **f32-only compute kernels** | Low | No f16/bf16 inference path. PARKED in gpu-perf for good reason (requires quantization-aware calibration), but limits practical ML inference performance. |

### 1.2 README Limitations That Could Be Addressed

| Limitation | Addressable? | Effort | Impact |
|------------|-------------|--------|--------|
| **Nightly Rust required** | No — `asm_experimental_arch`, `-Zbuild-std` are nightly-only. No path to stable without upstream changes. | — | — |
| **NVIDIA only** | Partially — SPIR-V backend exists for `rustc_codegen_spirv` (rust-gpu). Hostcall protocol is vendor-agnostic in principle. A SPIR-V port would need a different mapped-memory mechanism. | 3-6 months | High but speculative |
| **Hostcall latency ~20-100us** | Partially — batched hostcalls (multiple operations per packet) could amortize overhead. Persistent mapped memory reduces setup cost. Kernel-side buffering (accumulate N prints, flush once) is straightforward. | 2-3 weeks | Medium |
| **Uniform I/O (warp-level)** | Yes — per-lane I/O via lane masking + per-lane packet allocation. But this fundamentally changes the hostcall packet model (32x packets instead of 1). | 4-6 weeks | Low (niche use case) |
| **Partial std** | Yes — `std::net` via hostcall (TCP connect/read/write as new service IDs) is architecturally identical to file I/O. | 3-4 weeks | Medium |
| **f32 only** | Not without external tooling — quantization-aware weight conversion is a data pipeline problem, not a kernel problem. | N/A | PARKED |

### 1.3 Architectural Gaps

1. **Error recovery**: When a hostcall fails mid-pipeline, the GPU kernel currently has no way to retry or fall back. The error propagates up, but there's no `try` block equivalent at the warp level.

2. **Resource cleanup**: GPU file descriptors opened via hostcall rely on the host's drop-on-session-close. If a kernel panics after opening 10 files, cleanup happens implicitly — but there's no destructor protocol for GPU-allocated resources.

3. **Observability in production**: `gpu_trace!` compiles out in release. There's no "structured logging at low overhead" mode — it's either full tracing or zero observability.

4. **Build reproducibility**: Multiple Cargo.lock files across crates (gpu-libc, gpu-std-test, gpu-kernel-std, embassy-test) suggest the build isn't fully hermetic. Different crates could resolve different dependency versions.

## 2. Technical Opportunities

### 2.1 Directions That Leverage Existing Infrastructure

**A. GPU Networking via Hostcall**
The hostcall protocol already handles file I/O (open/read/write/close). Adding TCP socket operations (connect/send/recv/close) would reuse the exact same infrastructure: new service IDs in `gpu-protocol`, new handlers in `gpu-host/hostcall.rs`, new warp macros in `gpu-runtime`. The GPU kernel could make HTTP requests, query databases, or stream data — all from within a single kernel launch.

- Builds on: hostcall protocol, sideband buffer, `#[warp_async]`
- Serves: gpu-autonomous (extends autonomy to network), public-api (new capability)
- Risk: Latency — network round-trips are 1-100ms, which dwarfs hostcall overhead. But that's actually fine: the GPU issues the request and does compute while waiting.

**B. Host-Side Async Integration (tokio interop)**
Currently, the host polls hostcall buffers on a dedicated thread. Wrapping this in a tokio-compatible `Future` would let host programs write:
```rust
let result = gpu.launch_kernel("my_kernel").await;
```
This is a host-side-only change — no GPU code modifications needed. It makes the SDK feel modern and composable with existing Rust async ecosystems.

- Builds on: gpu-host SDK, HostcallSession
- Serves: public-api (ergonomics), codebase-health (modern API patterns)
- Risk: Low — this is well-understood Rust async wrapping

**C. Batched Hostcall Protocol**
Instead of one operation per packet round-trip, allow the GPU to queue N operations in a single packet (or sideband buffer) and submit them as a batch. This amortizes the 20-100us latency across multiple operations. Particularly useful for patterns like "print 10 debug lines" or "open file, write header, write N records, close file."

- Builds on: hostcall protocol, sideband buffer
- Serves: gpu-perf (reduces I/O overhead), gpu-autonomous (more efficient pipelines)
- Risk: Medium — changes packet format, needs backward compatibility

**D. Publishable Crate Split**
Restructure for crates.io publication: `gpu-host` as the user-facing SDK, `gpu-runtime` + `gpu-protocol` as internal dependencies, `gpu-kernel` as an example/template crate. Requires resolving the multi-Cargo.lock issue and making the PTX build step automatic (build.rs already exists for examples).

- Builds on: existing crate structure, build.rs pattern from examples
- Serves: public-api (primary criterion), codebase-health (workspace consolidation)
- Risk: Low-medium — mostly packaging/build system work

### 2.2 Cross-Cutting Improvements

**E. Structured Release-Mode Observability**
A lightweight `gpu_log!` macro that writes structured events to a ring buffer in device memory (not via hostcall). Host reads the buffer after kernel completion. Zero hostcall overhead, survives panics, always-on. Different from `gpu_trace!` which uses hostcall and compiles out.

- Builds on: gpu-debug infrastructure, mapped memory
- Serves: gpu-debug (if reopened), public-api (production-ready debugging)
- Risk: Low — ring buffer in device memory is a well-known pattern

## 3. Skeptic Challenges

### 3.1 What's Actually Worth Pursuing

| Direction | Worth it? | Reasoning |
|-----------|-----------|-----------|
| **GPU Networking** | **Probably not yet** | The project has no users requesting this. Adding TCP to a research project that isn't published on crates.io means building features nobody can consume. Fix distribution first, then add capabilities. |
| **Host async (tokio)** | **Yes** | Low effort (1-2 weeks), high ergonomic impact, makes the SDK feel production-grade. Every Rust developer expects `.await` on the host side. This is table-stakes for adoption. |
| **Batched hostcall** | **Maybe** | Performance improvement on an already-fast path. The 20-100us latency is dominated by CUDA mapped memory synchronization, not packet format overhead. Batching may only save 10-30% per operation. Worth prototyping but don't build a full protocol extension. |
| **Publishable crate** | **Yes, highest priority** | This is the difference between "research project on GitHub" and "tool others can use." The project's README is impressive but if `cargo add gpu-host` doesn't work, adoption is effectively zero. |
| **Release-mode observability** | **Maybe** | Nice-to-have for debugging production GPU code. But the project doesn't have production users yet. Solve distribution first. |
| **Multi-GPU** | **No** | Massive engineering investment, unclear demand, and the project doesn't even have single-GPU users yet (no published crate). |
| **SPIR-V / AMD port** | **No** | 3-6 months minimum, requires a completely different memory mapping mechanism, and `rust-gpu` (SPIR-V) has its own ecosystem. Wrong time. |

### 3.2 Risk/Reward Assessment

| Direction | Effort | Reward | Risk | Net |
|-----------|--------|--------|------|-----|
| Publishable crate | 3-4 weeks | Enables all future adoption | Build system complexity | **High net positive** |
| Host tokio interop | 1-2 weeks | Modern API, composable host code | Minimal — well-understood pattern | **High net positive** |
| Batched hostcall | 2-3 weeks | 10-30% I/O latency reduction | May not measurably improve real workloads | **Neutral** |
| GPU networking | 3-4 weeks | New capability class | No users to benefit; premature | **Low net positive** |
| Release observability | 1-2 weeks | Better debugging | No production users yet | **Low net positive** |

### 3.3 The Hard Truth

This project has achieved extraordinary research results — 247 tasks, GPT-2 inference in pure Rust PTX, warp-cooperative async/await, real std on GPU. But it faces the classic research-to-product gap:

1. **No external users** — the project is not consumable as a library
2. **No stable API contract** — internal refactors can break everything
3. **No CI beyond local scripts** — `ci-lint.sh` is manual
4. **Documentation is research-oriented** — README reads like a thesis, not a quickstart

The highest-leverage work is NOT adding new GPU capabilities. It's making the existing capabilities usable by someone who isn't the original author.

## 4. Concrete Recommendations

### Theme 1: `publish-ready` — Publishable Crate on crates.io
**Epic**: public-api
**Priority**: 1 (highest)
**Rationale**: The single biggest barrier to project impact. Everything else is premature optimization of a product nobody can install.

| Task | Kind | Title |
|------|------|-------|
| publish-ready.1 | design | Design crate split for crates.io — what's published vs internal, semver strategy, feature flags |
| publish-ready.2 | experiment | Consolidate workspace — single Cargo.lock, resolve multi-lock fragmentation |
| publish-ready.3 | experiment | Implement build.rs PTX automation — user runs `cargo build` and gets a working binary |

**Success criteria**:
1. `cargo add gpu-host` installs the SDK from crates.io (or from git path as intermediate step)
2. Single `cargo build` compiles host + kernel PTX for a new project using gpu-host as dependency
3. All crates share one workspace Cargo.lock

### Theme 2: `host-async` — Host-Side Async/Await Integration
**Epic**: public-api
**Priority**: 2
**Rationale**: Low effort, high ergonomic impact. Makes the host SDK composable with the Rust async ecosystem. Every modern Rust project uses tokio or async-std.

| Task | Kind | Title |
|------|------|-------|
| host-async.1 | design | Design async API surface — `gpu.launch(kernel).await`, `Stream<HostcallEvent>`, cancellation |
| host-async.2 | experiment | Implement tokio-compatible GPU launch future — wrap hostcall polling in `impl Future` |

**Success criteria**:
1. Host program can `gpu_runtime.launch_kernel("name", &args).await` inside a tokio runtime
2. Hostcall events can be consumed as an async `Stream`
3. GPU kernel launch + hostcall handling coexists with other tokio tasks (no thread monopolization)

### Theme 3: `batched-hc` — Batched Hostcall Protocol (stretch goal)
**Epic**: gpu-perf
**Priority**: 3 (only if themes 1-2 complete)
**Rationale**: Addresses the hostcall latency limitation with a concrete, measurable improvement. Worth prototyping to see if the overhead reduction is meaningful.

| Task | Kind | Title |
|------|------|-------|
| batched-hc.1 | investigation | Profile hostcall latency breakdown — where does 20-100us actually go? (CAS contention vs mapped memory vs host processing) |

**Success criteria**:
1. Latency breakdown identifies whether batching would help (if 80%+ is per-round-trip fixed cost, batching helps; if it's per-byte processing, it doesn't)

## Key Insight

The project has reached the "research complete, productization needed" inflection point. The technical achievements are genuinely impressive — no other project has Rust async/await on GPU with warp-cooperative state machines, real std, and full GPT-2 inference. But impressive technology without distribution is a tree falling in an empty forest. The highest-leverage work for the next cycle is making this consumable, not making it more capable.
