## Technical Analysis

### Where spin-wait lives (the core problem)
The I/O call chain on GPU:
```
println!("hello")
  → std::io::Stdout::write()        [patched std PAL: sys_stdio_cuda.rs]
    → gpu_stdout_write()             [gpu-kernel-std: extern "C" bridge]
      → gpu_runtime::hostcall::gpu_hostcall_request()  [gpu-runtime]
        → spin-wait loop (sys_spin_load_acquire_u32)   ← THIS IS THE BLOCKER
```

For File I/O:
```
File::create("x.txt")
  → std::sys::fs::cuda::File::open() [patched std PAL: sys_fs_cuda.rs]
    → open()                          [gpu-libc: hostcall_io.rs]
      → gpu_runtime::hostcall::gpu_hostcall_request()
        → spin-wait loop              ← SAME BLOCKER
```

The spin-wait is in `gpu_runtime::hostcall::gpu_hostcall_request()` (lib.rs:306-327).
It polls `CONTROL_READY` flag up to `GPU_MAX_SPIN` (10M) iterations.

### Making it yield-capable
Two approaches:

**Approach A: Async hostcall at gpu-runtime level**
- Add `gpu_hostcall_request_async()` that returns `impl Future` instead of spinning
- The future checks `CONTROL_READY` once per poll, returns `Pending` if not ready
- PAL layer calls this async version when in warp-cooperative context
- Problem: PAL functions (`Stdout::write`, `File::open`) are sync — they return `io::Result`, not `Future`

**Approach B: Coroutine-aware spin-wait (yield from inside spin loop)**
- The MIR pass already inserts yield points at `.await` boundaries
- Instead of making PAL async, make the spin-wait itself yield-aware
- When `#[warp_cooperative]` context is detected, the spin loop calls a yield intrinsic
- This is transparent to PAL — `write()` still returns `io::Result`
- Implementation: replace spin loop with `loop { check; if !ready { yield_to_warp(); } }`
- `yield_to_warp()` = `bar.warp.sync` (let other warps run)

**Approach B is much simpler** — no need to change PAL signatures, no async plumbing through std.
The question is: does `bar.warp.sync` actually help? It synchronizes lanes within a warp but doesn't yield to the scheduler. `nanosleep` might be better for yielding GPU cycles.

**Approach C: Hybrid — keep sync PAL, but warp-cooperatively batch the hostcall**
- Under `#[warp_cooperative]`, all 32 lanes reach `println!()` together (thanks to MIR pass)
- Lane 0 does the actual hostcall, other lanes wait via `bar.warp.sync`
- This is already what `warp_print!` does — 1 hostcall per warp instead of 32
- The MIR pass ensures convergence at each `.await` → sync I/O is fine if warp-batched

**Approach C is the most practical for the first milestone.** It matches the user's vision:
standard `println!()` becomes warp-cooperative automatically. The key insight is that
the MIR pass already ensures all lanes reach the same point — we just need the I/O
implementation to detect "I'm in a warp-cooperative context" and batch accordingly.

### Detection mechanism: "am I in warp-cooperative context?"
Options:
1. **Global flag** set at kernel entry: `static WARP_COOPERATIVE: bool`
2. **Per-warp runtime check**: if `activemask() == 0xFFFFFFFF`, we're converged
3. **Compile-time**: different PAL functions linked depending on kernel type
4. **MIR pass inserts context**: the pass could inject a thread-local flag

Option 2 is simplest and requires zero compiler changes — just check activemask in the hostcall path.

## Skeptic Challenges

1. **Approach C assumes convergence = safe batching**: But `println!()` with different format args produces different-length strings per lane. Batching into 1 hostcall requires either: (a) only lane 0 prints (losing other lanes' output), or (b) gathering all lanes' strings into one buffer. This is non-trivial.

2. **PAL yield is fundamentally hard**: `std::io::Write::write()` returns `io::Result<usize>`, not `Poll<...>`. You can't return `Pending` from a sync function. The MIR pass inserts yield points at `.await` but `println!()` has no `.await` inside it.

3. **Real question**: Does the user want `println!()` from all 32 lanes to produce 32 output lines (current behavior), or 1 line (warp-cooperative)? This affects the design fundamentally.

4. **Criterion 3 ("PAL yields instead of spin-waiting") may be impossible without making PAL async**: If the I/O functions are synchronous, they MUST block. The only option is to make the blocking more efficient (nanosleep, warp-yield) but not truly async.
