## Technical Analysis — 5 Directions

### Direction 1: Patched std in sysroot (HIGHEST PRIORITY)

**Goal**: `use std::fs::File` in GPU kernel without importing gpu-runtime Futures.

**Current state**:
- 9 patch files + 5 new `.rs` files in `std-patches/`
- `build-toolchain.bat` Step 4 applies them to `patched-rustc/library/std/`
- `bootstrap.toml` includes `nvptx64-nvidia-cuda` as a target
- `python x.py build compiler library` should build std for nvptx64
- `gpu-kernel-std` and `std-build-test` already have `build-std = ["std", "core", "panic_abort"]`

**What's needed**:
1. Build the patched toolchain with std patches applied (Step 4 in build-toolchain.bat)
2. Verify `x.py build` succeeds with std for nvptx64-nvidia-cuda
3. Switch kernel configs from `build-std = ["core"]` to `build-std = ["std", "core", "panic_abort"]`
4. Test: kernel with `use std::fs::File; File::create("test.txt")` compiles to PTX

**Feasibility**: HIGH. The patches exist, the build script exists, the allocator exists.
The main question is whether `x.py build` will succeed end-to-end for nvptx64.

**Risks**:
- **LLVM nvptx codegen surprises**: std pulls in much more code than core. String formatting,
  HashMap, Vec — all generate LLVM IR that the nvptx backend must handle. Could hit unsupported
  LLVM instructions (e.g., `thread_local`, 128-bit atomics, floating-point exceptions).
- **Link-time symbol resolution**: std depends on many `extern "C"` symbols. gpu-libc must
  provide them all, or we get linker errors. Currently only open/read/write/close/errno are
  stubbed. What about `malloc`/`free` (used by Vec internally)? The slab allocator in
  `sys_alloc_cuda.rs` implements `GlobalAlloc for System` — this should cover it, but
  `#[global_allocator]` registration in the sysroot path may differ from user crate path.
- **Binary size explosion**: std includes a LOT of code. PTX output could balloon from ~5KB
  to 100KB+. CUDA JIT compilation time may increase significantly.
- **Panic infrastructure**: `std` uses `panic_unwind` or `panic_abort`. The `panic_abort`
  profile should work if our panic stub correctly routes to PTX `trap;`. But `core::fmt`
  machinery (used by `write!`, `format!`) pulls in substantial code.
- **`build-std` vs sysroot**: Two paths — (A) build std into the sysroot via `x.py`, or
  (B) use `-Zbuild-std` to rebuild std from patched source per-kernel. Path (B) is simpler
  (no sysroot modification) but requires the patched std source be available. Path (A) gives
  a cleaner UX. User wants (A).

**Dependencies**: Working patched rustc (already built).

**Critical path tasks**:
1. Attempt `x.py build compiler library` with std patches — diagnose failures
2. If sysroot build fails, fallback: use `-Zbuild-std` with `RUST_LIB_SRC` pointing to patched std
3. Create test kernel using `std::fs::File`, `std::io::Write`, `println!`
4. Wire PAL's sync hostcall through to async Futures (deeper integration)

### Direction 2: GPU Executor

**Goal**: Replace 30-line manual poll boilerplate with `executor::block_on(my_async_fn())`.

**Current state**: Every kernel manually creates `RawWaker`, `Waker`, `Context`, `Pin`,
then runs a poll loop with nanosleep. See `async-pipeline/kernel/src/lib.rs` lines 114-149.

**What's needed**:
- `gpu_runtime::executor::block_on<F: Future>(f: F) -> F::Output`
- Configurable yield strategy: nanosleep duration, max poll count, exponential backoff
- Integrate with warp-cooperative: `block_on` must work correctly when the future
  contains `#[warp_cooperative]` code (all lanes must enter block_on together)

**Feasibility**: HIGH. This is straightforward library code.

**Risks**:
- **Warp divergence**: If `block_on` is called by only some lanes, the warp diverges.
  Need to either (a) require all lanes call it, or (b) use activemask to handle partial warps.
- **Timeout behavior**: What happens when a hostcall never completes? Current code loops
  10M times then exits. Executor should have configurable timeout + error path.
- **No real wake mechanism**: GPU has no interrupt. Polling is the only option. The executor
  is fundamentally a poll loop — the question is whether the abstraction is worth the cost
  of hiding this from users.

**Dependencies**: None (can be done in parallel with Direction 1).

**Effort**: Small (1-2 tasks). High value-to-effort ratio.

### Direction 3: PTX codegen patches

**Goal**: Fix LLVM nvptx backend to not emit `.ptr .align N` and to stub panic symbols.

**Current state**:
- `.ptr .align 1` appears in kernel entry point parameters (2 instances in async-pipeline)
- `panic_const_async_fn_resumed` has a body referencing panic infrastructure that doesn't exist on GPU
- Post-processing scripts exist (`postprocess-ptx.sh`, now deleted) but are fragile

**What's needed**:
- Patch LLVM's `NVPTXAsmPrinter.cpp` to suppress `.ptr .align` for kernel params
- Or patch `rustc_codegen_llvm` to set the right metadata so LLVM doesn't emit it
- Add a linker-level transform that replaces undefined panic symbols with `trap;`

**Feasibility**: MEDIUM. Requires understanding LLVM internals.

**Risks**:
- **LLVM version coupling**: Patches against LLVM are version-specific. CI-downloaded LLVM
  (`download-ci-llvm = true`) means we can't patch LLVM itself without building from source.
  Either need `download-ci-llvm = false` (much longer build) or find a rustc-level fix.
- **Upstream changes**: These are nvptx-specific LLVM bugs. Fixing them properly should go
  upstream, but upstream nvptx maintenance is minimal.
- **PTX version compatibility**: `.ptr .align` was removed in PTX ISA 7.8+ as mandatory.
  We could target PTX 7.8+ (`ptxas -arch=sm_86`) to avoid the issue entirely.

**Dependencies**: Requires building LLVM from source for proper fix, or finding a
rustc_codegen_llvm-level workaround.

### Direction 4: Warp-batched hostcall

**Goal**: 32 lanes share 1 hostcall packet. Lane 0 submits, shfl broadcasts result.

**Current state**: Each lane independently submits to packet pool. With 32 lanes active,
32 packets are consumed. Current async-pipeline only runs on thread 0 (tid != 0 returns).

**What's needed**:
- Modify `GpuOpenFuture`, `GpuReadFuture`, `GpuWriteFuture`, `GpuCloseFuture`
- Before submit: check `lane_id()`. If lane 0, submit request. If not, skip.
- After result ready: lane 0 broadcasts result via `shfl.sync.idx` to all lanes.
- All lanes must agree on the file path / fd / buffer — this only makes sense for
  warp-cooperative code where all lanes execute the same I/O.

**Feasibility**: MEDIUM-HIGH. The shfl.sync pattern is already working for
`#[warp_cooperative]` state machine dispatch.

**Risks**:
- **Correctness**: If lanes have different buffer pointers (each lane operates on its own
  data slice), broadcasting one result is wrong. Need clear semantics: is this "all lanes
  do the same I/O" or "each lane does its own I/O but batched"?
- **Mixed-lane I/O**: If lane 3 wants to read file A and lane 7 wants to read file B,
  warp-batching doesn't apply. This only helps when all active lanes do identical I/O.
- **Integration with MIR pass**: The MIR pass inserts convergence barriers, not I/O batching.
  Batching is a runtime optimization, orthogonal to the compiler pass.

**Dependencies**: Direction 2 (executor) helps make the API cleaner. Direction 1 (patched std)
determines whether the Future API or std API is the primary interface.

### Direction 5: Public API

**Goal**: gpu-host as a library crate with docs + examples.

**Current state**: gpu-host exists with `GpuDevice`, kernel launch, hostcall runtime. But it's
structured as an application, not a library.

**What's needed**:
- Clean public API boundary (what's pub, what's internal)
- Documentation with examples
- At least 3 working examples
- Single-command build story

**Feasibility**: HIGH. Mostly documentation and API polish work.

**Dependencies**: Directions 1-4 affect the API surface. Better to stabilize internals first.

## Skeptic Challenges

### What assumptions are untested?

1. **std compiles for nvptx64 at all**. We have patches but haven't attempted the full build.
   `std` has `#[cfg]` gates for target_os, target_arch, etc. Our `target_os = "cuda"` patches
   may miss some `#[cfg(not(...))]` branches that pull in unsupported code (e.g., `std::net`,
   `std::process`, `std::thread`).

2. **Allocator works in sysroot context**. The slab allocator in `sys_alloc_cuda.rs` uses
   `static mut GPU_HEAP` — a 1MB static. On GPU, statics live in global memory. When compiled
   as part of the sysroot (not user crate), does the linker place this correctly? Or does
   each compilation unit get its own copy?

3. **`extern "C"` symbols resolve**. `sys_fs_cuda.rs` declares `extern "C" { fn open(...) }`.
   These must be provided by gpu-libc. But gpu-libc is a user crate — does it link before
   or after sysroot std? With `-Zbuild-std`, the user crate and std are compiled together,
   so symbol resolution should work. With a pre-built sysroot, it may not.

4. **PTX size is manageable**. Unknown until tested. A pathological case: std pulls in
   `core::fmt` which is ~50KB of LLVM IR. The nvptx backend may struggle.

5. **The MIR pass survives std compilation**. The WarpCooperativeTransform pass runs on
   `#[warp_cooperative]` functions only. But does it interfere with std's own compilation?
   It shouldn't (std functions aren't annotated), but edge cases in MIR analysis could cause
   ICEs during sysroot build.

### What could go wrong with patched std in sysroot?

- **Worst case**: `x.py build` fails with hundreds of errors because `std` for nvptx64 tries
  to compile `std::net`, `std::process`, `std::env`, `std::thread` — all of which need OS
  primitives that don't exist on GPU. The patches handle `std::fs`, `std::io`, `std::alloc`,
  but there are ~20 more PAL modules.

- **Mitigation**: The nvptx64 target likely falls into the `unsupported` PAL category for most
  modules (similar to wasm, SGX). The patches add `target_os = "cuda"` branches in the modules
  we care about. Modules we don't care about should fall through to the existing `unsupported`
  stubs. But this needs verification.

- **Medium case**: Build succeeds but linking fails. gpu-libc provides only 5 C functions.
  std's `unsupported` stubs may reference `libc::` symbols that gpu-libc doesn't have.

- **Best case**: Build succeeds, `use std::fs::File` works, PTX is reasonable size. This is
  plausible given that the `std-build-test` crate already has `build-std = ["std"]`.

### Is GPU executor worth the effort vs manual poll?

**Yes**, for three reasons:
1. Every kernel currently copies 30 lines of boilerplate (waker, context, pin, poll loop).
   This is error-prone and obscures the actual kernel logic.
2. Yield strategy (nanosleep duration, backoff) should be tunable without editing every kernel.
3. When std works on GPU, users expect `block_on` — not manual `Pin::new_unchecked`.

The executor is small (~50 lines of library code) with high impact on usability.
