## Skeptic Challenges

### Challenge 1: "Safety audit without GPU testing is theater"
Adding `// SAFETY` comments to `unsafe` blocks documents *intent* but cannot verify *correctness*. The hostcall CAS protocol has subtle ordering requirements (acquire/release semantics, warp-level visibility). Without running on actual hardware, SAFETY comments express what the author *believes* is true, not what *is* true.

**Counter**: This is still valuable. Future contributors (or the author with GPU access) need to understand the safety invariants. Documenting them forces careful reasoning. The alternative — unmarked unsafe blocks — is strictly worse.

**Verdict**: Do it, but frame it as "documenting safety invariants" not "verifying safety."

### Challenge 2: "API renaming is bikeshedding"
The epic says `GpuDevice/KernelBuilder/HostcallRuntime`. The code says `GpuRuntime/HostcallBuffer/HostcallSession`. Is this a real gap or a criteria that was aspirational and the actual implementation chose better names?

**Counter**: `GpuRuntime` wraps `CudaDevice` and does device init + PTX loading + kernel launch + memory ops. That's a runtime, not just a device. `HostcallBuffer` manages the shared memory packet pool — it's a buffer. The current names are accurate. The criteria should be updated, not the code.

**Verdict**: Update the epic's success criteria to reflect the actual (good) API naming.

### Challenge 3: "The project is feature-complete — further work is make-work"
All 11 feature epics are done. The remaining epics are evergreen (low priority). TCP networking was already stretching into "nice to have" territory. What's the actual user need being served by more work?

**Counter**: This is valid. The project has proven its thesis (Rust async/await on GPU) with comprehensive features (file I/O, TCP, std, error handling, debugging, warp-cooperative async). The remaining work is polish. Polish has diminishing returns.

**Verdict**: Focus only on high-signal polish (safety comments) and stop when done. Don't invent work.

### Challenge 4: "202 unsafe blocks is a lot — is a focused audit enough?"
Auditing only hostcall CAS/packet operations covers maybe 30% of unsafe blocks. GPU-runtime has 34 unsafe occurrences. Kernel code has more. A "focused" audit could miss critical issues elsewhere.

**Counter**: The unsafe blocks fall into clear categories:
- **Inline PTX asm** (gpu-runtime, gpu-kernel, examples): These are inherently unsafe by nature — PTX assembly. SAFETY comments here document "this inline asm does X." Value is moderate.
- **Hostcall CAS protocol** (gpu-host, gpu-runtime): Lock-free concurrent code. SAFETY comments here are high-value because the invariants are non-obvious.
- **CUDA FFI** (gpu-host via cudarc): Mostly delegated to cudarc. Low value to audit.
- **Raw pointer ops in std-patches**: PAL layer bridging std to hostcall. Medium value.

**Verdict**: Prioritize hostcall CAS (both host and GPU sides) and std-patches. Skip inline PTX (obvious) and cudarc FFI (upstream's problem).

### Challenge 5: "No tests can run — how do you know anything works?"
319 completed tasks, but the project has no GPU hardware for testing. All verification is compile-only. The inline PTX, CAS protocol, warp synchronization — none of it has been tested on actual hardware.

**Counter**: This is the project's fundamental constraint and has been acknowledged throughout. The architecture is designed to be correct-by-construction where possible (e.g., MIR pass inserts sync barriers at every await point). But yes, the first real GPU test run may reveal issues.

**Verdict**: This is accepted risk. Document it clearly. Don't pretend compile-verification equals testing.

## Recommendations

### Priority 1: Safety Audit — Hostcall Protocol (epic: codebase-health)

**Theme: safety-audit**

Catalog and document `unsafe` blocks in the hostcall CAS/packet protocol (gpu-host `hostcall.rs` + gpu-runtime CAS operations + std-patches PAL layer). Currently 202 unsafe occurrences across the codebase but only 10 have SAFETY comments.

- **safety-audit.1** (investigation): Catalog all unsafe blocks in hostcall.rs, gpu-runtime CAS paths, and std-patches. Classify by risk level (lock-free CAS > raw pointer > inline PTX > FFI).
- **safety-audit.2** (experiment): Add `// SAFETY:` comments to all high/medium-risk unsafe blocks. Document invariants: what must be true for this to be sound, what ordering guarantees are assumed, what could break.

**Rationale**: Highest-signal work remaining. External reviewers will look at unsafe blocks first. No GPU needed. Directly serves codebase-health criterion of being self-documenting.

### Priority 2: Update public-api Epic Criteria (epic: public-api)

The success criteria reference `GpuDevice/KernelBuilder/HostcallRuntime` but the actual API uses `GpuRuntime/HostcallBuffer/HostcallSession`. The actual names are better. Update the criteria to match reality rather than renaming working code.

- **api-criteria.1** (experiment): Update `public-api` epic success criteria in state.toml to reference actual type names. Verify all 4 criteria are met. If so, note epic as effectively complete (though evergreen).

**Rationale**: Low effort, high clarity. Prevents future confusion about whether the API "matches" the spec.

### Priority 3: Module-Level API Documentation (epic: public-api)

gpu-host has 814 doc comments on individual items but no module-level documentation explaining the overall usage pattern: init device → load PTX → allocate hostcall buffer → launch kernel → start listener → collect results.

- **api-docs.1** (experiment): Add `//!` module docs to `gpu-host/src/lib.rs` and `gpu-host/src/hostcall.rs` with usage overview and code examples.

**Rationale**: The one piece of documentation that would most help a new user. Individual doc comments exist but the "how do I use this library?" overview is missing.
