## New Direction Proposals

### 1. Multi-GPU Support (multi-device, NCCL-like primitives)
**What**: Launch kernels on multiple GPUs, with inter-device communication primitives (allreduce, broadcast, scatter/gather) backed by hostcall.
**Demo value**: HIGH — "distributed async GPU" is headline-worthy.
**Feasibility**: MEDIUM — requires multi-device CUDA context management on host side. The hostcall framework already supports per-device sessions. The hard part is efficient inter-GPU data transfer (P2P vs staged through host).
**Effort**: Large (new epic, ~15-20 tasks).

### 2. Async GPU Streams (multiple concurrent kernels)
**What**: Launch multiple kernels concurrently on different CUDA streams, with async coordination from host.
**Demo value**: MEDIUM — useful but not as novel as the existing single-kernel async story.
**Feasibility**: HIGH — mostly host-side work (cuLaunchKernel on different streams + stream synchronization). gpu-host already wraps cuLaunchKernel.
**Effort**: Medium (~8-10 tasks).

### 3. GPU Memory Management (smart pointers, RAII)
**What**: `GpuBox<T>`, `GpuVec<T>`, `GpuSlice<T>` with automatic alloc/free via cuMemAlloc/cuMemFree, plus unified memory support.
**Demo value**: MEDIUM — quality-of-life improvement, not a new capability.
**Feasibility**: HIGH — straightforward wrapper types on host side.
**Effort**: Small-medium (~6-8 tasks).

### 4. Higher-Level Abstractions (GPU iterator, parallel collections)
**What**: `GpuIterator` trait with `.map()`, `.filter()`, `.reduce()` that compile to GPU kernels. Parallel `Vec` operations.
**Demo value**: HIGH — "Rust iterators on GPU" is instantly understandable and compelling.
**Feasibility**: LOW-MEDIUM — generating PTX from closures at runtime is extremely hard. Would likely need to be compile-time with proc macros, which limits expressiveness significantly. The nvptx64 target requires all GPU code to be `#![no_std]` kernels compiled ahead of time, so dynamic kernel generation is out of scope.
**Effort**: Very large, and the result may disappoint vs the promise.

### 5. Documentation / Tutorial Epic
**What**: Step-by-step tutorials, architecture deep-dive, blog post series, video walkthroughs.
**Demo value**: HIGH for adoption, LOW for technical demonstration.
**Feasibility**: HIGH — the code exists, just needs narrative.
**Effort**: Medium (~10 tasks), but low-risk.

### 6. Performance Optimization (occupancy, register pressure)
**What**: Tune kernel launch parameters, minimize register usage, maximize occupancy, profile with NSight.
**Demo value**: LOW — improvements are incremental and hard to show.
**Feasibility**: HIGH — standard GPU optimization work.
**Effort**: Medium, but open-ended.

### 7. Compatibility (different architectures, compute capabilities)
**What**: Test on SM 75/80/86/89/90, handle architecture-specific features (tensor cores, async copy).
**Demo value**: LOW — "it works on more GPUs" is not exciting.
**Feasibility**: MEDIUM — requires access to multiple GPU architectures.
**Effort**: Medium.

### 8. Ecosystem Integration (tokio bridge, wgpu interop)
**What**: Bridge between tokio runtime on host and GPU async tasks. Or interop with wgpu for cross-platform GPU compute.
**Demo value**: HIGH — connects async_gpu to the broader Rust ecosystem.
**Feasibility**: MEDIUM for tokio bridge (host-side async coordination), LOW for wgpu (completely different GPU abstraction layer, would require reimplementing everything).
**Effort**: Tokio bridge: medium (~8-10 tasks). wgpu: prohibitively large.

### 9. Unpark gpu-channels (complete the async pattern)
**What**: Finish mpsc channels + waker integration + producer-consumer demo.
**Demo value**: MEDIUM — completes the async story but is incremental.
**Feasibility**: HIGH — investigation already done, designs exist, oneshot working.
**Effort**: Small (~4 tasks remaining).

## Skeptic Challenges

### Which proposals are most realistic?
- **Proposals 4 (GPU iterators) and 8-wgpu are unrealistic.** GPU iterators would require runtime kernel generation or extremely constrained compile-time macro magic. wgpu operates at a completely different abstraction level (shader-based, not Rust-native).
- **Proposal 1 (multi-GPU) is realistic but large.** The hostcall framework is per-device, so multi-GPU means multiple hostcall sessions + inter-device communication. Doable but significant effort.
- **Proposals 2, 3, 5, 9 are low-risk and achievable.** They build directly on existing infrastructure.

### What has the highest ROI for demonstration value?
The project's unique selling point is: **"Rust async/await running natively on GPU with compiler support."** New directions should amplify this, not dilute it.

- **Multi-GPU** amplifies it: "async/await across multiple GPUs with zero-copy communication."
- **Tokio bridge** amplifies it: "your existing tokio app can offload async tasks to GPU."
- **GPU channels** completes it: "full async runtime on GPU — tasks, channels, executor."
- **GPU iterators** would be compelling but technically infeasible at the quality level needed.
- **Streams, memory, docs, perf, compat** are supporting work, not headlines.

### What about diminishing returns?
The project has already demonstrated everything it set out to prove. 334 research cycles, 362 completed tasks, 16 completed epics. At this point, the highest-value work is either:
1. **One more "wow" feature** that generates a new headline (multi-GPU or tokio bridge)
2. **Polishing what exists** to make it accessible (docs + completing channels)

The worst use of time would be incremental improvements (perf tuning, compat testing) that don't change the story.

## Recommendations

### Top 3 Proposals (priority ordered)

#### 1. **gpu-channels completion** (unpark, priority: medium, effort: small)
**Rationale**: Lowest effort, highest completeness gain. The investigation and design work is already done. Finishing mpsc + waker + demo gives the project a complete async runtime story: executor + channels + futures. This is the "close the loop" work.

**Epic**: Already exists (gpu-channels, parked). Unpark and execute remaining 4 tasks.
**Success criteria**: Already defined — mpsc channel, waker integration, producer-consumer demo.
**Time estimate**: ~4-6 research cycles.

#### 2. **tokio-bridge** (new epic, priority: high, effort: medium)
**Rationale**: Highest ecosystem impact. A tokio::spawn()-like API that transparently offloads async work to GPU would connect async_gpu to every Rust developer who uses tokio. The host side already uses tokio-like patterns internally.

**Epic definition**:
```
id = "tokio-bridge"
title = "Tokio Bridge — bidirectional async coordination between host tokio runtime and GPU"
success_criteria = [
    "GpuRuntime integrates with tokio runtime (hostcall listener runs as tokio task)",
    "gpu_spawn() returns a tokio::JoinHandle-like future that resolves when GPU task completes",
    "Host can await GPU kernel results without blocking the tokio runtime",
    "Demo: tokio server that offloads compute to GPU via async bridge",
]
```
**Time estimate**: ~10-12 research cycles.

#### 3. **multi-gpu** (new epic, priority: medium, effort: large)
**Rationale**: Most impressive headline feature, but significantly more work. Best attempted after tokio-bridge, since multi-GPU coordination benefits from host-side async.

**Epic definition**:
```
id = "multi-gpu"
title = "Multi-GPU — launch and coordinate kernels across multiple devices"
success_criteria = [
    "GpuRuntime supports multiple CUDA devices (enumerate, select, launch per-device)",
    "Per-device hostcall sessions with independent packet pools",
    "Device-to-device data transfer (P2P if available, host-staged fallback)",
    "Demo: multi-GPU parallel computation with result aggregation on host",
]
```
**Time estimate**: ~15-20 research cycles.

### Execution Order
1. **gpu-channels** first (small, closes existing gap, ~1 session)
2. **tokio-bridge** next (medium, high ecosystem value, ~2-3 sessions)
3. **multi-gpu** if momentum continues (large, impressive but optional)

### What NOT to do
- GPU iterators (technically infeasible at quality level needed)
- wgpu interop (completely different paradigm)
- Performance tuning (diminishing returns, not demo-worthy)
- Compatibility testing (requires hardware access, low demo value)
