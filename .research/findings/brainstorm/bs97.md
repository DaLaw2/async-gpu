## Technical Analysis

### Root Cause of MMA Precision Failure

The previous research (precision-fix.1 through tf32-mma.2) established:

1. **f32→f16 input truncation** (30-40% of error): 10-bit mantissa loses ~0.1% per conversion
2. **f16×f16 multiply rounding** (20-30%): each multiply has ~2^{-10} error
3. **K-dimension accumulation** (30-40%): errors compound over K/16 MMA steps

For K=3072 (FFN GEMM2), that's 192 MMA tiles. Each contributes ~0.001 rounding error.
Accumulated: ~0.024 max absolute error per GEMM → divergent top-5 after 12 layers.

### Why Industry Gets Away With It

Key insight the previous research MISSED:

1. **cuBLAS uses split-K reduction**: Large K is split into chunks, each accumulated
   independently in f32, then reduced. This limits per-chunk error.

2. **HuggingFace f16 checkpoints**: Weights are stored in f16 natively — no f32→f16
   truncation at all. Our pipeline downloads f32 weights and converts.

3. **Kahan compensated summation**: Some implementations track rounding residuals
   in the f32 accumulator, achieving near-f64 accuracy for the sum.

4. **Per-channel scaling**: Scale weights to maximize f16 dynamic range utilization
   before MMA, rescale after. This is infrastructure, not QAT.

### Proposed Fix Strategy

**Phase 1: Split-K accumulation (highest impact)**

Current: K=3072 → 192 sequential MMA tiles, each rounding the f32 accumulator.
Fix: Split into chunks of K_CHUNK=256 (16 MMA tiles each). Each chunk has its own
f32 accumulator. Final reduction sums 12 partial results in f32.

Expected error reduction: sqrt(12) ≈ 3.5x improvement per GEMM.
For K=3072: error drops from ~0.024 to ~0.007 per GEMM.

Implementation: Two-pass kernel or cooperative groups reduction.
- Pass 1: Each thread block computes partial [M_tile × N_tile] for K_CHUNK
- Pass 2: Reduce across K chunks (element-wise f32 sum)

**Phase 2: Direct f16 weight loading**

Download HuggingFace f16 checkpoint directly (float16 or bfloat16 format).
Upload f16 weights to GPU without f32→f16 conversion.
Eliminates 30-40% of the error source.

HuggingFace model IDs:
- `openai-community/gpt2` has `model.safetensors` in f32
- But safetensors format supports f16 storage — we can convert once on host

**Phase 3: Kahan compensated accumulation (if needed)**

If split-K + f16 weights aren't enough, add Kahan summation to the MMA accumulator:
```
// Standard: c += mma_result
// Kahan: compensation tracks lost bits
y = mma_result - compensation
t = c + y
compensation = (t - c) - y
c = t
```

Cost: 2 extra f32 registers per accumulator, ~3 extra FMA instructions per tile.
Expected: near-perfect f32 accumulation quality.

**Phase 4: Benchmark and validate**

- GEMM correctness at all GPT-2 dimensions vs f32 FMA reference
- GPT-2 12-layer inference top-5 agreement (target: 2/3 prompts)
- Throughput comparison: MMA vs f32 FMA (target: ≥2x)
- Per-token latency comparison (target: significantly < 68ms)

### Risk Assessment

| Risk | Likelihood | Mitigation |
|------|-----------|------------|
| Split-K adds kernel launch overhead | Medium | Use cooperative groups or atomic reduction, not separate kernel |
| f16 weights still diverge | Low | Kahan summation as fallback |
| Split-K reduces MMA throughput below 2x target | Medium | Tune K_CHUNK size; split-K overhead is O(N_chunks) not O(K) |
| Register pressure from Kahan | Low | Only 2 extra regs; current ~40 regs, limit is 255 |

## Key Design Decisions

1. **Start with f16 MMA, not BF16/TF32**: f16 has the best speedup (1.8x measured)
   and 10-bit mantissa (same as TF32 but K=16 tiles vs K=8). BF16 only 1.4x.

2. **Split-K first, Kahan second**: Split-K is higher impact (error scales with
   sqrt of chunks) and simpler. Kahan is a fallback if split-K alone isn't enough.

3. **3D grid for split-K**: Each (bx, by, bz) block computes M_tile × N_tile × K_chunk.
   Z-dimension reduction via atomicAdd or workspace.

4. **K_CHUNK = 256 as starting point**: 16 MMA tiles per chunk, 12 chunks for K=3072.
   Can tune up/down based on precision-throughput trade-off.
