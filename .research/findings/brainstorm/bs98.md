## Technical Analysis

### YOLOv8-nano Architecture Breakdown

YOLOv8-nano (ultralytics) is a single-stage detector with ~3.2M params.
Architecture components:

| Layer Type | Count in YOLOv8-nano | Parameters |
|-----------|---------------------|------------|
| Conv2D (3x3, stride 1/2) | ~25 | Kernel, bias, BN params |
| BatchNorm2D | ~25 | gamma, beta, running_mean, running_var |
| SiLU activation | ~25 | None (elementwise) |
| Concat | ~5 | None (memory layout) |
| Upsample (2x nearest) | 2 | None (index math) |
| C2f block (bottleneck) | ~8 | Contains Conv2D internally |
| SPPF (MaxPool 5x5) | 1 | None |
| Detection head | 3 scales | Conv2D layers |
| NMS post-processing | 1 | Host-side |

### Minimal Kernel Set

We need these GPU kernels (6 unique operations):

1. **Conv2D** — The workhorse. Handles 3x3, 1x1 kernels with stride 1 or 2, padding.
   Two implementation strategies:
   - **im2col + GEMM**: Reshape input patches into columns, then call existing MMA GEMM.
     Pro: reuses split-K MMA kernel. Con: im2col memory overhead (9x for 3x3).
   - **Direct convolution**: Each thread computes one output pixel by iterating over
     filter taps. Pro: no memory overhead. Con: can't use Tensor Cores easily.

   **Recommendation**: im2col + GEMM for 3x3 convolutions (leverages MMA 2.18x speedup),
   direct convolution for 1x1 (which is just GEMM with channels as K dimension).

2. **BatchNorm + SiLU fused** — Elementwise: `SiLU(gamma * (x - mean) / sqrt(var + eps) + beta)`.
   At inference time BN uses running stats (no reduction needed). This is a simple
   elementwise kernel — one thread per element. Can fuse with SiLU since both are
   pointwise. ~20 lines of inline PTX.

3. **MaxPool2D (5x5)** — Used only in SPPF block. Each thread reads a 5x5 window and
   outputs the maximum. Simple nested loop, no shared memory needed for small windows.

4. **Upsample 2x (nearest neighbor)** — Each output pixel copies from
   `input[y/2][x/2]`. Pure index math, trivially parallel.

5. **Concat** — Concatenate tensors along channel dimension. This is a memory copy
   with offset computation. Can be done on host (just pointer arithmetic into a
   pre-allocated buffer) or as a simple copy kernel.

6. **NMS (Non-Maximum Suppression)** — Post-processing on detection head outputs.
   Sort boxes by confidence, suppress overlapping boxes (IoU > threshold).
   **This should run on host** — it's sequential, small data, and easier to debug.

### Can We Reuse MMA GEMM?

**Yes, heavily.** The split-K MMA GEMM kernel from tensor-core-gemm is directly
applicable:

- **1x1 Conv2D** = GEMM where M=H*W, K=C_in, N=C_out. Direct reuse.
- **3x3 Conv2D via im2col** = GEMM where M=H_out*W_out, K=C_in*9, N=C_out.
  Requires an im2col kernel to reshape input, then standard GEMM.
- **Detection head linear layers** = standard GEMM.

The existing `layer_norm` kernel pattern (warp reduction) is also directly
reusable for BatchNorm (same structure, different formula).

### Image Loading

Options for loading test images without heavy external crates:

1. **PPM/PGM format** — Plain text or binary, trivially parseable in ~50 lines of Rust.
   No compression, no dependencies. Convert any test image to PPM offline.
   **Recommended** — simplest, no new dependencies.

2. **Raw f32 binary** — Pre-process image to raw CHW f32 floats, save as .bin file.
   Even simpler than PPM (just `std::fs::read` + transmute). But less portable.

3. **BMP format** — Uncompressed, parseable without dependencies (~100 lines).
   More complex than PPM due to header/padding.

4. **image crate** — Full-featured but adds a dependency. Against project minimalism.

**Recommendation**: Use PPM (P6 binary) for the test image. Convert a COCO test image
to 640x640 PPM using any offline tool (Python/ImageMagick). Include the PPM in the
repo or download via hostcall. Parse on host, upload pixel data to GPU as f32 CHW tensor.

### Model Weights

YOLOv8-nano weight sources:

1. **ONNX format** — Ultralytics exports to ONNX. We'd need an ONNX parser to extract
   raw weight tensors. The `onnx-pb` or manual protobuf parsing is complex.

2. **PyTorch .pt format** — Proprietary, requires Python to extract.

3. **safetensors format** — We already have a safetensors parser (`gpu-host/model.rs`)!
   Convert YOLOv8-nano weights to safetensors using a one-time Python script:
   ```python
   from ultralytics import YOLO
   import safetensors.torch
   model = YOLO("yolov8n.pt")
   safetensors.torch.save_file(dict(model.model.state_dict()), "yolov8n.safetensors")
   ```
   **Recommended** — reuses existing infrastructure.

4. **Pre-extracted raw binary** — Dump each tensor as a raw f32 .bin file.
   Simplest loading but many files and no metadata.

**Recommendation**: safetensors via existing parser. Extend `model.rs` to support
YOLO weight layout (Conv2D kernel shapes [C_out, C_in, H, W], BN params).

## Skeptic Challenges

### "YOLOv8-nano has complex architecture — is this realistic?"

**Assessment: Realistic but requires disciplined scoping.**

YOLOv8-nano has ~60 layers, but only 6 unique operation types. The C2f block
(bottleneck with skip connections) is just Conv2D + SiLU + Concat repeated.
The real complexity is in:
- Getting the layer graph right (skip connections, concat order)
- Tensor dimension tracking through stride-2 convolutions and upsampling
- Detection head output format (box regression + class probabilities)

Mitigation: Build and test incrementally. First get Conv2D + BN + SiLU working
on a single layer. Then chain into backbone. The detection head is just more
Conv2D layers plus reshape + sigmoid.

**Risk level: Medium.** The kernel code is straightforward. The integration
complexity is in bookkeeping (tensor shapes, memory layout, layer connectivity).

### "Conv2D with MMA: is im2col + GEMM feasible?"

**Assessment: Feasible with caveats.**

im2col for 3x3 conv with C_in=64, H=W=80 creates a matrix of size
(6400 x 576). That's 14.4 MB in f16. For the largest layers (C_in=256,
3x3, H=W=20), im2col creates (400 x 2304) = 3.6 MB. Total im2col workspace
across all layers: ~50 MB peak. RTX 3060 has 12 GB — no problem.

However, for 1x1 convolutions (which are ~40% of YOLOv8-nano layers),
im2col is unnecessary — it's a direct GEMM. This saves significant memory
and kernel launch overhead.

**Alternative**: For small spatial dimensions (later layers, H=W=10-20),
direct convolution may be faster than im2col+GEMM due to the overhead of
the im2col kernel. We should benchmark both paths.

### "How to validate correctness without a reference implementation?"

**Validation strategy (layered)**:

1. **Per-kernel unit tests**: Conv2D on known inputs (e.g., identity filter,
   all-ones filter) where expected output is analytically known.

2. **Per-layer comparison**: Run each layer in PyTorch, dump intermediate
   tensors, compare with GPU output. One-time Python script generates
   reference data.

3. **End-to-end visual check**: Run on a well-known test image (e.g., COCO
   "dog on bicycle"). If we detect dog + bicycle + person, it works.
   Bounding box coordinates don't need to match exactly — just correct
   class labels and roughly correct locations.

4. **Top-K confidence check**: Compare top-5 detected objects (class + confidence)
   with PyTorch reference. Same approach as GPT-2 top-5 validation.

### Key Design Decisions

1. **im2col + MMA GEMM over direct convolution**: Leverages the proven 2.18x MMA
   speedup. The im2col memory overhead (~50 MB peak) is negligible on RTX 3060 (12 GB).
   For 1x1 convolutions, skip im2col entirely — treat as direct GEMM.

2. **Fuse BN + SiLU into one kernel**: Saves one global memory round-trip per layer.
   Since both are elementwise, fusion is trivial (same thread does both ops).

3. **Host-side NMS**: NMS is inherently sequential (sort + suppress loop). Running it
   on GPU provides no speedup for the ~100-1000 candidate boxes YOLO produces.
   Host-side is simpler, debuggable, and fast enough.

4. **safetensors for weights**: Reuses existing infrastructure from GPT-2.
   One-time Python conversion script is acceptable (runs once, output committed).

5. **PPM for test image**: Zero dependencies, trivial parser. The 640x640 RGB PPM is
   ~1.2 MB uncompressed — small enough to commit or download via hostcall.

6. **f32 throughout (initially)**: Start with f32 FMA convolutions for correctness.
   Once end-to-end works, optionally switch to MMA f16 for speed. The MMA GEMM
   kernel already supports both paths.
