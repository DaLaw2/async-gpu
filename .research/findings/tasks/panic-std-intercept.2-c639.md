# panic-std-intercept.2: GPU warp/thread metadata in std default_hook

## Status: DONE

## What Was Done
Modified `patched-std/src/panicking.rs` to include GPU block/warp/lane metadata
in the panic output format when compiling for `target_os = "cuda"`.

### Changes
1. Added `gpu_panic_indices()` function (line 247) — reads `%ctaid.x` (blockIdx.x)
   and `%tid.x` (threadIdx.x) via inline PTX assembly. Only compiled on CUDA.
2. Modified `default_hook` (line 296) — on CUDA, formats panic output as:
   `thread 'main' (block 0, warp 0, lane 3) panicked at src/main.rs:5:5:\nmessage`
3. Non-CUDA targets retain the original format:
   `thread 'main' (42) panicked at src/main.rs:5:5:\nmessage`

### Build Verification
- x86_64 host build: PASSED (incremental rebuild, 33s)
- nvptx64 target: core/alloc rebuilt; std for nvptx64 requires full kernel build
  (extern C symbols from gpu-runtime are resolved at kernel link time, not sysroot time)
- Patches regenerated via `gen-std-patches.sh`

## Design Decisions
1. **Inline PTX asm in panicking.rs** — rather than adding new extern C functions
   or routing through sys::thread::cuda, we read GPU special registers directly.
   This keeps the change self-contained (one file) and avoids adding new cross-crate APIs.
2. **`cfg(target_os = "cuda")` guard** — matches the cfg pattern used throughout
   patched-std (sys/thread/mod.rs, sys/stdio/mod.rs, etc.).
3. **Block + warp + lane** — chosen over block + raw threadIdx because warp/lane
   is more meaningful for GPU debugging (warp divergence, lane masking).

## Gap: abort path missing set_warp_trapped() and write_panic_to_result()
The no_std panic handler (gpu-runtime::panic_handler!) calls:
- `write_panic_to_result(msg)` — writes error to kernel result buffer
- `set_warp_trapped()` — marks warp as trapped so BlockScope::join_all() can detect it
- `send_panic_hostcall(buf, msg)` — sends SERVICE_PANIC structured message

The std path does NOT call these before `process::abort()` → `trap;`. This means:
- BlockScope::join_all() will spin forever if a std-compiled warp panics
- Host won't get structured error in kernel result buffer
- Only SERVICE_PRINT (plain text) is used, not SERVICE_PANIC (structured)

**To fix**: expose `set_warp_trapped`, `write_panic_to_result`, and optionally
`send_panic_hostcall` as `#[no_mangle] extern "C"` from gpu-runtime, then call
them from a CUDA-specific `abort_internal()` or from the default_hook. This is a
separate task (panic-std-intercept.3).
