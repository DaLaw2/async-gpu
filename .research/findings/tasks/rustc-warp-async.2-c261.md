# rustc-warp-async.2: MIR Pass Design for Warp-Cooperative Async/Await
**Cycle**: 261 | **Theme**: rustc-warp-async | **Kind**: design | **Status**: done

## Overview

`WarpCooperativeTransform` is a custom MIR pass that runs after `StateTransform` (the coroutine-to-state-machine lowering). It rewrites the generated state machine so that lane 0 of a CUDA warp exclusively polls inner futures, while all 32 lanes stay converged via `shfl.sync.idx.b32` broadcasts of discriminants and payload values. The pass only activates for functions annotated with `#[warp_cooperative]` when compiling for `nvptx64` targets.

The transformation is semantically equivalent to what the existing `#[warp_async]` proc macro does at the AST level, but operates on already-lowered MIR, enabling it to handle arbitrary `async fn` bodies with standard `.await` syntax — including loops, nested control flow, and `?` operator — without the proc macro's requirement for restricted macro-call syntax.

---

## Pass Registration

### Location in the pipeline

The pass is registered in `compiler/rustc_mir_transform/src/lib.rs`, in the `mir_drops_elaborated_and_const_checked` pipeline. It runs **after** `StateTransform` and **before** optimization passes that may restructure the CFG (inlining, const-prop, etc.).

```
// In run_optimization_passes() or equivalent:
&[
    // ... existing passes ...
    &coroutine::StateTransform,
    // NEW: warp-cooperative transform (must be after StateTransform)
    &warp_cooperative::WarpCooperativeTransform,
    // ... subsequent passes ...
]
```

### Pass struct

```rust
// compiler/rustc_mir_transform/src/warp_cooperative.rs

pub struct WarpCooperativeTransform;

impl<'tcx> MirPass<'tcx> for WarpCooperativeTransform {
    fn is_enabled(&self, sess: &Session) -> bool {
        // Only on nvptx64 targets
        sess.target.arch == "nvptx64"
    }

    fn run_pass(&self, tcx: TyCtxt<'tcx>, body: &mut Body<'tcx>) {
        // Check for #[warp_cooperative] attribute
        let def_id = body.source.def_id();
        if !has_warp_cooperative_attr(tcx, def_id) {
            return;
        }
        // Must be a coroutine body (post-StateTransform)
        if body.coroutine.is_none() {
            return;
        }
        transform_warp_cooperative(tcx, body);
    }
}
```

### Why this position

1. **After StateTransform**: The coroutine is already lowered to a flat struct + dispatch switch. The pass operates on regular MIR (SwitchInt, Call, Return) without needing to understand coroutine-specific constructs (Yield, CoroutineDrop).
2. **Before optimizations**: The MIR structure is predictable — the dispatch switch, poll calls, and branch patterns are in canonical form. Later passes (inlining, SimplifyCfg) might restructure the CFG and make pattern-matching unreliable.
3. **Before codegen**: The inserted intrinsic calls (shfl.sync, syncwarp) are lowered to LLVM IR normally, and LLVM's NVPTX backend emits the correct PTX instructions.

## Attribute Detection

### Attribute definition

`#[warp_cooperative]` is a new attribute recognized by rustc. It can be registered as:

**Option A — Built-in attribute** (requires `rustc_attr` changes):
```rust
// In compiler/rustc_feature/src/builtin_attrs.rs
gated!(warp_cooperative, Normal, template!(Word), ErrorFollowing,
    experimental!(warp_cooperative));
```

**Option B — Tool attribute under a feature gate** (less invasive):
```rust
#![feature(warp_cooperative)]
#[warp_cooperative]
async fn my_kernel_work() -> u32 { ... }
```

### Detection in the pass

```rust
fn has_warp_cooperative_attr(tcx: TyCtxt<'_>, def_id: DefId) -> bool {
    tcx.get_attrs(def_id, sym::warp_cooperative).next().is_some()
}
```

The attribute is only meaningful on `async fn` items (which become coroutines). If applied to a non-async function, the pass emits a diagnostic warning and does nothing.

### Interaction with the proc macro

When `#[warp_cooperative]` is used, the `#[warp_async]` proc macro is NOT needed. They are mutually exclusive approaches:
- `#[warp_async]` — AST-level state machine generation (current, no rustc changes)
- `#[warp_cooperative]` — MIR-level transformation (this design, requires rustc patch)

## MIR Pattern Matching

After `StateTransform`, the coroutine body has a specific structure. The pass identifies and transforms three key patterns.

### Pattern 1: Dispatch Switch (entry point)

**What to find**: The entry basic block (`bb0`) contains a `SwitchInt` on the coroutine discriminant. This is generated by `StateTransform::create_cases()`.

```
bb0: {
    _2 = discriminant((*_1));     // Read coroutine state discriminant
    switchInt(_2) -> [0: bb_unresumed, 1: bb_returned, 2: bb_poisoned,
                      3: bb_resume0, 4: bb_resume1, ..., otherwise: bb_unreachable]
}
```

**How to identify**: Look for the first `SwitchInt` terminator in the function body where the scrutinee is `Discriminant(Place)` on the self parameter (`_1`). The targets include values 0 (UNRESUMED), 1 (RETURNED), 2 (POISONED), and 3+ (suspension points).

**Detection algorithm**:
```rust
fn find_dispatch_switch(body: &Body<'_>) -> Option<(BasicBlock, &SwitchTargets)> {
    for (bb, data) in body.basic_blocks.iter_enumerated() {
        if let TerminatorKind::SwitchInt { discr, targets, .. } = &data.terminator().kind {
            if is_discriminant_of_self(discr, body) {
                return Some((bb, targets));
            }
        }
    }
    None
}
```

### Pattern 2: Poll Call + Result Branch

**What to find**: Within the state machine, the `.await` desugaring produces a `Call` to `Future::poll`, followed by a `Discriminant` read on the `Poll<T>` result, followed by a `SwitchInt` branching to Ready/Pending handlers.

```
bb_poll: {
    _poll_result = Call(<impl Future>::poll(Pin::new_unchecked(&mut __awaitee), cx))
                   -> [return: bb_check, unwind: bb_cleanup]
}

bb_check: {
    _discr = discriminant(_poll_result);   // 0 = Ready, 1 = Pending
    switchInt(_discr) -> [0: bb_ready, 1: bb_pending]
}

bb_ready: {
    _value = (_poll_result as Ready).0;    // Downcast + field access
    ...
}

bb_pending: {
    // Store current discriminant, return Poll::Pending
    ...
}
```

**How to identify the poll call**: The `Call` terminator's callee is an `Operand::Constant` referencing the `Future::poll` method. After monomorphization, this resolves to a concrete `<T as Future>::poll` instance. Detection:

```rust
fn is_future_poll_call(tcx: TyCtxt<'_>, callee: &Operand<'_>) -> bool {
    if let Operand::Constant(c) = callee {
        if let ty::FnDef(def_id, _) = c.const_.ty().kind() {
            let trait_id = tcx.trait_of_item(*def_id);
            return trait_id == Some(tcx.lang_items().future_trait().unwrap())
                && tcx.item_name(*def_id) == sym::poll;
        }
    }
    false
}
```

**How to identify the result branch**: Starting from the Call's success target block, find a `SwitchInt` on `Discriminant(_poll_result)` where the targets have two arms (0 = Ready, 1 = Pending).

### Pattern 3: Return (completion)

**What to find**: `TerminatorKind::Return` statements, which indicate `Poll::Ready(final_value)` from the outermost state machine.

```
bb_return: {
    // Store final output into the return place
    _0 = Poll::Ready(value);
    return;
}
```

**Detection**: Straightforward — find all `Return` terminators.

## MIR Rewrite Rules

### Rule 1: Broadcast the Dispatch Discriminant

**Before** (post-StateTransform):
```
bb0: {
    _discr = discriminant((*_1));
    switchInt(_discr) -> [0: bb_unresumed, 3: bb_resume0, 4: bb_resume1, ...]
}
```

**After** (post-WarpCooperativeTransform):
```
bb0: {
    _discr = discriminant((*_1));
    _mask = Call(activemask) -> bb0a;
}
bb0a: {
    _discr_broadcast = Call(shfl_sync_idx_u32, _mask, _discr as u32, const 0u32) -> bb0b;
}
bb0b: {
    switchInt(_discr_broadcast) -> [0: bb_unresumed, 3: bb_resume0, 4: bb_resume1, ...]
}
```

**Rationale**: All lanes must agree on which state to execute. Lane 0 reads the authoritative discriminant from the coroutine struct; all other lanes receive it via shuffle. This ensures warp convergence at the dispatch switch.

### Rule 2: Leader-Only Poll with Result Broadcast

**Before**:
```
bb_poll: {
    _poll = Call(Future::poll, pin, cx) -> bb_check;
}
bb_check: {
    _poll_discr = discriminant(_poll);
    switchInt(_poll_discr) -> [0: bb_ready, 1: bb_pending]
}
```

**After**:
```
bb_poll: {
    _lane = Call(lane_id) -> bb_poll_gate;
}
bb_poll_gate: {
    _is_leader = Eq(_lane, const 0u32);
    switchInt(_is_leader) -> [true: bb_leader_poll, false: bb_follower_join]
}
bb_leader_poll: {
    _poll = Call(Future::poll, pin, cx) -> bb_broadcast_discr;
}
bb_follower_join: {
    // Followers skip the poll call and proceed to broadcast
    goto -> bb_broadcast_discr;
}
bb_broadcast_discr: {
    _mask = Call(activemask) -> bb_broadcast_discr2;
}
bb_broadcast_discr2: {
    // Leader has the real discriminant; followers get 0 (overwritten by broadcast)
    _poll_discr = discriminant(_poll);    // Only meaningful on lane 0
    _bc_discr = Call(shfl_sync_idx_u32, _mask, _poll_discr as u32, const 0u32) -> bb_sync1;
}
bb_sync1: {
    Call(syncwarp, _mask) -> bb_switch;
}
bb_switch: {
    switchInt(_bc_discr) -> [0: bb_ready_bc, 1: bb_pending]
}
```

**Key subtlety — follower lanes reading `discriminant(_poll)`**: On follower lanes, `_poll` was never written (the `Call` was skipped). The pass must ensure that (a) `_poll` is initialized to a default before the branch, or (b) the discriminant read is predicated. Approach (b) is preferred:

```
bb_broadcast_discr2: {
    _raw_discr = const 0xFFFF_FFFFu32;     // Sentinel, will be overwritten
    switchInt(_is_leader) -> [true: bb_read_discr, false: bb_do_broadcast]
}
bb_read_discr: {
    _raw_discr = discriminant(_poll) as u32;
    goto -> bb_do_broadcast;
}
bb_do_broadcast: {
    _bc_discr = Call(shfl_sync_idx_u32, _mask, _raw_discr, const 0u32) -> bb_sync1;
}
```

### Rule 3: Broadcast the Ready Payload

**Before**:
```
bb_ready: {
    _value = (_poll as Ready).0;    // Downcast + field projection
    // ... use _value ...
}
```

**After** (for u32 payload):
```
bb_ready_bc: {
    // Leader: extract the actual value
    _raw_val = const 0u32;
    switchInt(_is_leader) -> [true: bb_extract_val, false: bb_broadcast_val]
}
bb_extract_val: {
    _raw_val = (_poll as Ready).0;
    goto -> bb_broadcast_val;
}
bb_broadcast_val: {
    _bc_val = Call(shfl_sync_idx_u32, _mask, _raw_val, const 0u32) -> bb_sync2;
}
bb_sync2: {
    Call(syncwarp, _mask) -> bb_resume_with_val;
}
bb_resume_with_val: {
    // All lanes now have the same value in _bc_val
    // Replace all subsequent uses of _value with _bc_val
    ...
}
```

### Rule 4: Barrier Before Return

**Before**:
```
bb_return: {
    _0 = Poll::Ready(final_output);
    return;
}
```

**After**:
```
bb_return: {
    _0 = Poll::Ready(final_output);
    _mask2 = Call(activemask) -> bb_ret_sync;
}
bb_ret_sync: {
    Call(syncwarp, _mask2) -> bb_actual_return;
}
bb_actual_return: {
    return;
}
```

**Rationale**: All lanes must exit the function together. Without the barrier, some lanes might return before others reach the return point, causing divergence in the caller.

## Intrinsic Calls

### Representation in MIR

The pass inserts calls to warp intrinsics. Three options for representing these in MIR:

#### Option 1: Inline Assembly (RECOMMENDED)

Use `TerminatorKind::InlineAsm` with PTX inline assembly strings, matching the project's existing approach (`gpu-atomics` crate).

```rust
// shfl.sync.idx.b32
InlineAsm {
    template: "shfl.sync.idx.b32 $0, $1, $2, 31, $3;",
    operands: [
        InlineAsmOperand::Out { reg: "r", place: _result },
        InlineAsmOperand::In { reg: "r", value: _src_val },
        InlineAsmOperand::In { reg: "r", value: _src_lane },
        InlineAsmOperand::In { reg: "r", value: _mask },
    ],
    destination: Some(bb_next),
}

// bar.warp.sync (syncwarp)
InlineAsm {
    template: "bar.warp.sync $0;",
    operands: [
        InlineAsmOperand::In { reg: "r", value: _mask },
    ],
    destination: Some(bb_next),
}

// activemask
InlineAsm {
    template: "activemask.b32 $0;",
    operands: [
        InlineAsmOperand::Out { reg: "r", place: _mask },
    ],
    destination: Some(bb_next),
}

// mov.u32 %laneid
InlineAsm {
    template: "mov.u32 $0, %laneid;",
    operands: [
        InlineAsmOperand::Out { reg: "r", place: _lane },
    ],
    destination: Some(bb_next),
}
```

**Rationale**: (1) Proven to work — `gpu-atomics` uses this pattern for all warp intrinsics. (2) No dependency on LLVM recognizing `llvm.nvvm.*` intrinsics, which are broken on some nightly LLVM versions (see ADR-1 amendment). (3) The MIR pass generates the same inline asm that a user would write manually.

#### Option 2: LLVM Intrinsics (NOT recommended)

Would use `Call` terminators targeting LLVM intrinsics like `llvm.nvvm.shfl.sync.idx.i32`. Rejected because NVVM intrinsics are unreliable on current nightly LLVM (per project technical notes).

#### Option 3: Extern Functions (fallback)

Declare `extern "C" { fn __shfl_sync_idx_u32(...) -> u32; }` and emit `Call` terminators. Requires linker support that PTX doesn't have (no PTX linker). Would only work if the functions are always inlined via LTO — fragile.

### Creating Inline Asm in MIR

The pass constructs `InlineAsmOperand` values and a `TerminatorKind::InlineAsm` terminator. The template string is a `&[InlineAsmTemplatePiece]`. Helper function:

```rust

    body: &mut Body<'tcx>,
    mask: Local,
    src: Local,
    src_lane: Local,
    dest: Local,
    source_info: SourceInfo,
) -> BasicBlock {
    let bb = body.basic_blocks_mut().push(BasicBlockData::new(None));
    // ... construct InlineAsm terminator with template "shfl.sync.idx.b32 ..."
    bb
}
```

## Type Broadcasting

The broadcast strategy depends on the `Output` type of the polled future.

### Tier 1: Primitive types (u32, i32, f32, bool)

Single `shfl.sync.idx.b32` call. `bool` is zero-extended to u32, broadcast, then truncated.

```
_bc = shfl.sync.idx.b32(mask, value, 0);
```

Cost: 1 shuffle instruction per yield point.

### Tier 2: 64-bit types (u64, i64, f64)

Two `shfl.sync.idx.b32` calls — broadcast low and high 32-bit halves separately, then reassemble. This matches the existing pattern in `warp_hostcall_wait_u64`:

```
_lo = value as u32;
_hi = (value >> 32) as u32;
_bc_lo = shfl.sync.idx.b32(mask, _lo, 0);
_bc_hi = shfl.sync.idx.b32(mask, _hi, 0);
_bc_value = (_bc_hi as u64) << 32 | (_bc_lo as u64);
```

Cost: 2 shuffle instructions per yield point.

### Tier 3: Small structs (up to 256 bytes)

Decompose the struct into 32-bit fields and broadcast each field individually. For a struct of N bytes, this requires ceil(N/4) shuffle instructions.

**Detection**: At MIR level, the pass computes `tcx.layout_of(output_ty).size` to determine the broadcast cost. If size <= 256 bytes (64 shuffles), use field-by-field decomposition.

**Implementation**: Use `memcpy`-style semantics — treat the value as a `[u32; N/4]` array, broadcast each element, reassemble.

```
// For a 12-byte struct (3 x u32):
_ptr = &value as *const u32;
_w0 = *_ptr;
_w1 = *(_ptr.offset(1));
_w2 = *(_ptr.offset(2));
_bc0 = shfl.sync.idx.b32(mask, _w0, 0);
_bc1 = shfl.sync.idx.b32(mask, _w1, 0);
_bc2 = shfl.sync.idx.b32(mask, _w2, 0);
// Write back to destination
*dest_ptr = _bc0;
*(dest_ptr.offset(1)) = _bc1;
*(dest_ptr.offset(2)) = _bc2;
```

### Tier 4: Large types and types with references (SHARED MEMORY)

For types > 256 bytes, or types containing references/pointers (which cannot be meaningfully broadcast), use shared memory:

1. Lane 0 writes the value to a `__shared__` buffer
2. `syncwarp(mask)` — barrier
3. All lanes read from the shared buffer

**MIR representation**: The shared memory buffer is allocated as a `static` with `#[link_section = ".shared"]` (nvptx64 convention). The pass emits store/load sequences with the barrier.

**Limitation**: Shared memory is a scarce resource (48-96 KB per SM). The pass emits a compile-time warning if the total shared memory usage for broadcasts exceeds 4 KB per function.

### Tier 5: Unsupported types (COMPILE ERROR)

The following types cause a compile error if they appear as `Output` of a future polled inside `#[warp_cooperative]`:
- `dyn Trait` (dynamically sized — size unknown at compile time)
- Types containing raw pointers or references that point into the coroutine struct (self-referential)
- Types implementing `Drop` with side effects (drop runs on all lanes but value only exists on lane 0)

## Edge Cases

### Nested Futures

When an async fn awaits another async fn, the inner future's state machine is embedded within the outer state machine by `StateTransform`. Each nested `.await` produces its own poll-call + SwitchInt pattern in the MIR.

**Handling**: The pass processes ALL poll-call patterns uniformly, regardless of nesting depth. Each poll call site gets the same leader-only/broadcast transformation. This works because after `StateTransform`, the nesting is already flattened into the outer state machine's dispatch switch.

**Caveat**: If the inner future is itself `#[warp_cooperative]`, it has already been transformed by this pass. The outer future's poll of the inner future then polls a warp-cooperative state machine — which is correct, because the inner poll also broadcasts its results.

### Multiple `.await` Points

Each `.await` produces one suspension point (one dispatch variant, one poll-call site). The pass iterates over all poll-call sites and transforms each independently.

**State numbering**: The discriminant values (3, 4, 5, ...) correspond to suspension points. Broadcasting the discriminant ensures all lanes resume from the same suspension point.

### Error Propagation (`?` Operator)

The `?` operator on an `.await` expression desugars to:
```rust
match future.await {
    Ok(val) => val,
    Err(e) => return Err(e),
}
```

After `StateTransform`, this becomes a `SwitchInt` on the `Result` discriminant following the `Poll::Ready` extraction. The pass must broadcast BOTH:
1. The `Poll` discriminant (Ready vs Pending)
2. The `Result` discriminant (Ok vs Err)
3. The payload (Ok value or Err value)

**Implementation**: After broadcasting the Ready payload, check if it's a `Result` type. If so, decompose and broadcast the `Result` discriminant, then broadcast the appropriate variant's payload.

```
// After poll broadcast determines Ready:
_result = broadcast_ready_payload(...);
_result_discr = discriminant(_result);
_bc_result_discr = shfl.sync.idx.b32(mask, _result_discr, 0);
switchInt(_bc_result_discr) -> [0: bb_ok, 1: bb_err]

bb_ok: {
    _ok_val = (_result as Ok).0;
    _bc_ok_val = broadcast_typed(mask, _ok_val);
    // continue
}
bb_err: {
    _err_val = (_result as Err).0;
    _bc_err_val = broadcast_typed(mask, _err_val);
    // early return with Err
}
```

### Panic Handling

If lane 0 panics during a poll call, the `trap` instruction kills the warp (on SM70+). All lanes die together because `trap` is a warp-level instruction — there is no partial-warp trap.

**For unwind paths**: The poll call's `Call` terminator has an `unwind` target. The pass does NOT transform unwind paths — if an unwind occurs, the standard panic/abort mechanism takes over. On nvptx64, this means `trap; exit;` which kills all lanes.

**No special handling needed**: GPU panics are terminal. The pass does not attempt recovery.

### Loops Containing `.await`

```rust
loop {
    let item = stream.next().await;
    if item.is_none() { break; }
    process(item.unwrap());
}
```

After `StateTransform`, this becomes a cycle in the dispatch switch — the Pending path sets the discriminant back to the same suspension point, and the Ready path may loop back. The pass handles this naturally because it transforms each poll-call site independently; the loop structure is already encoded in the dispatch switch targets.

### Conditional `.await`

```rust
if condition {
    a.await;
} else {
    b.await;
}
```

After `StateTransform`, each branch's `.await` becomes a separate suspension point with its own discriminant value. The pass transforms each poll-call site independently. **Critical requirement**: `condition` must be evaluated uniformly (all lanes must take the same branch). Since the discriminant is broadcast, this is automatically enforced — all lanes execute the same suspension point.

**Correctness argument**: The dispatch switch is on the broadcast discriminant. If lane 0 took the `if` branch and suspended at point N, all lanes resume at point N. The condition evaluation is embedded in the pre-suspension code, which only lane 0 executes. All lanes follow lane 0's control flow decisions.

## Limitations

### 1. Self-Referential Borrows Across Yield Points

Standard `async fn` can hold references across `.await` points (e.g., `let x = &mut data; foo.await; *x = 1;`). The compiler stores these references in the coroutine struct. In a warp-cooperative context, follower lanes would hold stale pointers into lane 0's coroutine struct.

**Status**: UNSUPPORTED. The pass must reject functions where the liveness analysis shows references live across suspension points. Detection: check `CoroutineLayout.field_tys` for reference types in suspension point variants.

### 2. Trait Object Futures (`dyn Future`)

`dyn Future<Output = T>` hides the concrete future type. The pass cannot determine the layout of `T` at compile time, preventing field-by-field broadcast generation.

**Status**: COMPILE ERROR. Emit diagnostic: "warp_cooperative does not support polling trait object futures".

### 3. Side-Effectful Drops on Broadcast Values

If the `Output` type implements `Drop`, the drop will run on all 32 lanes, but only lane 0 owns the real value. This can cause double-free or other unsoundness.

**Status**: COMPILE ERROR for types implementing `Drop`. Emit diagnostic: "warp_cooperative output types must not implement Drop".

### 4. Maximum Broadcast Size

Practical limit of ~256 bytes per broadcast (64 shuffle instructions). Larger payloads cause excessive register pressure and instruction count.

**Status**: COMPILE WARNING if output type exceeds 256 bytes. COMPILE ERROR if it exceeds 1024 bytes.

### 5. Non-Uniform Warp Execution

The pass assumes all 32 lanes are active. If some lanes are inactive (e.g., due to earlier divergence or launch configuration with fewer than 32 threads), the shuffle broadcast is incorrect — inactive lanes don't participate in `shfl.sync`.

**Mitigation**: Use `activemask()` instead of hardcoded `0xFFFFFFFF` for the mask parameter. Lanes not in the active mask are undefined but won't corrupt active lanes' values.

### 6. Recursion

Recursive async functions would create unbounded suspension points. The pass does not limit recursion, but GPU stack space is limited (~1 KB per thread by default). This is a general GPU limitation, not specific to this pass.

### 7. Multiple Coroutines Per Function

If a function contains multiple independent async blocks or closures, each produces a separate coroutine body. The pass transforms each body independently — no cross-coroutine coordination.

## ADR

See ADR-016 in `decisions.md` — this design document is the detailed specification referenced by that decision record.

**Key design choices made in this document**:
1. Inline PTX assembly for intrinsics (not LLVM intrinsics) — aligns with project's existing approach
2. Leader predication via `switchInt(_is_leader)` rather than PTX `@p` predicated instructions — stays at MIR level
3. Per-field broadcast decomposition for structs — avoids shared memory for common cases
4. Reject self-referential borrows, trait objects, and Drop types — soundness over generality
5. `activemask()` for dynamic lane membership — handles non-full warps

## Implementation Roadmap

### Phase 1: Skeleton Pass (no-op)
- Register the pass in the pipeline
- Detect `#[warp_cooperative]` attribute
- Emit diagnostic: "warp_cooperative: found N suspension points"
- No MIR modifications

### Phase 2: Discriminant Broadcast
- Implement Rule 1 (dispatch switch broadcast)
- Verify all lanes enter the same state

### Phase 3: Leader-Only Poll
- Implement Rule 2 (leader gates the poll call, broadcasts result)
- Handle u32 output type only

### Phase 4: Type Broadcasting
- Implement Rule 3 for u64 and small structs
- Add shared memory fallback for large types

### Phase 5: Edge Cases
- `?` operator (Result broadcasting)
- Barriers before Return (Rule 4)
- Validation: reject self-referential borrows, dyn Future, Drop types

### Phase 6: Testing
- Unit tests with known MIR patterns
- Integration tests with actual nvptx64 compilation
- Comparison with `#[warp_async]` proc macro output for identical kernels
